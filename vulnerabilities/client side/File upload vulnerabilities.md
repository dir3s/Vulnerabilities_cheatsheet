File upload vulnerabilities виникають тоді, коли вебсервер дозволяє користувачам **завантажувати файли у свою файлову систему** без належної перевірки таких параметрів, як **назва файлу, тип, вміст або розмір**. Недостатнє застосування обмежень може призвести до того, що навіть **проста функція завантаження зображень** буде використана для завантаження **довільних і потенційно небезпечних файлів**. Це може включати навіть **серверні скриптові файли**, які дозволяють виконувати довільний код на сервері.

У деяких випадках **сам факт завантаження файлу** вже може спричинити шкоду. Інші атаки можуть вимагати **додаткового HTTP-запиту** до цього файлу, зазвичай для того, щоб **спровокувати його виконання сервером**.

Якщо **ім’я файлу не перевіряється належним чином**, це може дозволити атакувальнику **перезаписати критично важливі файли**, просто завантаживши файл з такою самою назвою. Якщо сервер також уразливий до **directory traversal**, це може означати, що атакувальник здатний завантажувати файли у **непередбачені каталоги**.

## How do web servers handle requests for static files?
Історично вебсайти майже повністю складалися зі статичних файлів, які передавалися користувачам за запитом. Як наслідок, шлях кожного запиту можна було співвіднести 1:1 з ієрархією каталогів і файлів на файловій системі сервера. Сьогодні вебсайти дедалі більше стають динамічними, і шлях запиту часто не має прямого відношення до файлової системи взагалі. Тим не менш, вебсервера все ще обробляють запити на деякі статичні файли, такі як стилі, зображення та інші.

Процес обробки цих статичних файлів в основному залишився незмінним. На певному етапі сервер аналізує шлях запиту, щоб визначити розширення файлу. Потім він використовує це для визначення типу файлу, зазвичай порівнюючи його з попередньо налаштованими відповідностями між розширеннями та MIME-типами. Далі все залежить від типу файлу та конфігурації сервера.

- Якщо тип файлу не є виконуваним, наприклад, зображення або статична HTML-сторінка, сервер може просто надіслати вміст файлу клієнту у відповіді HTTP.
- Якщо файл є виконуваним, наприклад, PHP-файл, і сервер налаштований на виконання таких файлів, він присвоїть змінні на основі заголовків і параметрів HTTP-запиту, перш ніж запустити скрипт. Результуючий вихід потім може бути надісланий клієнту у відповіді HTTP.
- Якщо файл є виконуваним, але сервер не налаштований на виконання таких файлів, він зазвичай відповість помилкою. Однак у деяких випадках вміст файлу може бути все ж надісланий клієнту як простий текст. Такі некоректні налаштування можуть іноді бути використані для витоку вихідного коду та іншої чутливої інформації. 

Заголовок **Content-Type** у відповіді може надати підказки щодо того, який тип файлу сервер вважає тим, що він надіслав. Якщо цей заголовок не був явно заданий кодом застосунку, він зазвичай містить результат відповідності між розширеннями файлів і MIME-типами.

`<?php echo system($_GET['command']); ?>` - дозволяє виконувати команди на сервері

## Exploiting flawed validation of file uploads (є якісь певні обмеження)

Під час надсилання HTML-форм браузер зазвичай відправляє введені дані у POST-запиті з типом вмісту `application/x-www-form-urlencoded`. Це добре підходить для передавання простого тексту, наприклад імені чи адреси. Однак цей формат **не підходить для передавання великих обсягів бінарних даних**, таких як зображення або PDF-файл. У таких випадках використовується тип вмісту `multipart/form-data`.

Один зі способів, яким вебсайти намагаються перевіряти завантажувані файли, — це перевірка того, що **заголовок `Content-Type` відповідає очікуваному MIME-типу**. Наприклад, якщо сервер очікує лише зображення, він може дозволяти тільки типи `image/jpeg` та `image/png`.

Проблеми виникають тоді, коли сервер **безумовно довіряє значенню цього заголовка**. Якщо не виконується додаткова перевірка, чи справді вміст файлу відповідає заявленому MIME-типу, **такий захист легко обійти** за допомогою інструментів на кшталт **Burp Repeater**.

## Preventing file execution in user-accessible directories

Хоча, безумовно, краще **спочатку не допускати завантаження небезпечних типів файлів**, другою лінією захисту є **заборона серверу виконувати будь-які скрипти**, які все ж змогли пройти перевірки.

Як запобіжний захід, сервери зазвичай виконують лише ті скрипти, **MIME-типи яких явно дозволені в конфігурації**. В іншому випадку сервер може просто повернути повідомлення про помилку або, в деяких випадках, **віддати вміст файлу як звичайний текст**:

`GET /static/exploit.php?command=id HTTP/1.1 Host: normal-website.com   HTTP/1.1 200 OK Content-Type: text/plain Content-Length: 39  <?php echo system($_GET['command']); ?>`

Така поведінка може бути цікавою сама по собі, оскільки **дозволяє витік вихідного коду**, але вона **зводить нанівець спроби створити веб-шел**.

Подібна конфігурація часто **відрізняється залежно від директорії**. Каталог, у який завантажуються файли від користувачів, зазвичай має **набагато суворіші обмеження**, ніж інші місця у файловій системі, які вважаються недоступними для кінцевих користувачів. Якщо вам вдасться **завантажити скрипт в іншу директорію**, яка не призначена для користувацьких файлів, сервер може **виконати ваш скрипт**.

Вебсервери часто використовують поле `filename` у запитах `multipart/form-data`, щоб визначити **ім’я файлу та шлях**, за яким його буде збережено. Тобто може бути дві вразливості одночасно, file upload та path travelsal, тобто Content-Disposition: form-data; name="avatar"; filename="..%2fshell.php" збереже файл не в /files/avatars, а в /file, що дозволить його виконати.
## Insufficient blacklisting of dangerous file types

Один із найбільш очевидних способів запобігти завантаженню шкідливих скриптів — це **додавання потенційно небезпечних розширень файлів**, таких як `.php`, **до чорного списку**.

Однак підхід із чорними списками **спочатку є помилковим**, оскільки дуже складно явно заблокувати **всі можливі розширення файлів**, які можуть бути використані для виконання коду. Такі чорні списки інколи можна **обійти**, використовуючи **менш відомі або альтернативні розширення**,
які все ще можуть виконуватися сервером, наприклад `.php5`, `.shtml` тощо.

Вебсервери використовують конфігураційні файли, якщо вони присутні, але зазвичай **до них неможливо отримати доступ через HTTP‑запити**. Проте іноді трапляються сервери, які **не забороняють завантаження власних шкідливих конфігураційних файлів**.

У такому випадку, навіть якщо потрібне розширення файлу знаходиться у чорному списку, ви можете **обманути сервер**, змусивши його **зіставити довільне користувацьке розширення файлу з виконуваним MIME‑типом**.

Як приклад можна взяти випадок, коли ми працюємо з апаче сервером і маємо доступ до редагування **.htaccess**, та при спробі завантаження файлу з розширенням .php ми отримуємо відповідь сервера, що даний тип файлі не приймається:
- Зміни значення параметра **filename** на **.htaccess**
    
- Зміни значення заголовка **Content-Type** на **text/plain**
    
- Замінити вміст файлу (PHP‑код) на таку директиву Apache:
    
    `AddType application/x-httpd-php .l33t` 
Тобто ми змінюємо конфігурацію додаючи правило яке наказує Apache обробляти файли з розширенням **.l33t** як виконувані PHP‑скрипти, тому навіть після завантаження файлу з розширенням .l33t, сервер всеодно буде обробляти його як php файл.

## Obfuscating file extensions

Навіть найретельніші чорні списки потенційно можна обійти, використовуючи **класичні техніки обфускації**. Припустимо, код перевірки є **чутливим до регістру** і не розпізнає, що `exploit.pHp` насправді є файлом `.php`. Якщо ж код, який згодом зіставляє розширення файлу з MIME‑типом, **не є чутливим до регістру**, така невідповідність дозволяє пропустити шкідливі PHP‑файли через перевірку, і з часом сервер може їх виконати.

Подібного ефекту також можна досягти за допомогою таких технік:

- **Використання кількох розширень.** Залежно від алгоритму обробки імені файлу, наступний файл може бути інтерпретований або як PHP‑файл, або як JPG‑зображення:  
    `exploit.php.jpg`
    
- **Додавання символів у кінці імені.** Деякі компоненти видаляють або ігнорують пробіли, крапки та подібні символи в кінці:  
    `exploit.php.`
    
- **URL‑кодування (або подвійне URL‑кодування)** крапок, слешів або зворотних слешів. Якщо значення не декодується під час перевірки розширення, але пізніше декодується на сервері, це може дозволити завантажити шкідливі файли, які інакше були б заблоковані:  
    `exploit%2Ephp`
    
- **Додавання крапок з комою або нульових байтів (URL‑кодовних)** перед розширенням. Якщо перевірка написана мовою високого рівня (наприклад, PHP або Java), а сервер обробляє файл за допомогою низькорівневих функцій на C/C++, це може призвести до різного трактування кінця імені файлу:  
    `exploit.asp;.jpg` або `exploit.asp%00.jpg` - %00 (NULL) байт відкидає все після себе
    
- **Використання багатобайтових Unicode‑символів**, які після конвертації або нормалізації Unicode можуть перетворюватися на нульові байти або крапки. Послідовності на кшталт `xC0 x2E`, `xC4 xAE` або `xC0 xAE` можуть бути інтерпретовані як `x2E`, якщо ім’я файлу спочатку обробляється як UTF‑8, а потім перетворюється в ASCII перед використанням у шляху.
    

Інші захисні механізми передбачають **видалення або заміну небезпечних розширень**, щоб запобігти виконанню файлу. Якщо така трансформація **не застосовується рекурсивно**, можна розмістити заборонений рядок так, що після його видалення все одно залишиться валідне розширення. Наприклад, якщо видаляти `.php` з такого імені файлу:

`exploit.p.phphp`

У результаті все ще залишиться допустиме розширення `.php`.

## Flawed validation of the file's contents

Замість того щоб беззастережно довіряти значенню `Content-Type`, вказаному в запиті, більш захищені сервери намагаються **перевіряти, чи відповідає фактичний вміст файлу очікуваному типу**.

У випадку функції завантаження зображень сервер може перевіряти **внутрішні властивості зображення**, наприклад його розміри. Якщо, наприклад, спробувати завантажити PHP‑скрипт, він взагалі не матиме жодних розмірів. Тому сервер може зробити висновок, що це **не може бути зображенням**, і відхилити завантаження.

Аналогічно, деякі типи файлів завжди містять **специфічну послідовність байтів** у заголовку або кінці файлу. Їх можна використовувати як **відбиток або сигнатуру** для визначення того, чи відповідає вміст очікуваному типу. Наприклад, JPEG‑файли завжди починаються з байтів **FF D8 FF**.

Це значно **надійніший спосіб перевірки типу файлу**, однак і він **не є абсолютно безпечним**. За допомогою спеціальних інструментів, таких як **ExifTool**, досить легко створити **поліглот‑JPEG‑файл**, який містить шкідливий код у своїх метаданих.
Як приклад  ось команда:
```
exiftool -Comment="<?php echo 'START ' . file_get_contents('/home/carlos/secret') . ' END'; ?>" <YOUR-INPUT-IMAGE>.jpg -o polyglot.php 
```
Це **поліглот‑файл** — файл, який є **одночасно валідним JPEG і валідним PHP‑скриптом**.
 
 **Коли сервер перевіряє файл**

- Дивиться на:
    - сигнатуру JPEG (`FF D8 FF`)
    - розміри зображення
    - Вважає файл безпечним зображенням
    - НЕ перевіряє метадані

**Коли сервер виконує файл як PHP**

- PHP‑інтерпретатор ігнорує JPEG‑байти
- Але бачить `<?php ... ?>`
-  Виконує код у метаданих

Саме тому такий поліглот файл часто може проходити і виконуватись, навіть якщо є перевірка.

## Exploiting file upload race conditions

Сучасні фреймворки є значно краще захищеними від подібних атак. Зазвичай вони **не завантажують файли одразу в кінцеве місце у файловій системі**. Натомість застосовуються запобіжні заходи, наприклад, файл спочатку завантажується в **тимчасову ізольовану (sandbox) директорію**, а його ім’я **рандомізується**, щоб уникнути перезапису наявних файлів. Потім над цим тимчасовим файлом виконується перевірка, і лише після того, як його визнають безпечним, файл переноситься у кінцеве місце.

Втім, розробники іноді **реалізують власну логіку обробки завантаження файлів**, не використовуючи можливості фреймворків. Це не лише досить складно реалізувати правильно, але й може призвести до появи **небезпечних race condition**, які дозволяють зловмиснику **повністю обійти навіть дуже надійні механізми перевірки**.

Наприклад, деякі вебсайти **завантажують файл безпосередньо в основну файлову систему**, а потім **видаляють його**, якщо він не проходить перевірку. Така поведінка характерна для сайтів, які покладаються на **антивірусне програмне забезпечення** або подібні інструменти для перевірки на шкідливий вміст. Хоча перевірка може тривати лише кілька мілісекунд, протягом цього короткого проміжку часу, **поки файл існує на сервері**, зловмисник потенційно може **виконати його**.

Такі вразливості часто є **надзвичайно тонкими**, тому їх складно виявити під час **black‑box тестування**, якщо тільки не вдасться якимось чином отримати доступ до відповідного вихідного коду.

Наприклад, якщо файл завантажується у **тимчасову директорію з випадковою назвою**, теоретично зловмисник не зможе скористатися race condition, оскільки він **не знає назву цієї директорії** і не може надіслати запит до файлу, щоб виконати його. Однак, якщо випадкова назва директорії генерується за допомогою **псевдовипадкових функцій**, таких як `uniqid()` у PHP, її потенційно можна **підібрати методом brute force**.

Щоб полегшити такі атаки, можна спробувати **збільшити час обробки файлу**, тим самим розширивши вікно часу для brute‑force підбору імені директорії. Один зі способів — **завантажити великий файл**. Якщо він обробляється частинами, зловмисник може скористатися цим, створивши **шкідливий файл**, у якому корисне навантаження розміщене на початку, а далі йде **велика кількість довільних байтів‑заповнювачів**.

## Exploiting file upload vulnerabilities without remote code execution
Навіть якщо вам не вдається виконувати скрипти на сервері, ви все ще можете завантажувати файли для **клієнтських атак**. Наприклад, якщо дозволено завантажувати **HTML‑файли або SVG‑зображення**, ви потенційно можете використати теги `<script>` для створення **stored XSS‑пейлоадів**.

Якщо завантажений файл згодом відображається на сторінці, яку відвідують інші користувачі, **їхній браузер виконає цей скрипт** під час рендерингу сторінки. Зауважте, що через обмеження **політики одного джерела (same‑origin policy)** такі атаки працюватимуть лише в тому випадку, якщо завантажений файл віддається **з того ж самого origin**, на який його було завантажено.

Якщо здається, що завантажений файл **зберігається та віддається безпечно**, останнім варіантом є спроба експлуатації **вразливостей, пов’язаних із парсингом або обробкою конкретних форматів файлів**.

Наприклад, якщо відомо, що сервер **парсить файли на основі XML**, такі як документи Microsoft Office **.doc або .xls**, це може бути **потенційним вектором для атак типу XXE (XML External Entity)**.

Варто знати, що деякі вебсервери можуть бути налаштовані на підтримку HTTP‑методу **PUT**. Якщо належний захист відсутній, це може дати **альтернативний спосіб завантаження шкідливих файлів**, навіть якщо на сайті немає явної форми для завантаження файлів.

Приклад запиту:

`PUT /images/exploit.php HTTP/1.1 Host: vulnerable-website.com Content-Type: application/x-httpd-php Content-Length: 49  <?php echo file_get_contents('/path/to/file'); ?>`

У цьому випадку атакувальник напряму завантажує PHP‑файл на сервер. Якщо сервер дозволяє PUT і зберігає файл у вебдоступній директорії та ще й виконує PHP‑код, це може призвести до **віддаленого виконання коду**.

**Порада: можна надсилати HTTP‑запити OPTIONS до різних endpoint’ів, щоб перевірити, чи сервер повідомляє про підтримку методу PUT.**

## How to prevent file upload vulnerabilities

- **Перевіряти розширення файлу за whitelist‑ом (білим списком)** дозволених розширень, а не за blacklist‑ом (чорним списком) заборонених. Набагато легше визначити, які формати _дозволені_, ніж передбачити всі варіанти, які може використати атакувальник.
- **Переконатися, що ім’я файлу не містить підрядків**, які можуть бути інтерпретовані як шлях або directory traversal (`../`).
- **Перейменовувати завантажені файли**, щоб уникнути конфліктів і випадкового перезапису існуючих файлів.
- **Не зберігати файли у постійній файловій системі сервера**, доки вони не пройшли повну перевірку.
- **По можливості використовувати готові фреймворки** для обробки завантажень файлів, а не писати власну логіку валідації, яка часто містить помилки.
