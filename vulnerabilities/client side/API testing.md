**APIs (інтерфейси прикладного програмування)** дозволяють програмним системам і застосункам взаємодіяти та обмінюватися даними. **Тестування API** є важливим, оскільки вразливості в API можуть підірвати ключові аспекти вебсайту: **конфіденційність, цілісність і доступність**.

## API recon

Щоб розпочати **тестування API**, спочатку потрібно зібрати якомога більше інформації про API, щоб визначити його **поверхню атаки**.

Насамперед слід **ідентифікувати API-ендпоїнти**. Це адреси, за якими API приймає запити щодо певного ресурсу на сервері. Наприклад, розглянемо такий GET-запит:

`GET /api/books HTTP/1.1 Host: example.com`

Ендпоїнтом API для цього запиту є **/api/books**. Він призводить до взаємодії з API з метою отримання списку книг із бібліотеки. Іншим ендпоїнтом API може бути, наприклад, **/api/books/mystery**, який повертає список книг жанру детектив.

Після того як ендпоїнти визначено, необхідно зʼясувати, **як з ними взаємодіяти**. Це дозволить сформувати коректні HTTP-запити для тестування API. Зокрема, потрібно дізнатися таку інформацію:

- які **вхідні дані** обробляє API, зокрема обовʼязкові та необовʼязкові параметри;
    
- які **типи запитів** приймає API, включаючи підтримувані HTTP-методи та формати даних;
    
- наявні **обмеження швидкості запитів (rate limits)** та **механізми автентифікації**.


## API documentation

API зазвичай мають **документацію**, щоб розробники знали, як ними користуватися та інтегрувати їх у свої застосунки.

Документація може бути **людиночитною** та **машиночитною**.  
Людиночитна документація призначена для розробників і пояснює, як користуватися API. Вона може містити детальні описи, приклади та сценарії використання.  
Машиночитна документація призначена для обробки програмами з метою автоматизації таких завдань, як інтеграція API та його перевірка. Вона зазвичай записується у структурованих форматах, таких як **JSON** або **XML**.

Документація API часто є **публічно доступною**, особливо якщо API призначений для використання сторонніми розробниками. Якщо це так, завжди варто **починати розвідку (recon)** саме з вивчення документації.

### Discovering API documentation

Навіть якщо **документація API** не є відкрито доступною, її все одно можна знайти, **переглядаючи застосунки**, які використовують цей API.

Для цього можна скористатися **Burp Scanner**, щоб просканувати (crawl) API. Також можна **вручну переглядати застосунок** за допомогою вбудованого браузера Burp. Звертай увагу на ендпоїнти, які можуть вести до документації API, наприклад:

```
/api 
/swagger/index.html
/openapi.json`
```

Якщо ти знайшов ендпоїнт певного ресурсу, обов’язково досліди **базовий шлях**. Наприклад, якщо виявлено ендпоїнт ресурсу  
`/api/swagger/v1/users/123`,  
тоді варто перевірити такі шляхи:

```
/api/swagger/v1 
/api/swagger
/api
```

Також можна використовувати **список поширених шляхів** і шукати документацію за допомогою **Burp Intruder**.

### Using machine-readable documentation

Для аналізу **машиночитної документації API** можна використовувати різні автоматизовані інструменти.

Наприклад, можна скористатися **Burp Scanner** для сканування та аудиту документації **OpenAPI**, а також будь-якої іншої документації у форматах **JSON** або **YAML**. Також OpenAPI-документацію можна розібрати за допомогою **OpenAPI Parser BApp**.

Крім цього, можна використовувати **спеціалізовані інструменти** для тестування задокументованих ендпоїнтів, такі як **Postman** або **SoapUI**.

## Identifying API endpoints

Також можна зібрати багато корисної інформації, **переглядаючи застосунки, які використовують API**. Це часто варто робити навіть тоді, коли в тебе є доступ до документації API, оскільки вона іноді може бути **неточною або застарілою**.

Можна скористатися **Burp Scanner**, щоб просканувати застосунок, а потім **вручну дослідити цікаву поверхню атаки** за допомогою вбудованого браузера Burp.

Під час перегляду застосунку звертай увагу на **шаблони в URL**, які можуть вказувати на API-ендпоїнти, наприклад `/api/`. Також обов’язково переглядай **JavaScript-файли** — вони можуть містити посилання на API-ендпоїнти, які ти не викликав безпосередньо через браузер.  
**Burp Scanner** автоматично витягує деякі ендпоїнти під час сканування, але для більш глибокого аналізу можна використати **JS Link Finder BApp**. Також JavaScript-файли можна **переглядати вручну** безпосередньо в Burp.

### Identifying supported HTTP methods

**HTTP-метод** визначає дію, яка має бути виконана над ресурсом. Наприклад:

- **GET** — отримує дані з ресурсу.
    
- **PATCH** — застосовує часткові зміни до ресурсу.
    
- **OPTIONS** — отримує інформацію про типи HTTP-запитів, які можна використовувати для ресурсу.
    

Один API-ендпоїнт може підтримувати **різні HTTP-методи**, тому під час дослідження API важливо перевіряти **всі можливі методи**. Це може допомогти виявити **додаткову функціональність ендпоїнта**, що розширює поверхню атаки.

Наприклад, ендпоїнт **/api/tasks** може підтримувати такі методи:

- **GET /api/tasks** — повертає список завдань.
    
- **POST /api/tasks** — створює нове завдання.
    
- **DELETE /api/tasks/1** — видаляє завдання.
    

Для автоматичного перебору різних HTTP-методів можна використати **вбудований список HTTP-дієслів у Burp Intruder**.

Під час тестування різних HTTP-методів варто працювати з **низькопріоритетними об’єктами**. Це допоможе уникнути небажаних наслідків, наприклад зміни критично важливих даних або створення надмірної кількості записів.

#### Identifying supported content types

API-ендпоїнти часто очікують дані у **певному форматі**, тому можуть поводитися по-різному залежно від **типу вмісту (content type)**, який передається в запиті. Зміна типу вмісту може дозволити:

- викликати **помилки**, що розкривають корисну інформацію;
    
- **обійти некоректні механізми захисту**;
    
- скористатися **відмінностями в логіці обробки даних**. Наприклад, API може бути захищеним під час обробки JSON, але вразливим до інʼєкцій під час роботи з XML.
    

Щоб змінити тип вмісту, потрібно **відредагувати заголовок `Content-Type`**, а також відповідно **переформатувати тіло запиту**. Для автоматичного перетворення даних у запитах між **XML** та **JSON** можна скористатися **Content type converter BApp**.

Головна перевірка це метод OPTION, так можна зрозуміти які методи підтримуються, а також дивитись у бьорпі чи є там згадка про апі після того як посерфили на сайті.

#### Using Intruder to find hidden endpoints

Після того як ти **визначив початкові API-ендпоїнти**, можна використати **Burp Intruder** для пошуку **прихованих ендпоїнтів**. Наприклад, уявімо ситуацію, коли ти знайшов такий API-ендпоїнт для оновлення інформації користувача:

`PUT /api/user/update`

Щоб виявити приховані ендпоїнти, можна застосувати **Burp Intruder** для пошуку інших ресурсів із **подібною структурою**. Наприклад, ти можеш додати payload у позицію `/update` в URL і підставляти список інших поширених дій, таких як `delete` або `add`.

Під час пошуку прихованих ендпоїнтів використовуй **словники**, засновані на поширених **конвенціях іменування API** та термінах, що використовуються в індустрії. Також обов’язково додавай **терміни, релевантні конкретному застосунку**, які ти виявив під час початкової розвідки (recon).

## Finding hidden parameters

Під час **розвідки API (API recon)** ти можеш знайти **недокументовані параметри**, які підтримує API. Спробувавши використати їх, можна змінити **поведінку застосунку**. Burp містить багато інструментів, які допомагають знаходити **приховані параметри**:

- **Burp Intruder** дозволяє автоматично виявляти приховані параметри, використовуючи **словники поширених назв параметрів** для заміни наявних або додавання нових. Обов’язково додавай також назви, **релевантні конкретному застосунку**, на основі початкової розвідки.
    
- **Param Miner BApp** дозволяє автоматично вгадувати до **65 536 назв параметрів на один запит**. Param Miner підбирає назви, релевантні застосунку, використовуючи інформацію з **scope**.
    
- **Content Discovery tool** дозволяє знаходити контент, який **не пов’язаний з видимими сторінками**, доступними для перегляду, зокрема й параметри.
### Mass assignment vulnerabilities

**Mass assignment** (також відоме як **auto‑binding**) може ненавмисно створювати **приховані параметри**. Це відбувається тоді, коли програмні фреймворки **автоматично прив’язують параметри запиту до полів внутрішнього об’єкта**.

У результаті масового присвоєння застосунок може почати **підтримувати параметри, які розробник не планував обробляти**, що може призвести до серйозних проблем із безпекою.

#### Identifying hidden parameters

Оскільки **mass assignment** створює параметри з полів об’єкта, часто можна виявити такі **приховані параметри**, уважно проаналізувавши об’єкти, які повертає API.

Наприклад, розглянемо запит **PATCH /api/users/**, який дозволяє користувачам оновлювати ім’я користувача та email і містить такий JSON:

```
{ 
"username": "wiener",
"email": "wiener@example.com",
}
```

Одночасно запит **GET /api/users/123** повертає такий JSON:

```
{
 "id": 123,
 "name": "John Doe",
 "email": "john@example.com", 
 "isAdmin": "false" 
}
```
Це може свідчити про те, що **приховані параметри `id` та `isAdmin`** прив’язані до внутрішнього об’єкта користувача разом з параметрами `username` та `email`, які оновлюються.

#### Testing mass assignment vulnerabilities

Щоб перевірити, чи можна змінити знайдений параметр **`isAdmin`**, додай його до PATCH-запиту:

```
{     
"username": "wiener",     
"email": "wiener@example.com",     
"isAdmin": false
}
```

Додатково надішли PATCH-запит з **некоректним значенням** параметра `isAdmin`:

```
{     
"username": "wiener",     
"email": "wiener@example.com",     
"isAdmin": "foo" 
}
```

Якщо застосунок поводиться **по-різному**, це може означати, що некоректне значення впливає на логіку запиту, а коректне — ні. Це може свідчити про те, що параметр **можна успішно змінювати**.

Після цього можна надіслати PATCH-запит зі значенням `isAdmin`, встановленим у `true`, щоб спробувати **експлуатувати вразливість**:

```
{     
"username": "wiener",     
"email": "wiener@example.com",     
"isAdmin": true 
}
```

Якщо значення `isAdmin` з запиту прив’язується до об’єкта користувача **без належної валідації та фільтрації**, користувач **wiener** може помилково отримати **права адміністратора**. Щоб перевірити це, увійди в застосунок від імені **wiener** та подивись, чи з’явився доступ до **адміністративного функціоналу**.

## Preventing vulnerabilities in APIs

Під час **проєктування API** важливо з самого початку враховувати **питання безпеки**. Зокрема, переконайся, що ти:

- **Захищаєш документацію**, якщо не плануєш робити API публічно доступним.
    
- **Підтримуєш документацію в актуальному стані**, щоб легітимні тестувальники мали повне уявлення про поверхню атаки API.
    
- **Застосовуєш allowlist дозволених HTTP-методів**.
    
- **Перевіряєш тип вмісту (content type)** для кожного запиту та відповіді, щоб він відповідав очікуваному.
    
- **Використовуєш загальні повідомлення про помилки**, аби не розкривати інформацію, корисну для зловмисника.
    
- **Застосовуєш захисні механізми до всіх версій API**, а не лише до поточної продакшн-версії.
    
- Для запобігання **вразливостям масового присвоєння (mass assignment)** використовуєш **allowlist властивостей**, які користувач може змінювати, та **blocklist чутливих властивостей**, змінювати які користувачу не дозволено.


# Server-side parameter pollution

Деякі системи містять **внутрішні API**, які **не доступні безпосередньо з інтернету**. **Забруднення параметрів на стороні сервера (server-side parameter pollution)** виникає тоді, коли вебсайт **вставляє введені користувачем дані в серверний запит до внутрішнього API без належного кодування**. У результаті зловмисник може **маніпулювати або інʼєктувати параметри**, що, наприклад, дозволяє:

- **перезаписувати наявні параметри**;
    
- **змінювати поведінку застосунку**;
    
- **отримувати несанкціонований доступ до даних**.
    

Будь-які **вхідні дані користувача** варто перевіряти на можливість **забруднення параметрів**. Наприклад, вразливими можуть бути **параметри запиту (query parameters)**, **поля форм**, **HTTP-заголовки** та **параметри в URL-шляху**.

## Testing for server-side parameter pollution in the query string

Щоб перевірити **забруднення параметрів на стороні сервера** в рядку запиту (query string), вставляй у введені дані **спеціальні символи синтаксису запиту**, такі як `#`, `&` і `=`, та спостерігай, **як реагує застосунок**.

Розглянемо вразливий застосунок, який дозволяє шукати інших користувачів за ім’ям користувача. Під час пошуку браузер надсилає такий запит:

`GET /userSearch?name=peter&back=/home`

Щоб отримати інформацію про користувача, сервер звертається до **внутрішнього API** з таким запитом:

`GET /users/search?name=peter&publicProfile=true`

### Truncating query strings

Можна використати **URL-кодований символ `#`**, щоб спробувати **усікти серверний запит**. Щоб легше було інтерпретувати відповідь, після символу `#` можна додати будь‑який рядок.

Наприклад, можна змінити рядок запиту так:

`GET /userSearch?name=peter%23foo&back=/home`

У результаті фронтенд спробує звернутися до такого URL:

`GET /users/search?name=peter#foo&publicProfile=true`

Дуже важливо **URL-кодувати символ `#`**. Інакше фронтенд‑застосунок сприйме його як **ідентифікатор фрагмента** і не передасть у внутрішній API.

Уважно проаналізуй **відповідь сервера**, шукаючи ознаки того, чи було **усічено запит**. Наприклад:

- якщо у відповіді повертається користувач **peter**, це може означати, що серверний запит був усічений;
    
- якщо ж повертається помилка **Invalid name**, застосунок міг сприйняти `foo` як частину імені користувача, що вказує на те, що серверний запит, ймовірно, **не був усічений**.
    

Якщо вдається усікти серверний запит, **вимога встановлення параметра `publicProfile=true` зникає**. Це може дозволити **повернути непублічні профілі користувачів**, тобто експлуатувати вразливість.

### Injecting invalid parameters

Можна використати **URL-кодований символ `&`**, щоб спробувати **додати другий параметр** у серверний запит.

Наприклад, можна змінити рядок запиту так:

`GET /userSearch?name=peter%26foo=xyz&back=/home`

У результаті це призведе до такого **серверного запиту до внутрішнього API**:

`GET /users/search?name=peter&foo=xyz&publicProfile=true`

Уважно проаналізуй **відповідь сервера**, шукаючи підказки щодо того, **як обробляється додатковий параметр**. Наприклад, якщо відповідь **не змінилася**, це може означати, що параметр було **успішно інʼєктовано**, але застосунок його **проігнорував**.

Щоб сформувати **повнішу картину**, потрібно провести **додаткове тестування**.

### Injecting valid parameters

Якщо тобі вдалося **змінювати рядок запиту**, далі можна спробувати **додати другий коректний параметр** у серверний запит.

Наприклад, якщо ти виявив параметр **`email`**, можна додати його до рядка запиту так:

`GET /userSearch?name=peter%26email=foo&back=/home`

У результаті це призведе до такого **серверного запиту до внутрішнього API**:

`GET /users/search?name=peter&email=foo&publicProfile=true`

Уважно проаналізуй **відповідь сервера**, щоб зрозуміти, **як обробляється додатковий параметр**.

### Overriding existing parameters

Щоб підтвердити, чи є застосунок вразливим до **забруднення параметрів на стороні сервера**, можна спробувати **перезаписати початковий параметр**. Для цього інʼєктуй **другий параметр з такою самою назвою**.

Наприклад, можна змінити рядок запиту так:

`GET /userSearch?name=peter%26name=carlos&back=/home`

У результаті це призведе до такого **серверного запиту до внутрішнього API**:

`GET /users/search?name=peter&name=carlos&publicProfile=true`

Внутрішній API отримує **два параметри `name`**. Наслідки залежать від того, **як саме застосунок обробляє другий параметр**, що відрізняється в різних вебтехнологіях. Наприклад:

- **PHP** обробляє лише **останній параметр**. У результаті пошук користувача виконуватиметься для **carlos**.
    
- **ASP.NET** **об’єднує обидва параметри**. Це призведе до пошуку **peter,carlos**, що може викликати повідомлення про помилку _Invalid username_.
    
- **Node.js / Express** обробляє лише **перший параметр**. У цьому випадку пошук виконуватиметься для **peter**, і результат не зміниться.
    

Якщо тобі вдається **перезаписати початковий параметр**, це може дозволити **експлуатувати вразливість**. Наприклад, можна додати `name=administrator` у запит, що потенційно дозволить **увійти в систему під обліковим записом адміністратора**.

## Testing for server-side parameter pollution in REST paths

**RESTful API** може розміщувати **назви та значення параметрів у URL‑шляху**, а не в рядку запиту. Наприклад, розглянемо такий шлях:

`/api/users/123`

URL‑шлях можна розбити так:

- **/api** — кореневий ендпоїнт API
    
- **/users** — ресурс, у цьому випадку користувачі
    
- **/123** — параметр, ідентифікатор конкретного користувача
    

Розглянемо застосунок, який дозволяє редагувати профілі користувачів за їхнім іменем. Запити надсилаються до такого ендпоїнта:

`GET /edit_profile.php?name=peter`

Це призводить до такого **серверного запиту**:

`GET /api/private/users/peter`

Зловмисник може спробувати **маніпулювати параметрами в URL‑шляху на стороні сервера**, щоб експлуатувати API. Для перевірки цієї вразливості можна додати **послідовності обходу шляху (path traversal)**, змінюючи параметри та спостерігаючи за реакцією застосунку.

Наприклад, можна передати **URL‑кодоване значення** `peter/../admin` як значення параметра `name`:

`GET /edit_profile.php?name=peter%2f..%2fadmin`

У результаті сервер може сформувати такий запит:

`GET /api/private/users/peter/../admin`

Якщо серверний клієнт або бекенд‑API **нормалізує цей шлях**, він може бути перетворений на:

`/api/private/users/admin`

Це може дозволити доступ до **профілю адміністратора**, що вказує на потенційну вразливість.

## Testing for server-side parameter pollution in structured data formats

Зловмисник може **маніпулювати параметрами**, щоб експлуатувати вразливості в обробці сервером **інших структурованих форматів даних**, таких як **JSON** або **XML**. Щоб перевірити це, інʼєктуй **неочікувані структуровані дані** у користувацьке введення та спостерігай за реакцією сервера.

Розглянемо застосунок, який дозволяє користувачам редагувати свій профіль, а потім застосовує зміни через запит до серверного API. Коли ти змінюєш ім’я, браузер надсилає такий запит:

`POST /myaccount name=peter`

Це призводить до такого **серверного запиту**:

`PATCH /users/7312/update {"name":"peter"}`

Ти можеш спробувати додати параметр **`access_level`** до запиту так:

`POST /myaccount name=peter","access_level":"administrator`

Якщо введені користувачем дані **додаються до серверного JSON без належної валідації або санітизації**, це призведе до такого серверного запиту:

`PATCH /users/7312/update {name="peter","access_level":"administrator"}`

У результаті користувач **peter** може отримати **права адміністратора**.

Розглянемо подібний приклад, але коли **клієнтське введення передається у форматі JSON**. Коли ти змінюєш ім’я, браузер надсилає такий запит:

`POST /myaccount {"name": "peter"}`

Це призводить до такого серверного запиту:

`PATCH /users/7312/update {"name":"peter"}`

Ти можеш спробувати додати параметр **`access_level`** так:

`POST /myaccount {"name": "peter\",\"access_level\":\"administrator"}`

Якщо користувацьке введення **декодується**, а потім **додається до серверного JSON без належного кодування**, це призведе до такого серверного запиту:

`PATCH /users/7312/update {"name":"peter","access_level":"administrator"}`

Знову ж таки, це може призвести до того, що користувач **peter** отримає **адміністративні привілеї**.

---

**Інʼєкції у структуровані формати** можуть також виникати у **відповідях**. Наприклад, якщо користувацьке введення безпечно зберігається в базі даних, але потім **вбудовується в JSON‑відповідь бекенд‑API без належного кодування**. Зазвичай такі інʼєкції у відповідях можна виявити та експлуатувати **так само, як і в запитах**.

## Testing with automated tools

**Burp Scanner** автоматично визначає **підозрілі трансформації введених даних** під час проведення аудиту. Вони виникають тоді, коли застосунок отримує введення користувача, **певним чином змінює його**, а потім виконує подальшу обробку результату. Така поведінка **не завжди означає наявність вразливості**, тому необхідно провести **додаткове ручне тестування** з використанням описаних вище методів. Детальніше дивись у визначенні проблеми **Suspicious input transformation**.

Також можна скористатися **Backslash Powered Scanner BApp** для виявлення **серверних інʼєкційних вразливостей**. Сканер класифікує введені дані як **boring (нецікаві)**, **interesting (цікаві)** або **vulnerable (вразливі)**. **Цікаві** введення потрібно додатково досліджувати за допомогою **ручних технік**, описаних вище. Докладніше дивись у документі **Backslash Powered Scanning: hunting unknown vulnerability classes**.

## Preventing server-side parameter pollution

Щоб **запобігти server-side parameter pollution**, використовуй **allowlist** символів, які **не потребують кодування**, і переконайся, що **всі інші дані, введені користувачем, кодуються** перед включенням у серверний запит.

Також необхідно забезпечити, щоб **усі вхідні дані відповідали очікуваному формату та структурі**. Це допоможе запобігти маніпуляціям параметрами та зменшить ризик експлуатації вразливостей.
