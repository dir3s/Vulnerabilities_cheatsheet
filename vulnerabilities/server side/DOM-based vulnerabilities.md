## What is the DOM?

Об’єктна модель документа (DOM) — це ієрархічне представлення елементів сторінки у веббраузері. Вебсайти можуть використовувати JavaScript для маніпулювання вузлами та об’єктами DOM, а також їхніми властивостями. Сама по собі маніпуляція DOM не є проблемою — навпаки, це невід’ємна частина роботи сучасних вебсайтів.

Однак JavaScript, який небезпечно обробляє дані, може призводити до різних атак. DOM-орієнтовані вразливості виникають тоді, коли сайт містить JavaScript, що бере значення, контрольоване атакувальником (джерело, _source_), і передає його в небезпечну функцію (приймач, _sink_).

## Taint-flow vulnerabilities

Багато DOM-орієнтованих вразливостей зводяться до проблем у тому, як клієнтський код обробляє дані, контрольовані атакувальником.
### What is taint flow?

Щоб або експлуатувати, або запобігати таким вразливостям, важливо спочатку зрозуміти основи потоку даних між джерелами (_sources_) і приймачами (_sinks_).
#### Sources

Джерело — це властивість JavaScript, яка приймає дані, що потенційно контролюються атакувальником. Прикладом джерела є властивість `location.search`, оскільки вона читає дані з рядка запиту URL, який атакувальнику досить легко контролювати.

Загалом, будь-яка властивість, якою може керувати атакувальник, є потенційним джерелом. До них належать:

- URL, з якого прийшов користувач (доступний через `document.referrer`);
    
- cookies користувача (доступні через `document.cookie`);
    
- веб-повідомлення (web messages).
#### Sinks

Приймач — це потенційно небезпечна JavaScript-функція або DOM-об’єкт, який може призвести до небажаних наслідків, якщо йому передати дані, контрольовані атакувальником.

Наприклад, функція `eval()` є приймачем, оскільки вона обробляє переданий аргумент як JavaScript-код. Прикладом HTML-приймача є `document.body.innerHTML`, адже він може дозволити атакувальнику вставити шкідливий HTML і виконати довільний JavaScript.

У загальному вигляді DOM-орієнтовані вразливості виникають тоді, коли сайт передає дані з джерела в приймач, а той обробляє їх небезпечним способом у контексті сесії клієнта.

Найпоширенішим джерелом є URL, до якого зазвичай звертаються через об’єкт `location`. Атакувальник може створити посилання, яке приведе жертву на вразливу сторінку з payload’ом у рядку запиту або фрагменті URL. Приклад коду:
```
goto = location.hash.slice(1)
if (goto.startsWith('https:')) {
  location = goto;
}
```
Цей код уразливий до DOM-орієнтованого відкритого перенаправлення (DOM-based open redirect), оскільки джерело `location.hash` обробляється небезпечним чином. Якщо URL містить hash-фрагмент, що починається з `https:`, код бере значення `location.hash` і встановлює його як нове значення `location` для вікна браузера.

Атакувальник може скористатися цим, створивши такий URL:
```
https://www.innocent-website.com/example#https://www.evil-user.net
```
Коли жертва переходить за цим посиланням, JavaScript встановлює `location` рівним `https://www.evil-user.net`, що автоматично перенаправляє користувача на шкідливий сайт. Таку поведінку легко використати, наприклад, для фішингової атаки.
### Common sources

Нижче наведені типові **джерела (sources)**, які можуть бути використані для експлуатації різних вразливостей, пов’язаних із потоком «заражених» даних (taint flow):

- `document.URL`
- `document.documentURI`
- `document.URLUnencoded`
- `document.baseURI`
- `location`
- `document.cookie`
- `document.referrer`
- `window.name`
- `history.pushState`
- `history.replaceState`
- `localStorage`
- `sessionStorage`
- `IndexedDB` (`mozIndexedDB`, `webkitIndexedDB`, `msIndexedDB`)
- `Database`

Наступні типи даних також можуть використовуватися як джерела для експлуатації taint-flow вразливостей:

- Reflected data
- Stored data
- Web messages
# Controlling the web message source

У цьому розділі ми розглянемо, як **веб-повідомлення (web messages)** можуть використовуватися як **джерело (source)** для експлуатації DOM-вразливостей на сторінці-отримувачі. Також буде описано, як будується така атака, включно з тим, як часто вдається обійти поширені техніки перевірки походження (origin).

Якщо сторінка небезпечно обробляє вхідні веб-повідомлення - наприклад, неправильно або взагалі не перевіряє `origin` у слухачі подій - тоді властивості та функції, які викликаються цим слухачем, потенційно стають **sink’ами**. Наприклад, зловмисник може розмістити шкідливий `iframe` і використати метод `postMessage()` для передачі даних веб-повідомлення у вразливий обробник подій, який потім передає цей payload у небезпечний sink на батьківській сторінці. Це означає, що веб-повідомлення можна використовувати як джерело для поширення шкідливих даних до будь-якого з таких sink’ів.

## What is the impact of DOM-based web message vulnerabilities?

Потенційний вплив цієї вразливості залежить від того, **як документ-отримувач обробляє вхідне повідомлення**. Якщо документ-отримувач довіряє відправнику й вважає, що той не передаватиме шкідливі дані, і при цьому обробляє отримані дані небезпечним чином — наприклад, передаючи їх у sink — тоді спільна поведінка цих двох документів може дозволити зловмиснику скомпрометувати користувача.

## How to construct an attack using web messages as the source

Розглянемо наступний код:
```
<script>
window.addEventListener('message', function(e) {
  eval(e.data);
});
</script>
```
Цей код є вразливим, оскільки атакувальник може вставити JavaScript-навантаження, створивши такий iframe:
```
<iframe src="//vulnerable-website" onload="this.contentWindow.postMessage('print()','*')">
```
Оскільки обробник подій не перевіряє походження повідомлення, а метод `postMessage()` використовує значення `targetOrigin` `"*"`, обробник приймає корисне навантаження та передає його у небезпечну функцію (sink), у цьому випадку — `eval()`.
## Origin verification

Навіть якщо обробник подій містить певну перевірку походження (origin), ця перевірка інколи може бути принципово помилковою. Наприклад, розглянемо такий код:
```
window.addEventListener('message', function(e) {
    if (e.origin.indexOf('normal-website.com') > -1) {
        eval(e.data);
    }
});
```
Метод `indexOf` використовується для спроби перевірити, що походження вхідного повідомлення — це домен `normal-website.com`. Однак на практиці він лише перевіряє, чи міститься рядок `"normal-website.com"` десь у URL походження. У результаті атакувальник може легко обійти цю перевірку, якщо походження його шкідливого повідомлення буде, наприклад, `http://www.normal-website.com.evil.net`.

Та сама помилка стосується й перевірок, які використовують методи `startsWith()` або `endsWith()`. Наприклад, наступний обробник подій вважатиме безпечним походження `http://www.malicious-websitenormal-website.com`:
```
window.addEventListener('message', function(e) {
    if (e.origin.endsWith('normal-website.com')) {
        eval(e.data);
    }
});
```
Приклад експлоїта:
```
<iframe src=https://YOUR-LAB-ID.web-security-academy.net/
onload='this.contentWindow.postMessage("{\"type\":\"load-channel\",\"url\":\"javascript:print()\"}","*")'>
```
Коли цей `iframe` завантажується, він **відразу надсилає web-message** (`postMessage`) на сторінку лабораторії.  
Повідомлення — це JSON-рядок з:

- `type: "load-channel"`
    
- `url: "javascript:print()"`
    
Другий параметр `"*"` означає: **дозволено будь-яке походження (origin)**.

### How to prevent DOM-based taint-flow vulnerabilities

Не існує єдиної дії, яка повністю усуне загрозу DOM-based атак. Проте загалом **найефективніший спосіб** уникнути DOM-based вразливостей — **не дозволяти даним з ненадійних джерел динамічно змінювати значення, які передаються в sinks**.

Якщо функціональність застосунку робить таку поведінку неминучою, тоді захист потрібно реалізовувати **на стороні клієнта**. У багатьох випадках відповідні дані можна перевіряти за принципом **білого списку**, дозволяючи лише завідомо безпечний вміст. В інших випадках необхідно **очищати або кодувати** дані.

Це може бути складним завданням і, залежно від контексту, у який вставляються дані, може вимагати **комбінації JavaScript-екранування, HTML-кодування та URL-кодування**, застосованих у правильній послідовності.
# DOM-based open redirection

## What is DOM-based open redirection?

DOM-based вразливості **відкритого перенаправлення (open redirection)** виникають тоді, коли скрипт записує дані, які може контролювати атакувальник, у **sink**, здатний ініціювати перехід на інший домен.

Наприклад, наведений нижче код є вразливим через небезпечну обробку властивості `location.hash`:
```
let url = /https?:\/\/.+/.exec(location.hash);
if (url) {
  location = url[0];
}
```
Атакувальник може скористатися цією вразливістю, щоб сконструювати URL, який, якщо інший користувач його відкриє, призведе до перенаправлення на довільний зовнішній домен.
## What is the impact of DOM-based open redirection?

Таку поведінку можна використати, наприклад, для проведення **фішингових атак** проти користувачів вебсайту. Можливість застосувати **справжній URL легітимного застосунку**, який вказує на правильний домен і має **дійсний TLS‑сертифікат** (якщо використовується TLS), підвищує довіру до фішингової атаки. Багато користувачів, навіть якщо вони перевіряють ці ознаки, не помічають подальшого перенаправлення на інший домен.

Якщо атакувальник може контролювати **початок рядка**, який передається в API перенаправлення, то цю вразливість можна **підвищити до інʼєкції JavaScript**. У такому випадку атакувальник може сконструювати URL з псевдопротоколом `javascript:`, щоб виконати довільний код у момент, коли браузер обробляє цей URL.

## Which sinks can lead to DOM-based open-redirection vulnerabilities?

Нижче наведено основні **sink-и**, які можуть призводити до **DOM‑based open‑redirection вразливостей**:

- `location`
- `location.host`
- `location.hostname`
- `location.href`
- `location.pathname`
- `location.search`
- `location.protocol`
- `location.assign()`
- `location.replace()`
- `open()`
- `element.srcdoc`
- `XMLHttpRequest.open()`
- `XMLHttpRequest.send()`
- `jQuery.ajax()`
- `$.ajax()`

Усі ці sink-и є небезпечними, якщо в них потрапляють дані, які контролює атакувальник, оскільки вони можуть спричинити перенаправлення користувача на довільний (зовнішній) ресурс.

# DOM-based cookie manipulation

## What is DOM-based cookie manipulation?

Деякі **DOM‑based вразливості** дозволяють атакувальникам маніпулювати даними, які зазвичай вони не контролюють. Це перетворює зазвичай безпечні типи даних, наприклад **cookies**, на потенційні **sources**.  
**DOM‑based cookie‑manipulation вразливості** виникають тоді, коли скрипт записує дані, контрольовані атакувальником, у значення cookie.

Атакувальник може використати цю вразливість, щоб створити URL, який, у разі відвідування іншим користувачем, встановить довільне значення cookie в браузері жертви. Багато sink-ів самі по собі виглядають відносно нешкідливими, але атаки на основі маніпуляції cookies показують, як вразливості низької критичності іноді можуть бути частиною ланцюжка експлойтів, що призводить до серйозної атаки.

Наприклад, якщо JavaScript записує дані з source у `document.cookie` без попередньої санітизації, атакувальник може змінити значення cookie та вставити довільні дані:

`document.cookie = 'cookieName=' + location.hash.slice(1);`

Якщо вебсайт небезпечно відображає значення cookies без HTML‑кодування, атакувальник може використати техніки маніпуляції cookies для експлуатації цієї поведінки.
Приклад експлоїта:
```
<iframe src="https://YOUR-LAB-ID.web-security-academy.net/product?productId=1&'><script>print()</script>" onload="if(!window.x)this.src='https://YOUR-LAB-ID.web-security-academy.net';window.x=1;">
```
Цей код використовує **iframe для запуску XSS‑payload’у**. Спочатку iframe завантажує сторінку `/product` з параметром `productId`, у який підставлено шкідливий фрагмент `'><script>print()</script>`. Через те, що значення параметра відображається на сторінці без належного екранування, інʼєкція закриває HTML‑контекст і вставляє тег `<script>`, який браузер виконує. У результаті викликається `print()`, що підтверджує успішне виконання JavaScript у контексті жертви.

Обробник `onload` потрібен, щоб уникнути проблем із повторним завантаженням. Під час першого завантаження змінної `window.x` ще немає, тому iframe один раз перенаправляється на головну сторінку сайту, після чого `window.x` встановлюється в `1`. При наступному `onload` умова вже не спрацьовує, і перенаправлення не відбувається. Це дозволяє **один раз виконати XSS**, а потім стабілізувати поведінку iframe без нескінченних перезавантажень.
## What is the impact of a DOM-based cookie-manipulation attack?

Потенційний вплив цієї вразливості залежить від ролі, яку cookie відіграє на вебсайті. Якщо cookie використовується для керування поведінкою, що впливає на дії користувача (наприклад, перемикання між **production** та **demo** режимами), тоді атакувальник може змусити користувача виконувати небажані або неочікувані дії шляхом маніпуляції значенням cookie.

Якщо ж cookie використовується для відстеження сесії користувача, атакувальник може здійснити **атаку фіксації сесії (session fixation)**. У такому випадку він встановлює значення cookie на валідний токен сесії, який заздалегідь отримав із сайту, а потім перехоплює сесію під час подальшої взаємодії жертви з вебсайтом.

Подібна вразливість маніпуляції cookies може бути використана для атак не лише на конкретний уразливий сайт, але й на будь‑які інші сайти, що знаходяться в межах того самого батьківського домену.
